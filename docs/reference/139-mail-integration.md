# 中国移动 139 邮箱调研与接入评估

状态：**Implemented / 专用预设、授权码引导与官方帮助入口已有实现，已获用户手测反馈，完整兼容矩阵待补充** · 2026-10-29。

调研与实施基线为 `c7a6bbb`。本轮查阅中国移动官方帮助、审查现有代码，并做了不带账号或凭证的公开端点探测；后续按既有 QQ / 网易流程实现预设与引导。Agent 没有登录真实邮箱、读取邮件或发送邮件；用户手测反馈单独记录在第 6 节。下面区分官方规则、现有实现、公开探测和待验证事项。

## 1. 结论与建议范围

**可行性高，已按既有服务商流程加入预设。** 使用 **IMAP + SMTP + 邮箱授权码**，复用 MailX 的账号模型、SecretStore、账号路由、同步、正文读取、标记写回和发送队列。该路径没有 OAuth 应用注册依赖，本次没有新增认证类型、数据库迁移或核心协议特判。

| 配置 | 建议 |
| --- | --- |
| 首轮入口 | “139 邮箱”，仅匹配个人邮箱 `139.com`，内部 ID 为 `139` |
| 接收服务器 | `imap.139.com:993`，隐式 TLS |
| 发送服务器 | `smtp.139.com:465`，隐式 TLS，要求认证 |
| 邮箱地址 | 优先验证 `手机号@139.com` 主地址 |
| 登录用户名 | 可先沿用完整邮箱地址默认值，保留收发独立覆盖；手机号登录名与完整地址分别实测 |
| 凭证 | 用户在官方网页生成的邮箱授权码，收发共用一份 |

官方服务器表明确列出上述加密端口 [S1][S2]。部分基础教程只列 143/25 [S3]，不能据此采用明文默认配置或在 TLS 失败后降级。`imap.10086.cn` / `smtp.10086.cn` 也在官方表中，但首轮只采用一组固定默认端点，不自动轮换主机或端口；587 没有本轮官方依据。

当前可通过专用预设或通用 IMAP/SMTP 入口配置。已有用户手测反馈，但反馈没有逐项列出平台、登录名及收发场景，完整兼容矩阵仍需补充证据。首轮不扩大到中国移动企业邮箱、任意自有域名或其他品牌邮箱；也不自动合并手机号地址与别名对应的账号。

## 2. 账号资格与授权码生命周期

### 服务开通

官方明确 POP3/IMAP 默认关闭 [S4]。用户需在网页版邮箱的“设置 → 常规设置 → 账户与安全 → 邮箱协议设置”开启 IMAP/SMTP 并保存，按页面完成短信验证，然后获取授权码 [S5]。MailX 应提供固定官方帮助链接，具体按钮和验证流程以账号当时页面为准。

授权码是第三方客户端使用的专用密码，适用于 IMAP/SMTP 等服务 [S6]；官方 Foxmail 教程明确要求密码栏填写授权码 [S7]。产品应明确区分邮箱主密码、短信验证码与客户端授权码，不替用户在应用内完成开通或短信验证。

### 90 天有效期

官方“如何生成授权码”明确：**新生成的授权码有效期为 90 天，授权码旁会显示具体失效日期** [S5]。这是接入后的持续维护条件。

- 首版引导告知会到期，并提供修改授权码和官方帮助入口；认证被拒绝时将过期、撤销、服务关闭和账号安全验证列为排查项。
- MailX 没有这类授权码的自动刷新能力。本轮未找到自动续期、修改期限或旧码期限的官方承诺；重新生成是否立即撤销旧码也待验证。
- 不能从“保存到 MailX 的时间”推算真实到期日；用户可能导入已生成一段时间的码。到期提醒若以后实施，应由用户明确提供到期日或取得可靠接口依据。
- 在没有稳定服务器信号前，不能把普通认证失败精确标成“授权码已过期”，也不为 139 新增猜测性的错误解析。

### 运营商与付费边界

官方开通页特别注明：**暂不支持广电号码开启授权码** [S4]。因此，能注册或网页登录 139 邮箱，不等于该账号能接入第三方客户端；不能通过手机号前缀猜测携号转网后的资格。

官方资料说明联通、电信用户可以注册基础版且不收取月功能费 [S8]。客户端开通和授权码帮助没有写付费前置，现阶段不应引导用户为接入 MailX 购买会员；同时不把这些说明扩展为所有套餐、地区和号码的协议资格保证。联通、电信不能订购部分权益的规定 [S9] 也不等于 IMAP 被禁止。

### 登录名与别名

官方教程存在多种写法：Outlook 2016 手动配置写“用户名：139 邮箱手机号”，较早教程写完整 `手机号@139.com`，iPad 教程还涉及手机号和别名 [S10][S11][S12]。不能据此写死“必须去掉后缀”，也不能承诺任意别名均可直接认证或发信。

MailX 目前空用户名默认完整邮箱地址，已能分别覆盖 IMAP/SMTP 用户名。首轮用主地址验证完整地址；若失败，再由测试者明确改成官方列出的手机号登录名，分别记录，不在后台自动尝试多种身份。只有真实证据表明需要不同默认值时，才增加小型服务商登录名策略。别名登录、别名发件和主地址与别名的同邮箱关系单独验收。

## 3. 公开端点探测

2026-10-29 16:29（Asia/Shanghai），本机使用独立 Python 脚本直接连接两个默认端点，启用默认信任链和主机名校验。IMAP 仅执行 CAPABILITY / LOGOUT；SMTP 仅执行 EHLO / QUIT，没有 LOGIN / AUTH / MAIL / RCPT / DATA。

| 端点 | 本次观测 |
| --- | --- |
| `imap.139.com:993` | TLS 1.2，证书校验通过；登录前 CAPABILITY 为 `IMAP4rev1 XLIST ID RM_MAIL_TYPE UIDPLUS`。 |
| `smtp.139.com:465` | TLS 1.2，证书校验通过；EHLO 公告 `X-PART`、`PIPELINING`、`AUTH LOGIN PLAIN`、`AUTH=LOGIN PLAIN`、`8BITMIME`；未公告 SIZE。 |

结果证明这两个公开端点当时可达、可建立经过验证的 TLS，并提供 MailX 已有的协议能力。它不是 MailX 自身网络栈、代理路由或真实账号验证，也不证明登录后的能力、授权码认证、目录访问、持续连接或投递成功。登录前没有公告 IDLE / SPECIAL-USE，也不证明登录后或所有集群都不支持。

## 5. 需要重点验收的行为

### 目录、星标与历史范围

官方说明 IMAP 支持系统文件夹、代收邮件文件夹和自定义文件夹；VIP 邮件、星标邮件、待办任务以标签形态存在，不能作为相应 IMAP 目录收取 [S13]。不能承诺同步网页的这些聚合视图，也不能据此推断标准 `\Flagged` 不受支持；网页星标与 IMAP flags 的映射要单独实测。

MailX 的目录发现目前使用普通 `LIST "" *`（`core/src/imap/mod.rs:387`），没有因为服务器公告 XLIST 就自动改发 XLIST。目录角色先读 LIST 属性，再按常见中英文名称识别（`core/src/sync/folders.rs:115`）。如果 139 仅在 XLIST 中返回角色、且真实名称不在兜底规则内，目录可能显示为 Other；可选目录仍可同步。应先采集脱敏 LIST 属性、目录名和层级，有差异再补适配。

官方“最近 100 天”收取选项明确**只对 POP 有效** [S14]，不能套用为 IMAP 限制。MailX 自身仍有首次固定 30 天起点、每轮至多最新 1,000 UID 等既有头部覆盖边界；不能宣传添加后即收取全部历史。正文、附件和缓存行为沿用当前实现。

### 发信配额与附件

官方规定一个账号一天最多发 **250 封邮件**、当天所发收件人最多 **450 人**，达到任一条件后当日不能继续发信 [S15]。本轮资料未明确计数去重、重置时刻或套餐例外，不应实现精确剩余额度或保证某时刻恢复；网页和其他客户端的消耗也不能由 MailX 本地发送数代表。

本次 SMTP 没有公告 SIZE。MailX 会跳过服务端 MIME 大小预检、照常发送，不会给 MAIL FROM 加 SIZE 参数（`core/src/smtp/mod.rs:713`）。这不代表无限大小。MailX 当前本地附件上限为原始字节合计 20 MiB、最多 20 个，编码后的完整 MIME 更大；139 的真实 SMTP 上限仍待验。网页上传的 50M 或会员“超大附件”权益均不能直接当成 SMTP 限制 [S16][S17]，也不能由此承诺 MailX 本地上限一定可投递。

### 已发送副本与发送结果

官方“默认保存已发送”文章讲的是网页写信开关 [S18]，不足以证明 SMTP 自动保存。需要检查 MailX 发信后的服务器已发送目录、Message-ID 和副本数量。当前 MailX 不做 IMAP APPEND，accepted MIME 与列表的本地副本合并也尚未实现；先观测服务商行为，再决定是否需要单独推进副本能力。

SMTP accepted、收件方实际到达和已发送可见分别记录。副本未出现不能触发重发；DATA 后连接中断仍遵守现有 unknown 不自动重发语义。

### 持续使用和错误恢复

本轮没有取得官方固定并发连接数、每分钟请求数、登录频率或 IP 风控阈值。MailX 同步、正文、标记写回和发信可能并行建连，不能宣称账号始终只有一个连接。沿用当前轮询与退避，验证与官方客户端同时在线、前后台切换、连续阅读和标记操作；不凭常见经验编造限额，也不通过压力测试真实邮箱探测封禁阈值。
