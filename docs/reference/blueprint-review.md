# 从启动蓝图到初始设计

状态：**Reference** · 2026-10-14。本页说明如何将维护者提供的《MailX 项目落地执行指南》转成可实施的启动草案；不复制个人原文或把其中的行动清单当作已授权执行的任务。

## 保留的愿景

跨平台、Rust / Tauri、本地优先、多账号邮箱、分账号网络路由、内置 AI、对外 MCP，以及后续单用户 Docker Web。这些共同构成项目起点，未来也允许重新审视。

## 本轮收敛

| 蓝图表述 / 留白 | 初始设计处理 | 理由 |
| --- | --- | --- |
| “全邮箱兼容”与 30+ 预设 | 先 IMAP / SMTP + 小规模实测矩阵 | 预设无法保证认证与租户策略允许接入 |
| Svelte 或 React | 暂选 React / TypeScript / Bun | 复用维护者已有经验，后续可重评 |
| 全部内容、凭证都在 SQLite | 凭证库分离，大对象放 blob 文件 | 区分缓存、秘密与持久化语义 |
| “绝不向第三方发送数据”与 BYOK 云模型并存 | 不设 MailX 中继；云 AI / MCP 需明确披露 | 与真实数据流一致 |
| reqwest 实现分账号代理 | HTTP 和 IMAP / SMTP 流分别适配，统一策略 | HTTP 代理设置不能自动覆盖其他协议 |
| 冷启动 300ms / 内存 80MB / 容器 30MB | 探索目标，先建立可重复基准 | WebView、数据集和 OS 会影响资源消耗 |
| AI + MCP Server 称“双向 MCP” | 区分端内 AI、对外 Server 与未来 Client | 不把两种集成误称双向协议能力 |
| 启动即暴露 MCP / SSE 端口 | 默认关闭；stdio 先行、远程 Streamable HTTP 后续 | 明确进程、协议与授权边界 |
| 起草或发送共用一个工具 | 初版只创建草稿，交互 UI 发送 | 防止动作语义与授权混淆 |
| OTP 默认暴露 | 专项工具暂缓；普通阅读也说明敏感范围 | 验证码属于高敏感邮件内容 |
| SQLite 文件夹可直接拷贝备份 | 首版停机全目录备份；后续一致性在线快照 | 处理 WAL 与 blob 引用一致性 |
| 第 7 周同时完成 Docker 与所有平台 | 桌面闭环后分阶段 Web | 降低首版不确定性，不绑定日期 |
| 竞品价格、内存、停更与安全结论 | 不写入公开事实或首版宣传 | 原文未附证据，也不是实施架构的必要前提 |
| 运行命令、包名、域名与下载入口 | 注册与构建完成后补充 | 不展示不存在的分发产物 |

## 仍需实现阶段再决定

依赖精确版本、OAuth 应用注册 / 发布资格、SMTP 自定义流接入方案、DTO 生成器、中文短词搜索、Linux 凭据库体验、签名资源、Web 密钥格式及远程 MCP 授权实现。路线图为这些事项留有验证或决策节点，不用臆测结果来填满设计。

开源许可证已由维护者确定为 [Apache-2.0](../../LICENSE)，并随首次提交纳入仓库。

## 如何继续演化

这批文件保存“刚开启项目时的一版愿景与设计”。后续可以调整目标、替换选型、合并模块或重做接口。更新相应文档并标记旧方案状态即可，不将本轮草案当作永久规则；只有后来实际发布并明确承诺兼容的内容，才承担届时定义的兼容义务。

技术资料已在相应章节就近引用，包括 IMAP / SMTP RFC、SQLite、Tauri、Gmail / Microsoft OAuth 与 MCP 官方规范。引用用于核对协议事实，具体 MailX 模块、参数和里程碑仍是本项目的设计建议。
