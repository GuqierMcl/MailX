# QQ / Foxmail 调研与接入方案

状态：**预设、官方图标、授权码向导与有界收发诊断已有实现 / 真实兼容验收待完成** · 2026-10-28。调研基线为 `75e43ee`，实现位于本次工作树；外部资料于同日查阅。已完成资料核验、代码实现及受控服务回归，未访问真实邮箱、执行真实账号认证或发送测试邮件；开发检查与待验项见[验证策略](../development/validation.md#11-qq--foxmail-预设与收发连接诊断)。

## 1. 建议

将 QQ 邮箱和 `@foxmail.com` 作为同一套服务商接入：**IMAP + SMTP + 授权码**，复用现有账号、凭证、路由和发送队列。首版提供一个带官方图标的“QQ 邮箱”入口，短描述注明 QQ / Foxmail，内部统一使用 `providerId=qq`，支持搜索 QQ、Foxmail、腾讯邮箱和两个域名。

这里的 Foxmail 指 `@foxmail.com` 邮箱地址。Foxmail 客户端可以配置其他服务商，不能由“用户使用 Foxmail 软件”推导其服务器地址；腾讯企业邮箱、自定义企业域名和 `@vip.qq.com` 不在本轮已核验范围内。

MailX 已有 QQ 头部同步与正文阅读的部分真实证据。本次工作的核心是预设和授权码体验、收发诊断及完整兼容验收；不需要从零实现 QQ 协议适配。预设本身不要求数据库迁移或新的认证类型。

## 4. 推荐的用户流程

继续使用现有三步向导：选择服务商 → 填连接信息 → 设置账号名称与颜色。

连接步骤默认只展示：

1. **邮箱地址**：完整 `@qq.com` 或 `@foxmail.com` 地址，支持 QQ 数字地址和英文地址。
2. **授权码**：明确标注“16 位授权码”，旁边提供“如何获取”；提示需要先开启 IMAP/SMTP。
3. **高级设置**：按需展开独立 IMAP/SMTP 登录用户名、账号路由和端点。默认用户名跟随本次输入地址、收发共享授权码、直连。

两个默认端点可在摘要中查看，避免要求普通用户手填。若地址不属于两个已核验域名，提示选择其他邮箱或通用配置，不把任意企业邮箱发送到 QQ 端点。

创建时应用预设，回退向导时保留用户已填内容；关闭后清空秘密。编辑已有账号不重新覆盖端点、用户名、路由或凭证。原来通过通用配置接入的 QQ 账号保持原记录，不自动迁移、重建或清缓存。

输入端可对误粘贴空格和非 16 位内容给出提示，但不要向通用密码模型添加 QQ 格式约束，也不要擅自改写凭证字符。授权码只经现有写入型输入进入后端 SecretStore，不写入 localStorage、日志、诊断报告或截图。

Foxmail 默认使用输入的完整地址同时作为登录名和发件地址；若特定账号需要不同登录身份，由高级设置明确输入。只有实测确认后才能把这种组合列为已验证，不尝试自动轮换多个用户名。一个邮箱的不同别名可能对应同一收件箱，首版不靠域名或用户名猜测并自动合并账号；多发件身份管理另行设计。

## 5. 连接验证与错误体验

### 最小接入

保存仍是本地配置事务，随后启动现有同步。界面应表达“已保存，正在同步”，不能将保存成功或 IMAP 成功表述为“收发验证通过”。QQ 认证失败时，复用现有错误分类，附上以下排查路径：

- 确认网页端已开启 IMAP/SMTP。
- 确认填入授权码，且未被停用或重置；改过 QQ 主密码时重新生成。
- 确认完整邮箱地址及高级登录用户名，检查服务商是否提示安全验证。
- 提供“修改授权码”和“打开官方帮助”的操作。

没有明确协议证据时，只能确定“认证失败”；不承诺自动区分未开服务、授权码错误、授权码撤销和风控。TLS、代理失败、网络超时保持各自提示，不都归为授权码错误。

### 已实现的连接诊断

`verifyAccountConnection(accountId, expectedRevision, signal?)` 针对**已保存账号**验证连接，返回分别描述 IMAP / SMTP 的报告。桌面适配器为每次操作生成独立 verificationId，AbortSignal 通过专用取消 IPC 终止该次诊断；core 实现在 `core/src/app/verification.rs`，具体输入与结果见[应用 API](../contracts/app-api.md#收发连接诊断与服务商帮助)。

- core 获取当前账号收发计划，释放存储锁后执行网络操作，全部经过原账号路由、TLS 和端点信任检查。
- IMAP 只做认证、能力检查和 NOOP，不读取目录或邮件；SMTP 只做 TLS → EHLO → AUTH → QUIT，验证阶段不运行 MAIL/RCPT/DATA。
- 分别返回 IMAP 和 SMTP 的成功/失败、固定原因码与阶段；不返回原始服务端响应、邮件头、目录中的私人名称或凭证。
- 整次调用共用 45 秒预算，支持取消和同账号并发保护；账号配置变化后，旧结果失效。持久化 `connectionStatus` 的重新设计可以后置，首版诊断结果绑定配置版本，仅用于当前界面。
- SMTP 认证成功只代表能够登录发送服务器；真实发送是否被接受、到达收件方，仍由专门的发信验收证明。

预设和诊断已同步实现；对外标记完整支持前仍须取得真实收发实测证据。

## 6. 两个需要明确的行为边界

### 服务端收取范围与本地缓存

QQ 的“最近 30 天”与 MailX 的固定窗口不同：MailX 在每个目录/UIDVALIDITY 首次同步时，以当日减 30 天确定起点，之后不每日滚动；每轮至多选取最新 1,000 UID，单批 200 封。QQ 可以再限制客户端实际能看到哪些历史邮件。

代码层已确认：`core/src/sync/messages.rs:82` 会把固定本地窗口内、在成功 SEARCH 中不再出现的已缓存 UID 判为消失，`:235` 提交对账；`core/src/storage/messages.rs:344` 将其置为 `remote_state=deleted`。这不是物理删除，但普通查询和正文读取会隐藏这些记录。

**待实测的条件是：QQ 范围缩窄或范围滚动是否确实让这些 UID 从成功 SEARCH 中消失。** 如果成立，旧信会在 MailX 隐藏，不能承诺已经下载就永久可读。范围放宽后，同 UID 可经重新获取恢复，但受本地窗口、1,000 UID 上限和 UIDVALIDITY 变化影响。

建议首版明确采用“同步服务器当前可见范围”的既有语义，在接入说明中告知范围限制；不自动修改用户的 QQ 安全设置，也不声称能自动识别该设置。实施前优先验收“全部 → 最近 30 天 → 全部”和跨日边界，准确记录可见性变化，不能把 SEARCH 缺失一律解释为用户在服务器删除邮件。

如果后续目标是永久本地归档，需要独立设计“远端不可见但本地保留可读”的状态、查询范围及正文/附件访问，并更新持久化和 API；它属于通用缓存语义变更，不应藏在一个 QQ preset 中。

### 已发送副本

发送队列已保存 accepted MIME 快照，但本地副本与服务器邮件的列表合并尚未实现，见 `docs/architecture/sending.md:232`。应实测 QQ SMTP 是否自动保存已发送、是否保留 Message-ID，以及 Foxmail 发件身份如何呈现。

首版不默认增加 IMAP APPEND，避免双副本；副本未出现也不能触发再次 SMTP 发送。若要交付完整的“发送后立即在已发送里看到”体验，可并行推进现有发送设计的本地副本展示与对账，但作为单独工作包。写信附件同样维持当前未实现的边界。

## 8. 验证矩阵与支持门槛

账号至少覆盖：QQ 数字地址、QQ 英文地址、`@foxmail.com` 地址；如果需要“QQ 登录身份 + Foxmail 发件地址”，该组合单独记录，不与 Foxmail 直接登录混为一项。

| 场景 | 需要证明的行为 |
| --- | --- |
| 首次/增量收信 | 收件箱及全部可选目录、中文和自定义目录、分页及头部搜索；按既有覆盖范围显示，不声称全历史已下载 |
| 正文与附件保存 | UTF-8、GB2312、明确 GBK 实样、纯文本、HTML、CID、现有附件下载；重复阅读及离线重开已缓存正文 |
| 标记写回 | 已读/未读、星标/取消星标；与网页交叉确认，不将网页特色标记等同标准 IMAP Flagged |
| 发信 | 新邮件、回复、转发；检查 SMTP accepted 和收件实际到达、From/MAIL FROM、中文内容、Message-ID 及服务器已发送副本数量 |
| 凭证修复 | 错误/撤销授权码，更新授权码后恢复；不无限撞认证，不清空缓存；不要求通过修改真实 QQ 主密码来测试官方已确认的失效规则 |
| 收取范围 | 全部/最近 30 天切换、恢复、跨日边界；区分本地固定窗口与服务端范围；记录旧缓存可读性 |
| 网络 | 直连、真实 SOCKS5 与 HTTP CONNECT 分别列状态；失败代理零直连回退，证书错误零凭证发送；某一路由通过不外推另一种 |
| 连续使用 | 同步同时读正文、标记写回、手机客户端并行、切前后台和手动刷新；观察登录频率、限流和恢复，不编造 QQ 连接上限 |
| 平台 | macOS、Windows、Linux 分别记录窗口、凭证库、重启恢复；不能用跨平台编译通过替代真实账号验收 |

可先将“默认端点 + 直连 + 已验平台”列为验证通过，未测路由和平台单独标记，不为补齐全部组合而阻塞最小范围交付，也不笼统宣称全平台/全路由支持。

自动回归重点放在预设填充、用户名覆盖、前后步骤状态、编辑配置保护、授权码清空，以及新增诊断的取消/超时/版本失效和零发信。收取范围风险用合成 IMAP 场景覆盖隐藏与恢复，再用真实账号确认 QQ 的行为。既有 ID、UTF-7、目录角色、TLS、代理、SMTP unknown 回归继续运行，只有新差异才补相应协议测试。

实施时按改动运行 `bun run check`、必要的 Rust fmt/Clippy/test 与桌面构建；生成 DTO、接口、凭证或同步语义发生变化时同步更新相应契约。真实发信测试依照仓库现有约定，届时仅使用获授权的测试账号和收件白名单；本方案没有发起这些动作。
