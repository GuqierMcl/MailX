# ADR 0005：内置 AI 自建流式客户端与智能体循环

状态：**Proposed** · 2026-11-15。尚无实现；设计见 [AI Runtime](../ai-runtime/README.md)。

## 背景

内置 AI 需要：OpenAI 兼容与 Anthropic 两种协议的流式输出和工具调用；一个智能体循环（模型回复里有工具调用就执行、把结果交回模型，直到给出回答）；运行中途暂停等待用户确认；取消、超时与快照恢复；内容发送同意。现有代码已具备非流式 `complete`、服务商与模型配置、按 AI 专用路由连网（代理失败不回退直连）、把服务商错误映射为固定错误码，以及与 MCP 共用、带 JSON Schema 的工具层。

## 调研的现成库（2026-11 crates.io）

| 库 | 版本 | 能提供什么 | 与 MailX 的出入 |
| --- | --- | --- | --- |
| `rig-core` | 0.46 | 多服务商客户端、流式、工具调用、`Agent` 多轮循环；HTTP 经 `rig-http` 的 `HttpClientExt` 抽象，可换成自己的传输 | 循环不提供“暂停等待界面确认”和运行快照，需要包一层或绕开；工具要改写成它的 `Tool` trait；错误携带服务商原文，需另行映射；0.x 版本迭代快，升级时 API 常变 |
| `genai` | 0.7 | 多服务商统一客户端、流式、工具调用 | 只到协议层，不含循环；直接依赖 `reqwest`，连网要让出 MailX 的路由与代理控制 |
| `async-openai` | 0.43 | OpenAI 接口 | 单一服务商，不含 Anthropic 与循环 |
| `swiftide`、`langchain-rust`、`autoagents` 等 | 0.x | 面向 RAG、任务图或通用智能体的框架 | 范围远超所需，依赖重，下载与维护规模小 |

## 决定

自建，不引入智能体框架：

1. **流式客户端**：在现有 `ai/client` 上增加两种协议的流式请求与工具调用，复用 `net::http` 的路由连接，把响应体改为按块读取，解析 SSE 后合并成统一的事件（文字片段、工具调用、结束原因、用量）。服务商原文不出模块，错误仍为固定错误码。
2. **智能体循环**：在 core 内实现一个小循环（约数百行）：组装消息、流式请求、执行工具、写回结果、检查上限；需要确认的工具让运行暂停，等主窗口回应再继续。工具直接调用现有工具层，不做第二套定义。

## 理由

- 真正难写的部分（暂停确认、同意、取消、快照、路由与错误脱敏、工具授权）都是 MailX 特有的，框架不提供，引入后仍要自己写。
- 框架能省下的只有协议解析与循环本身。两种协议、一个循环的规模不大，自建后完全掌握错误、超时与取消行为，便于测试。
- 不增加 `reqwest` 及其 TLS、代理栈，网络行为与邮件、翻译保持同一条路径。
- 不被 0.x 框架的频繁变更牵着升级。

## 代价与缓解

- 新服务商的协议差异要自己适配：只支持 OpenAI 兼容（Chat Completions）与 Anthropic Messages 两种协议，与已有的服务商配置一致；其他服务商走 OpenAI 兼容接口。
- SSE 与工具调用增量拼接的边界情况要自己测：用录制的真实响应片段做测试样本，包括分片断在 UTF-8 字符或 JSON 中间、多个并行工具调用、空的工具参数、提前结束。
- 实现时可参考上述库处理各服务商差异的做法与测试用例，但不复制代码。

## 重新评估的条件

需要支持更多原生协议（如 Gemini、Responses API 专有功能）、多模态输入或复杂编排（子任务、并行代理）时，重新比较框架方案；届时优先考虑能接入自有 HTTP 传输的库。
