# ADR 0004：内置 Agent 与 MCP 共用工具层

状态：**Accepted，未实现** · 2026-11-02 · 修订 [ADR 0003](0003-ai-and-agent-boundaries.md) 中内置 AI 的能力范围与 MCP 的接入方式；内容披露边界仍沿用 ADR 0003；发信授权在 2026-11-04 按下述补充决定修订。

## 背景

MailX 计划提供三类能使用邮件能力的调用方：

1. 内置 AI，从首批固定工作流逐步演进为能调用工具的内置 Agent；
2. 本机外部 Agent，经 stdio MCP 访问正在运行的桌面核心；
3. 服务端部署后，经网络协议访问的远程 MCP。

三者需要的领域能力大体相同：列账号、检索、读取正文、建草稿。若各自实现，权限检查、结果截断和错误语义会逐步漂移，安全审查也要做三遍。若反过来让内置 Agent 经本地 MCP 回环调用，或让远程 MCP 包装 stdio 进程，又会引入多余的进程、IPC、序列化与认证错配，也无法表达确认卡片、编辑器草稿这类与界面绑定的交互。

## 决定

1. **工具层位于 core，与传输无关。** 每个工具只有一份定义：稳定标识、输入输出 schema、处理函数、可见调用方与按调用方的策略。处理函数接收宿主构造的 `RequestContext`，经与 UI 相同的应用服务执行，不感知调用来自进程内还是网络。
2. **三种入口都是适配层。**
   - 内置 Agent 在核心进程内直接调用工具层，不说 MCP 协议，也不经 IPC。
   - 本地 MCP：核心进程托管 MCP 服务实现，经本机受控 IPC 承载 MCP 消息；stdio bridge 只负责启动握手、token 认证和字节转发，不理解具体工具。
   - 远程 MCP：服务端进程托管同一份 MCP 服务实现，传输换为 Streamable HTTP，认证按 MCP 授权规范另行设计。不以网关包装 stdio 进程的方式提供远程 MCP。
3. **工具集按“相交”建模。** 统一工具池中的工具分别声明对内置 Agent 与 MCP 是否可见。两侧共享领域工具，同时各有专属工具：内置 Agent 专属工具通常与界面绑定，MCP 专属工具只对外部 Agent 有意义。“内置工具集是 MCP 工具集的超集”可以是某阶段的实际结果，不作为约束。
4. **共享工具按调用方取不同策略。** 同一工具对不同调用方可以有不同的账号范围、输出上限、是否需要用户确认等策略；策略属于工具元数据与授权检查，不为不同调用方复制实现。
5. **MCP 默认不暴露。** 新工具必须显式声明对 MCP 可见才会出现在 MCP 工具列表中；即使声明可见，每个 MCP 客户端仍只在其授权范围内看到和调用。
6. **发送按宿主授予的动作与账号范围执行。** 2026-11-04 用户明确修订原“只能请求 UI 确认”的决定：本地 MCP 开启即授予发送能力，Agent 可直接将草稿入队，无需逐封确认；内置 Agent 由宿主明确授予 `mail:send`。发送必须核对草稿版本、幂等键与账号范围，未知结果不自动重发。本项替代 ADR 0003 和本 ADR 原先的逐封确认限制，见[发送与附件工具](../architecture/mail-send-tools.md)。

工具层的具体设计见[工具层与调用入口](../architecture/agent-tools.md)，MCP 侧契约见 [MCP 草案](../contracts/mcp.md)，模型执行见 [AI Runtime](../ai-runtime/README.md)。

## 代价

- 工具层需要先于任一入口设计 `RequestContext`、授权模型与结果整形，首个可用 AI 或 MCP 功能会因此稍晚。
- MCP 服务实现驻留核心进程，`rmcp` 等协议依赖进入核心或与核心同进程的共享模块；需要保证它不引入 Tauri、Axum 或 UI 依赖。
- 桥接程序只转发字节，MCP 协议版本协商在核心完成；桌面应用更新时，已配置的外部客户端随之看到新版本的工具集。

## 重评条件

- MCP 协议或目标客户端要求桥接程序理解协议内容（例如需要在桥接侧缓存或改写消息）；
- 内置 Agent 改为独立进程或采用现成 Agent SDK，进程内调用不再成立；
- 远程 MCP 的认证或多租户需求无法在共享 MCP 服务实现上以适配层满足。

出现上述情况时重新评估分层，并重新说明凭证、内容披露与发信授权边界。
