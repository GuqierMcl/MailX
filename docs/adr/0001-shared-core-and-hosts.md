# ADR 0001：共享 Rust 核心与分阶段宿主

状态：**Accepted / 骨架已落地** · 2026-10-14。当前采用单个 core 与薄宿主；服务端和业务功能仍待实现，后续可根据实际需求调整。

## 背景

启动愿景同时包含 Tauri 桌面客户端和 Docker Web。若一开始分别编写两套收发、搜索与权限逻辑，后续很难保证同样的离线、幂等和 AI 行为；同时交付两种形态又会让单人早期开发范围过大。

## 当前决定

将原先设想的 core 与 infra 合并为根目录 `core/`，业务服务、领域模型、SQLite、邮件协议、路由和模型 HTTP 实现均在包内按模块组织。这样新增功能时不必反复判断实现该落在哪个包，也不必为早期每个适配器建立端口层。

`desktop/` 是根目录 Tauri 宿主，只装配生命周期、通信与平台集成；第一阶段完成桌面 MVP，第二阶段再初始化 `server/`，复用同一 core。当前 Cargo workspace 包含 `core` 和 `desktop`，前端工作区位于 `frontend/`，使用 React + TypeScript + Vite + shadcn 的初始化骨架。

宿主无关的约束是 core 不依赖 Tauri、Axum、WebView 或 UI API，并不禁止其直接依赖存储、网络或协议库。确需替换的平台能力和测试边界再定义接口，不预建完整抽象体系。

每个数据目录只有一个核心写入实例，MCP 是该实例的受限入口。桌面与 Web 独立部署时分别保存数据，不直接共享 SQLite，也不把 Web 偷换成多租户服务。

## 代价与重评条件

单个核心 crate 的依赖可能随功能增加，需保持内部模块职责清晰、公共 API 收敛；桌面和服务器的平台差异仍需适配。当前只用版本信息打通宿主依赖，RequestContext、实例锁和真正的应用服务后续实现。暂不采用微服务或消息中间件。

当出现独立发布需求、显著的可选重依赖或可单独复用的模块时，再按证据拆包；不以预想的规模提前恢复 infra 层。

若远程桌面控制、团队协作、长驻 headless 同步或平台分发带来真实需求，可重新设计进程所有权与部署方式。更改时同步更新[总览](../architecture/overview.md)和[宿主边界](../architecture/desktop-web.md)，无需拘泥本记录。
