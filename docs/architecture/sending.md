## 2. 写信窗口：独立窗口

### 调研

| 客户端 | 新邮件 | 回复 / 转发 | 能否弹出为新窗口 |
| --- | --- | --- | --- |
| Apple Mail | 独立窗口 | 独立窗口 | 本身即窗口 |
| Thunderbird | 独立窗口 | 独立窗口 | 本身即窗口 |
| 经典版 Outlook | 独立窗口 | 默认在阅读窗格内联 | 可逐封弹出；有"回复与转发在新窗口打开"设置 |
| 新 Outlook / Outlook 网页版 | 主窗口内 | 阅读区内联 | 可逐封弹出；未查到"总是新窗口"设置 |
| Spark Desktop | 主窗口内 | 主窗口内 | 可弹出；有"总是在新窗口打开写信"设置 |
| Gmail 网页版 | 右下角浮动面板（非模态） | 内联 | 可弹出 |

规律：传统桌面客户端以独立窗口为主；Web 出身的现代客户端默认在主窗口内编辑，但都是**非模态**的（内联区或浮动面板），并都提供"弹出到新窗口"。没有主流客户端用遮挡主窗口的模态弹窗写信。

来源（2026-10-23 查阅）：[Spark Desktop 多窗口](https://sparkmailapp.com/help/sending-emails/multi-window-support-in-spark-desktop)、[Outlook 回复与转发](https://support.microsoft.com/en-us/outlook/reply-to-or-forward-an-email-message)、[Outlook 网页版回复设置](https://support.microsoft.com/en-us/office/reply-settings-in-outlook-on-the-web-3adc2c37-ee1e-46f5-98bb-1f0fb02003b3)、Thunderbird 帮助中心的写信窗口说明。Apple Mail 与 Gmail 为常见行为，未逐项查证当前版本。

### 取舍

| | 独立窗口 | 主窗口内（非模态） | 主窗口模态弹窗 |
| --- | --- | --- | --- |
| 写信时参考其他邮件 | 可以，两窗并排 | 受阅读区占用影响 | 不行，被遮挡 |
| 同时写多封 | 自然支持 | 需要标签或切换 | 不支持 |
| 权限隔离 | 可按窗口单独授权（见下） | 与主窗口共享全部权限 | 同左 |
| 实现成本 | 多窗口外壳、标题栏、生命周期 | 需要在岛内设计第二种布局 | 低 |
| 资源 | 每个窗口一个 WebView，首次打开要加载前端 | 无额外 | 无额外 |

模态弹窗直接排除：挡住阅读、易被 `Esc` 误关，也与"画布 + 岛"的设计语言冲突。

### 决定

- **桌面端 v0.1 一律用独立窗口**：新建、回复、全部回复、转发都在新窗口里写。理由是参考原邮件、多封并行和按窗口最小授权；这也符合用户的习惯判断。
- **写信组件与宿主无关**：同一个 `Composer` 组件既可以挂在独立窗口里，也可以挂在主窗口的岛内。以后 Web 宿主（无法开系统窗口）和"在阅读区内快速回复"选项复用它，那时再加设置"写信打开方式：新窗口 / 主窗口内"，不在 v0.1 做。
- 打开速度和内存占用**实现后实测**，不预设数字；首次打开明显偏慢时，再评估预创建一个隐藏的写信窗口。

### 窗口行为

- 窗口标签为 `composer-{draftId}`，一份草稿最多一个窗口；再次打开同一草稿时聚焦已有窗口。
- 入口：导航顶部的"写邮件"、阅读区工具栏的回复 / 全部回复 / 转发、`Cmd/Ctrl+N`、草稿列表的“继续编辑”、命令面板的“写邮件”（规则见[界面设计](ui-design.md#命令面板)）。
- 外观沿用画布与岛：自有标题栏（窗口标题为邮件主题，空时为"新邮件"），macOS 红绿灯照常；内容是一个岛，上方为发件账号、收件人、抄送 / 密送（默认收起）、主题，下面是富文本编辑区与其上方的格式工具栏（见第 14 节），底部为发送按钮、丢弃和保存状态（见下）。
- 默认尺寸约 760×680，最小 520×420，相对主窗口错开放置；v0.1 不记忆尺寸。
- 关闭（系统关闭按钮、自绘关闭按钮、Cmd+W）：
  - 空白草稿（无收件人 / 抄送 / 密送，主题与正文只有空白）：删除并关闭，不询问。
  - 内容与打开窗口时相同且草稿不是为本窗口新建的（从“草稿”列表重新打开）：直接关闭，不询问。
  - 其他情况弹出“要保存这封草稿吗？”（“保存后可以在‘草稿’中继续编辑。”），按钮“不保存”（最左）、“取消”、“保存草稿”（默认焦点）；`Esc` 等于取消。保存草稿：写出后关闭，保存失败时询问“仍要关闭（丢失未保存的修改）/ 取消”。不保存：新建的草稿（写邮件 / 回复 / 转发，宿主 URL 带 `fresh=1`）删除；已有草稿用打开时的内容覆盖回去（取最新 revision），**绝不删除已有草稿**。取消：窗口保持打开。
  - “丢弃”在内容非空时需要确认，行为不变。
  - 底栏左侧是保存状态，右侧依次为“丢弃”和“发送”（最右）。
  - 保存状态为 `idle`（不显示）/ `saving` / `saved` / `failed`：打开任何草稿（新建或重新打开）都从 `idle` 开始，用户改动之前什么都不显示；保存超过约 400 ms 才显示“正在保存…”，更快的保存直接显示“已保存”；内容重新变为空白（无收件人、主题和正文都为空）时回到不显示，因为空白草稿不保留、关闭时删除；失败显示“保存失败”和文字按钮“重试”（再次触发保存，关闭时对失败保存的处理不变）；草稿已进入发送队列只读时显示“已在发送队列中”，不显示保存状态。状态元素保持 `role="status"` / `aria-live="polite"`，并预留固定宽高，出现与消失不会推动右侧按钮；淡入在减少动态效果时关闭。自动保存节奏（约 1 s 防抖）不受影响。
- 关闭主窗口仍退出应用：宿主先向所有写信窗口发出关闭请求，等它们各自写出草稿，再退出。

**已实现（步骤 4a，宿主与客户端层，尚无界面）：**

- `composer_open { draftId }`（仅 main）：草稿必须存在；已有 `composer-{draftId}` 窗口则取消最小化并聚焦，否则新建。窗口加载 `index.html?composer={draftId}`，CSP 不变、不需要 `frame-src`；macOS 为 Overlay 标题栏、隐藏标题与红绿灯位置，Windows / Linux 为 `decorations(false)`（与 main 共用 `window_chrome::style_builder`）；尺寸 760×680、最小 520×420；位置在主窗口的基础上按已开启的写信窗口数每级错开 32 逻辑像素（8 级后循环），并夹在主窗口所在显示器内；窗口状态插件只记 main（过滤其余标签）。`on_navigation` 只放行应用页面来源并沿用正文链接拦截。
- 关闭：写信窗口的系统关闭请求（红绿灯、Alt+F4、自绘关闭按钮的 `close`）一律被拦截，宿主向该窗口发 `mailx://composer-close-requested`，前端写出草稿后调用 `composer_close`（销毁窗口）；3 秒内没有回应则宿主直接销毁。主窗口关闭请求或系统退出（Cmd+Q）在有写信窗口时被拦截，向每个写信窗口发 `mailx://app-closing`，等它们都关闭（最多 3 秒，之后强制销毁），然后退出；没有写信窗口时与以前一样立即退出。
- 与设计的差异：尺寸与位置用逻辑像素与主窗口位置换算，多显示器与缩放下的真实效果待实机验证；`composer_close` 的 `force` 参数保留在契约里但宿主不区分。关闭时“保存失败是否仍关闭”的询问和空草稿自动删除属于前端，已在 4b 实现（见下）。
- 写信窗口不读邮件正文：回复引用和转发内容由核心在创建草稿时生成并写入草稿，所以写信窗口不需要正文相关命令，也没有正文 iframe。

**已实现（步骤 4b，前端界面，自动测试通过，三平台实机未验证）：**

- 写信窗口页面 `ComposerApp` 复用主窗口同一个 `TitleBar`；`Composer` 与宿主无关。保存：停止输入约 1 秒后写出，同一时刻只有一个保存在途，期间的新修改在其后以新 revision 再发；每次都带上次保存的 `expectedRevision`；`conflict` 时重新加载核心里的草稿并提示（本地未保存的修改不合并、不覆盖）；`draftLocked`（含 `mailx://drafts` 的 `locked` 事件）时转只读；`unlocked` 时重新加载，`deleted` 时显示“草稿已不存在”。无效地址不写入草稿（核心会整份拒绝），保留为错误标签并阻止发送。
- 关闭：收到 `composer-close-requested` 后按“窗口行为”中的规则处理；收到 `app-closing`（整个应用退出）从不询问，写出后（最多约 2 秒）空白草稿删除，再调用 `composer_close`。写出失败时，系统关闭请求弹出“仍要关闭（丢失未保存的修改）/ 取消”。第二次点击发送成功后立即关闭窗口。“丢弃”在内容非空时要确认。
- 转发附件提示：草稿（`Draft`）里没有原邮件附件数，写信窗口也不读邮件，所以 **“原邮件的 N 个附件不会随转发发出”的提示尚未显示**。不再单独补这条提示，改由第 16.8 节的转发预填附件解决。
- 发信凭证不可信或缺失时，发送按钮第一次点击就拒绝并说明，不进入待确认。
- 与设计的差异：窗口原生标题只设置了 `document.title`，宿主没有 `set_title` 命令；点收件人标签可把它放回输入框修改。

### 发件账号

默认用触发写信时的上下文账号：回复 / 转发用原邮件所属账号；在某个账号的文件夹里新建时用该账号；在统一收件箱新建时用设置中的默认发件账号（`compose.defaultAccountId`），未设置或该账号已删除时用排序第一的账号。可以在窗口里改选。

每个账号有自己的**发件人名称**（`senderName`），即收件人看到的名字，如"张三"；它和账号名称（给自己看的标签，如"工作邮箱"）不同，单独保存。发件人名称属于账号资料：在账号管理弹窗的资料里直接编辑并自动保存，添加账号第 3 步（命名）也填写。留空时 `From` 只有地址。改名称不影响已入队的快照。

## 3. 发送按钮：两步确认

不弹确认框。发送按钮本身分两步：

1. **待发送**：按钮显示"发送"。第一次点击先校验（至少一个收件人、所有地址可解析、账号可用）。校验失败只标出字段，按钮不变。
2. **待确认**：校验通过后立刻写出未保存内容，按钮经过渡动画（宽度与颜色，约 200ms）变为"确认发送"；主题为空时显示"无主题，确认发送"。屏幕阅读器通过 `aria-live` 听到"再次按下以确认发送"。
3. **发送**：第二次点击后立即入队，关闭写信窗口。

约束：

- **防双击**：进入待确认后约 400ms 内的点击无效，双击不会直接越过确认。
- **自动退回**：约 4 秒内没有第二次点击、内容有任何修改、按 `Esc` 或窗口失焦，都退回"发送"。
- `Cmd/Ctrl+Enter` 同样需要按两次。
- 系统要求减少动态效果时不播放动画，防双击间隔保留。
- 入队请求携带进入待确认时已保存的 `expectedRevision` 和一个新的 `clientMutationId`；版本冲突时退回并加载最新草稿。

两步按钮只是防误触的交互，**不是安全边界**。后端独立核对调用方必须是写信窗口（交互 UI 主体）、草稿版本与快照，MCP 和模型主体无论如何调用都不能入队。

## 4. SMTP 会话

### 实现：手写会话，lettre 只做 MIME

第 2 步实现在 `core/src/smtp/`（`mod.rs` 会话、`reply.rs` 回复解析与脱敏、`message.rs` MIME、`plan.rs` 失败映射；登录计划在 `accounts/sync_plan.rs` 的 `AccountService::smtp_plan`，紧挨 IMAP 的 `sync_plan`）。

**没有使用 lettre 的 `AsyncSmtpConnection`，改为手写最小客户端**（EHLO / STARTTLS / AUTH PLAIN、LOGIN / MAIL / RCPT / DATA / RSET / QUIT，含多行回复解析和点填充）。原因：

- lettre 的连接把流放进内部 `BufReader<AsyncNetworkStream>`，`starttls` 只接受它自己的 `TlsParameters`，TLS 由 lettre 的 rustls / native-tls 特性完成，等于绕开 `net::upgrade_tls`，IMAP 与 SMTP 就有两套证书验证；启用 lettre 的 TLS 特性还会引入第二套 TLS 依赖。
- 探针阶段的换流方案要求在 `220` 之后从内部缓冲读取器里取回底层流，并确认缓冲区为空；lettre 不暴露这一点，无法做 STARTTLS 注入防御。
- `connect_with_transport` 的 EHLO 与 `send` 把 MAIL / RCPT / DATA 合并为一次调用，拿不到 354 与"正文开始"标记之间的钩子，也不能逐个收集 RCPT 拒绝。

`lettre` 现在是 `mailx-core` 的普通依赖，仅启用 `builder`（`default-features = false`）：用于 MIME 构造、RFC 2047 编码和 `Address` 解析；不启用 `smtp-transport`、`tokio1` 或任何 TLS 特性，`cargo tree -e normal` 中没有 `native-tls`、`openssl`、`aws-lc`。`rcgen` 仍只是开发依赖。

### 会话与探针结论（保留的探针证据）

原探针（直连 / SOCKS5 / HTTP CONNECT、不回退直连、STARTTLS 与隐式 TLS 经 SOCKS5）已由正式测试取代并删除 `smtp_probe.rs`；代理与 TLS 假件移入 `core/src/net/test_support.rs`，假 SMTP 服务器在 `core/src/smtp/fake_server.rs`（仅测试编译，只监听 127.0.0.1）。

### 会话步骤

1. 按账号路由 `net::connect`。465 端口立即走 `net::upgrade_tls`。
2. 587 端口：读问候语、`EHLO`，服务器必须声明 `STARTTLS`，否则失败（`tlsUnavailable`），绝不明文继续。发 `STARTTLS` 后，从包装器的共享槽里取出底层流，用 `net::upgrade_tls` 升级后放回，再发一次 `EHLO`。这样 IMAP 和 SMTP 只有一套证书验证；换流的实现：会话持有 `BufReader<BoxedStream>`；收到 `220` 后检查读缓冲为空（非空说明有人在明文里抢跑，按 `protocol` 永久失败，不丢弃也不重放），再 `into_inner()` 取出底层流交给 `net::upgrade_tls`，用结果建立新的读取器并重新 `EHLO`；握手前学到的能力一律丢弃。测试用 `TlsSource::Test`（仅 `#[cfg(test)]`，对应 `net::upgrade_tls_with`）注入测试 CA；生产只有 `TlsSource::Platform`，没有任何跳过验证的开关。
3. 认证前核对凭证的受信端点（协议、主机、端口、TLS、用户名）：在建立登录计划时完成（`smtp_plan`，`TrustEndpoint::mail("smtp", ...)`），不符时返回永久失败，**不打开任何连接**。会话按服务器声明选用 `AUTH PLAIN`（优先）或 `LOGIN`；没有声明可用机制为 `authUnavailable`。
4. 服务器声明了 `SIZE` 且快照超出时，在 `MAIL FROM` 之前失败。
5. `MAIL FROM`，然后逐个发 `RCPT TO` 并记录每个地址的结果。只要有一个被拒，就 `RSET` 并整体失败，返回全部被拒地址，**不只发给部分收件人**。
6. `DATA` 收到 354 后，先调用并等待调用方传入的 `DataStarted` 钩子（第 3 步在这里提交 `data_started_at`），成功后才写出正文和结束符；钩子失败则不发任何正文字节并断开，按"正文开始前"的临时失败返回（`dataMarkFailed`）。正文做 CRLF 规范化（裸 LF / CR 都转为 CRLF）和点填充，由会话自己完成并有测试。
7. 收到最终回复：250 记为 `accepted` 并保存回复码；明确的 4xx / 5xx 记为 `failed`；超时、断线或无法解析的回复记为 `unknown`。
8. `QUIT` 尽力而为，失败不影响已记录的结果。

超时按 RFC 5321 的建议上限设置（`Timeouts`，可注入）：问候与各命令 5 分钟、`DATA` 到 354 为 2 分钟、正文结束符之后的回复 10 分钟，以减少 `unknown`；连接沿用 `CONNECT_TIMEOUT`。日志只记录阶段、回复码和脱敏错误，从不输出 AUTH 或 DATA 内容。会话本身不写日志；服务器回复文本只保留回复码和脱敏文本（控制字符含 CR / LF 变空格、折叠空白、回显的密码替换为 `[redacted]`、最多 200 字符）。

### 会话结果（`SmtpOutcome`）

| 结果 | 含义 | 第 5 节处理 |
| --- | --- | --- |
| `Transient(原因)` | 正文开始前：连接失败、代理失败、超时、网络中断、任意 4xx、握手前的协议错误、`dataMarkFailed`、凭证库暂不可用 | 回到 `queued`，退避重试 |
| `Permanent(原因)` | 正文开始前：5xx、`authRejected`、`tlsVerification`、`tlsUnavailable`、`authUnavailable`、`messageTooLarge`、`protocol`（含 STARTTLS 后的明文注入）、`credentialUntrusted`、`credentialMissing`、`invalidMessage` | `failed` |
| `RecipientsRejected(列表)` | RCPT 有拒绝：已 `RSET`，未进入 DATA，列表含每个被拒地址与回复码 | `failed`，附全部被拒地址 |
| `Accepted(码, 文本)` | 正文后 2xx | `accepted` |
| `RejectedAfterData(码, 文本)` | 正文后 4xx / 5xx | `failed`，不自动重试 |
| `Unknown(超时 / 断线 / 回复无法解析)` | 正文后没有可用的最终回复，包括写正文时出错 | `unknown`，永不自动重发 |

与设计的差异与限制：

- **代理认证失败与其他代理错误不区分**：`net` 目前把 SOCKS5 / HTTP CONNECT 的失败都报为 `NetError::Proxy(字符串)`，没有结构化原因，所以会话一律按临时失败（`proxy`）处理；第 3 步若要对代理认证失败给出永久失败，需先让 `net` 报告结构化原因。
- `AUTH` 回复 4xx 视为临时服务器错误，5xx 为 `authRejected`。
- `EHLO` 使用地址字面量 `[127.0.0.1]` 作为客户端标识，避免泄露本机主机名；未支持 `SMTPUTF8`，非 ASCII 的信封地址在第 1 步校验时已被拒绝，MIME 必须是纯 ASCII（由 lettre 对非 ASCII 内容做 QP / base64），否则 `invalidMessage`。
- 没有实现 PIPELINING；命令逐条等待回复，以便逐个记录 RCPT 结果。
- 服务器声明 `SIZE` 时，MAIL FROM 附带 `SIZE=` 并在发送前比较；比较的是 MIME 字节数，未计点填充后的开销。

## 5. 状态与重试

状态沿用[发信状态机](mail-sync.md#5-本地草稿与可靠发送)：`queued → sending → accepted / failed / unknown`，另有 `canceled`。细化如下：

| 发生在 | 情况 | 结果 |
| --- | --- | --- |
| 正文开始之前 | 网络错误、超时、代理暂不可达、任意 4xx | 回到 `queued`，按退避自动重试 |
| 正文开始之前 | 5xx、认证失败、证书验证失败、代理认证失败、缺 STARTTLS、凭证需重新确认、超出 SIZE | `failed`，不自动重试 |
| 正文开始之前 | RCPT 有被拒地址 | `failed`，附全部被拒地址 |
| 正文开始之后 | 明确的 4xx / 5xx 最终回复 | `failed`，不自动重试，可由用户重新发送 |
| 正文开始之后 | 没有最终回复 | `unknown`，永不自动重发 |

- 正文开始之前，服务器还没收到任何内容，所以自动重试不会造成重复发送。退避为 30 秒、1、2、5、10 分钟，之后每 30 分钟一次；超过 24 小时转为 `failed`（`retryExhausted`）。应用启动、手动"立即重试"时立即尝试。
- 每次尝试用**当时**的账号路由与凭证；快照只固定内容，不固定路由。
- 账号被删除，或地址 / 服务器来源已被替换时，未发出的队列项转为 `failed`（`accountChanged`），需要用户确认后重新发送，因为快照里的发件人可能已不对应当前账号。
- 同一账号的队列串行发送，每次发送开一个独立连接，和同步、标记写回互不共用。

### 重启恢复

- `sending` 且没有正文开始标记：证明服务器未收到内容，回到 `queued`。
- `sending` 且有正文开始标记：转为 `unknown`。
- `queued`（包括撤销等待期内被关闭的）：启动后继续发送，并在发件箱中可见。

### `unknown` 的处理

写信内容保持锁定，界面说明"服务器可能已收到这封邮件"。提供三种选择：

- 在已发送中按 Message-ID 查到时显示"已在已发送中找到"，并允许标记为已发出。
- "标记为已发出"。
- "确认未发出，重新发送"：创建一次新的尝试，沿用同一 Message-ID，方便收件方去重。

### 第 3 步的实现（`core/src/send/`、`core/src/storage/outbox.rs`、`core/src/accounts/outbox.rs`）

- **每账号一个串行 worker**（`send::worker::OutboxManager`）：循环为“取下一项并解析登录计划（持锁、短事务）→ 不持锁发送 → 短事务记录结果”。启动时、新入队、撤销、立即重试、账号连接更新时唤醒；没有到期项时睡到最早的 `max(not_before, next_attempt_at)`，最长睡 60 秒（系统时钟被调整时不会长期滞留）。账号被删除时 worker 退出。
- **竞争点是一条带条件的 `UPDATE`**：worker 的 `queued → sending` 与 `cancel` 的 `queued → canceled` 都带 `WHERE state = 'queued'`，同一行只能有一个成功；输家得到 `alreadySending`（撤销时已在发送）或 `conflict`（已处于其他状态）。取走时 `attempts` 加一。
- **`DataStarted` 钩子**在 `spawn_blocking` 里写 `data_started_at`，提交后才返回 `Ok`；写失败或该行已不是 `sending` 时返回 `Err`，会话按 `dataMarkFailed` 在正文前停止。
- **结果映射**（`send::schedule`）：`Transient` → `queued`，`next_attempt_at = now + 30s / 1m / 2m / 5m / 10m，之后每 30m`（以第 n 次尝试失败计）；`now - first_queued_at > 24h` 时转 `failed`，原因码 `retryExhausted`（保留最后一次的服务器回复文本）。`Permanent`、`RecipientsRejected`（全部被拒地址写入 `last_error.rejected`）、`RejectedAfterData` → `failed`；`Accepted` → `accepted`；`Unknown` → `unknown`（原因码 `unknown`，文本为 `timeout` / `connectionLost` / `malformedReply`）。凭证未受信或缺失、认证被拒都是 `Permanent`，不会空转重试。
- **账号变更**：每次取项之前，把信封发件人与当前账号地址（大小写不敏感）不同的 `queued` 项转为 `failed`（`accountChanged`）；取项后若登录计划里的地址又变了，同样失败。只改服务器、用户名、路由或凭证的更新不使项失败，下一次尝试直接用新的计划。账号被删除时队列随外键级联删除（草稿同理）。
- **与第 2 节原文的差异**：`DraftLocked` 用单独的错误码，而不是复用 `conflict`；`drafts` 删除也被锁拒绝。重启恢复在 `MailxCore::open` 里于任何 worker 启动前完成，并为每个变化发出 `Outbox` 事件。
- **`unknown` 的处理**：`resolve_unknown(MarkSent)` 把该行变为 `accepted`（`accepted_at` 为标记时间，无服务器回复，草稿删除）；`Resend` 在同一事务里插入一行新 `queued`（相同 Message-ID、MIME、信封，`attempts` 0，`first_queued_at` 为现在，立即可发），并把旧行标记 `resolution = 'resent'`、`superseded_by` 指向新行。已标记的 `unknown` 不再算“存活”，不锁草稿、不出现在默认的发件箱列表。同一 `clientMutationId` 重放返回同一结果，换一种处理方式返回 `conflict`。`failed` 项的“重新发送”就是对可编辑的草稿再次 `queue_send`，生成新的 Message-ID。

## 6. 撤销发送

- 设置项 `compose.undoSendSeconds`，可选 0 / 5 / 10 / 20 / 30 秒，**默认 0（立即发送）**，与默认发件账号一起放在设置弹窗新增的"发信"页。
- 入队时记录 `notBefore = 入队时间 + N 秒`，等待期间仍是 `queued`。
- 写信窗口在第二次点击后总是立即关闭。主窗口显示提示："正在发送"；N > 0 时显示"将在 N 秒后发送 · 撤销"。**已实现（4b）**：toast 为“将在 N 秒后发送”加“撤销”按钮（N 为入队时 `notBefore` 与入队时间之差向上取整；N = 0 不显示这条），随后“正在发送…”“已发送”；失败显示“发送失败：<当前语言的受控原因>”、`unknown` 显示“可能已发送，需要确认”，二者带“查看”并在发件箱标出；撤销成功后重新打开写信窗口，`alreadySending` 提示“已开始发送，无法撤销”。上述为中文示例，新提示和系统通知按生成时的有效语言显示；已出现的 toast 沿用原语言，切换不重发提示或重置撤销倒计时。发送成功显示"已发送"，失败或 `unknown` 时提示并在发件箱中标出；主窗口不在前台时，经现有通知通道发系统通知。
- 撤销调用 `outbox.cancel`：仍是 `queued` 时转为 `canceled`，草稿回到可编辑状态并重新打开写信窗口。已开始发送时返回 `alreadySending`，提示"已开始发送，无法撤销"。

## 7. 草稿

- 草稿只存在本地，不同步到服务器草稿箱。
- 编辑时防抖保存（停止输入约 1 秒），每次保存 `revision` 加一；`expectedRevision` 不匹配报 `REVISION_CONFLICT`，加载最新版本由用户处理，不静默覆盖。
- 草稿字段：账号、类型（新建 / 回复 / 全部回复 / 转发）、来源邮件、收件人 / 抄送 / 密送、主题、正文（核心净化的 `body_html` 加由它生成的只读 `body_text`，见第 14 节）、`In-Reply-To`、`References`、时间戳、revision。
- 回复与转发的草稿由核心生成：
  - **收件人**：回复优先 `Reply-To`，否则 `From`；全部回复再加原 `To` 和 `Cc`，去掉自己的地址并去重。
  - **主题**：加 `Re:` / `Fwd:`，已有 `Re:`、`RE:`、`回复：` 等前缀时不重复添加。
  - **引用**：回复在空段落、日期和发件人之后接引用块；转发在空段落和头部块之后接原文。优先使用已缓存 HTML，经发信白名单降级；没有 HTML 时按行转义为段落。规则见第 14 节“回复与转发”。
  - **会话串联**：`In-Reply-To` 取原 `Message-ID`，`References` 取原 `References` 再接上原 `Message-ID`。头部同步不读 `References`，所以从缓存的原始 MIME 中取；尚未下载时，核心不在创建草稿的调用里下载，而是返回 `bodyNotCached`，由调用方先下载正文再重试（实现与本节原文的差异，原因是创建草稿保持纯本地、无网络）。
- 空白草稿不出现在草稿列表（`list_drafts` 过滤），核心启动时删除没有活动发送项的空白草稿（崩溃遗留）。
- 核心对每次草稿变更发出 `DraftChanged`：`created`、`updated`、`deleted`，以及队列的 `locked` / `unlocked`；主窗口据此刷新草稿列表，并在所选草稿被删除时清除选择。
- 已被 `accepted` 的草稿从草稿列表移除；`failed` 后回到可编辑；`unknown` 期间锁定。
- 导航新增本地"草稿"，以及仅在有未完成队列项（`queued`、`sending`、`failed`、`unknown`）时出现的"发件箱"。草稿在岛内列出，阅读区显示预览和"继续编辑"；发件箱的项目在阅读区显示状态和可用操作。**已实现（4b）**：两个视图的行与阅读区见[界面设计](ui-design.md#主窗口的写信入口草稿与发件箱)；发件箱操作为 `queued` → 撤销（成功后重新打开写信窗口）/ 立即重试（仅在已安排下次重试时）、`failed` → 编辑并重新发送（打开草稿）、`unknown` → 标记为已发出 / 确认未发出，重新发送（确认对话框）；失败项若同一草稿已有更新的非失败项（已重新发送），不再列出。`mailx://outbox` / `mailx://drafts` 事件使对应查询失效；系统通知点击携带的 `outboxId` 会选中发件箱项。

## 8. 邮件构造

- 使用 `lettre` 的 `builder` 生成 MIME（`core/src/smtp/message.rs`，纯函数 `build`）：处理中文主题和地址的编码，拒绝头部注入；构造器自己也拒绝任何头部值里的控制字符（含 CR / LF），不依赖第 1 步的校验已通过。至少需要一个收件人（`draft.recipients`）。
- 头部：`Date`（本地时区；lettre 只能输出 UTC，所以在构造后用 `Date` 头的预编码值替换为本地偏移，格式为 RFC 2822）、`Message-ID`、`From`、`To`、`Cc`、`Subject`、`In-Reply-To`、`References`、`MIME-Version`。正文为 `multipart/alternative`（先 UTF-8 纯文本、后 UTF-8 HTML），传输编码由库按内容选择，见第 14 节。
- `Message-ID` 由我们生成，形如 `<uuid@发件地址的域名>`，入队时保存，供 Sent 对账、串联和 `unknown` 处理使用。
- `Message-ID` 的域名取自发件地址，保留原大小写；`In-Reply-To` / `References` 必须是空格分隔的 `<local@domain>` 令牌，否则拒绝。
- 不添加 `User-Agent` / `X-Mailer`，避免暴露客户端与版本。
- 信封：`MAIL FROM` 为账号地址，`RCPT` 为 To + Cc + Bcc 去重。**Bcc 只进信封，不写入发出的头部。**
- 地址规则：第 1 步的本地校验器（`valid_address`）保留为准，因为它比 lettre 的解析更严格（lettre 接受带引号的本地部分和国际化域名）；构造器另外要求 lettre 也接受该地址，两者都通过才生成。因此没有用 lettre 的 `Address` 替换本地校验器。
- 入队时固定快照：MIME 字节、信封和 Message-ID 与队列项一起持久化，之后每次尝试都发送同一份字节，不重新生成。有附件时正文外层改为 `multipart/mixed`，快照改存 blob 文件，见第 16.5、16.6 节。

## 9. 已发送副本

v0.1 的原则：**服务器没有副本时，MailX 本地一定有；服务器对上后释放本地快照**，不向服务器追加。

- 发送被接受（`accepted`）后，入队时固定的 MIME 快照、信封、Message-ID 和接受时间留在本地，作为这封信的本地已发送副本。它不依赖服务商是否保存已发送，也不需要额外网络操作。快照保留到与服务器副本对上为止，之后释放（见下一条与第 16.7 节）；信封、Message-ID 等元数据一直保留。
- 本地副本显示在该账号的"已发送"文件夹里，与服务器同步来的邮件按时间合并排序；账号没有已发送文件夹时，导航中显示一个本地"已发送"。本地副本带"仅本机"标识，打开时从快照解析并走现有的正文净化与隔离阅读流程。
- 头部同步在已发送文件夹里取到 `Message-ID` 相同的邮件时，本地副本记为"服务器已有"，列表只显示服务器那封，不重复，并释放本地 MIME 快照。对上只按我们生成的 Message-ID，不按主题或时间猜测。服务商不保存已发送时永远对不上，快照就一直保留。
- 本地副本可以由用户删除，只删本机，不影响服务器。删除账号时一并删除。
- 撤销、失败和 `unknown` 的队列项不是已发送副本，留在发件箱里。

以后再做（不在 v0.1）：服务商不自动保存时，用 IMAP `APPEND` 追加到服务器的已发送，并提供账号级开关；`APPEND` 结果不确定时先按 Message-ID 查找再决定是否追加，永远不会触发再次发送。各服务商是否自动保存，在第 6 步逐家记录。

## 10. 存储

新增迁移，字段为方向性设计，实现时按[数据库迁移](database-migrations.md)落地：

| 表 | 内容 |
| --- | --- |
| `drafts` | 第 7 节的字段、`client_mutation_id` |
| `accounts` | 新增 `sender_name`（可空） |
| `outbox` | 每次尝试一行：草稿、账号、`client_mutation_id`、Message-ID、MIME 快照、信封、状态、`not_before`、`data_started_at`、回复码与脱敏错误、重试次数、下次重试时间 |
| `outbox`（续） | `accepted` 行即本地已发送副本：增加 `accepted_at`、`server_copy_message_id`（对上的服务器邮件，可空）、`deleted_locally_at` |

步骤 1 已落地的部分（迁移 v7，`core/src/storage/migrations/0007_drafts.sql`）：

- `drafts` 的收件人为 `{ name, address }` 的 JSON 数组；`source_email_id` 指向 `messages(id)` 并 `ON DELETE SET NULL`，原邮件消失时草稿保留（引用文字与串联头在创建时已复制进草稿），账号删除则级联删除草稿；`(account_id, client_mutation_id)` 唯一。
- 额外的 `create_canonical` 列保存创建请求的规范形式，使同一 `clientMutationId` 的重试返回同一草稿（即使之后已被编辑），内容不同则报 `idempotencyConflict`。
- 默认发件账号由宿主从设置读出后传给 `create_draft(request, default_account_id)`，核心的设置存储与数据库互不依赖。
- 地址校验使用保守的本地校验器（ASCII dot-atom 本地部分 + ASCII 主机名，拒绝引号本地部分与国际化地址）；步骤 2 决定保留它并额外要求 lettre 接受（见第 8 节）。
- `senderName` 上限 128 个字符，拒绝所有控制字符。

步骤 3 落地的部分（迁移 v8，`core/src/storage/migrations/0008_outbox.sql`）：

- `outbox` 为 STRICT 表，带 CHECK：`state` 六种取值、`accepted` 必有 `accepted_at`、`queued` / `canceled` 不能有 `data_started_at`、`resolution` 只能是 `unknown` 行的 `resent` 或 `accepted` 行的 `markedSent`；`(account_id, client_mutation_id)` 唯一。`draft_id` 为 `ON DELETE SET NULL`，账号删除时级联删除。
- 列在设计表之外另有：`queue_canonical`（入队请求的规范形式，用于 `clientMutationId` 重放与 `idempotencyConflict`）、`recipients_preview`（最多 3 个信封收件人）与 `recipient_count`（列表不解析 MIME）、`resolution` / `resolution_mutation_id` / `superseded_by`（`unknown` 的处理，取代 `resolved` 布尔值）。`envelope` 为 `{ from, recipients }`，`last_error` 为 `{ reason, smtpCode, text, rejected[] }`，`server_reply` 为 `{ code, text }`，均只含脱敏文本。
- 索引：`outbox_due`（`queued` 项的下一个到期项，部分索引）、`outbox_by_account`（列表）、`outbox_by_draft`、`outbox_by_message_id`、`outbox_sent`（本地已发送副本，按接受时间倒序，部分索引）。
- 草稿锁：草稿有“存活”项（`queued`、`sending`、未处理的 `unknown`）时，`update_draft` 与 `delete_draft` 返回 `draftLocked`，再次入队同一草稿也返回 `draftLocked`；检查与插入在同一事务中。`accepted` 时同一事务删除草稿；`failed` / `canceled` 时草稿保持原样，即可编辑。
- `accepted` 行保留 `mime`、`envelope`、`accepted_at`、`server_reply`，即本地已发送副本；`server_copy_message_id` 与 `deleted_locally_at` 已建列，由第 5 步使用，本步不读写。

快照已改为内容寻址的 blob 文件（第 16.6 节，迁移 v14）：`outbox` 行只记 `snapshot_hash`、`snapshot_size` 与释放时间 `snapshot_released_at`，`mime` 列可空、新行不再写入，旧行由启动外迁搬进 blob 后清空。草稿附件在 `draft_attachments`（迁移 v13）。

## 14. 富文本写信（已实现）

2026-10-24 确认：写信编辑器改为富文本，使用 Tiptap；**不再保留纯文本编辑模式**，因为富文本本身就能写纯文本。本节取代第 1 节中"纯文本正文"、第 7 节中"纯文本引用"和第 8 节中"正文为 `text/plain`"的旧描述。

### 选型

- 编辑引擎用 Tiptap（基于 ProseMirror）的开源包：`@tiptap/core`、`@tiptap/react`、`@tiptap/pm`、`@tiptap/starter-kit`、官方 `@tiptap/markdown` 及所需的 MIT 扩展，全部来自公开 npm。Markdown 解析和序列化交给官方扩展，不维护自有语法转换器。
- **不使用**任何 `@tiptap-pro` 包、Tiptap Cloud、AI Toolkit 或需要账号令牌的私有仓库：AI Toolkit 是付费附加项、发布在私有仓库，开源后别人无法构建，也违背"AI 由我们的核心控制"的原则。
- 选型依据：用户已在 Edge（Chromium，对应 Windows 的 WebView2）和 Safari（WebKit，对应 macOS 的 WKWebView）中试过官方示例的中文输入法，均无问题。真实 Tauri 窗口和 Linux（WebKitGTK）仍要手动验证。Squire 体积更小、专为邮件，但输入法相关 issue 未关闭，扩展空间也小；桌面应用不在乎那点体积，所以不选。

### 首版格式

| 包含 | 暂缓 |
| --- | --- |
| 粗体、斜体、下划线、删除线；标题 1–3 | 标题 4–6、代码、字体 / 字号 |
| 链接（仅 `http`、`https`、`mailto`） | 表格、图片（含粘贴的图片）、分隔线、任务列表 |
| 无序列表、有序列表（可嵌套） | 签名、表情选择、@提及 |
| 引用（可嵌套） | AI 改写与建议修改 |
| 换行、清除格式、撤销 / 重做 | |
| 左 / 居中 / 右对齐、8 色文字与 5 色高亮（第 15 节） | 两端对齐、任意颜色、取色器 |

暂缓的格式不在编辑器的结构定义（schema）里，所以粘贴进来的这些内容会在解析时降级为普通文字或被丢弃，而不是原样保留。

### 编辑行为

- **回车即换行，和常见邮件客户端一致**：每一行是一个段落，段落没有上下外边距；空一行就是一个空段落。编辑器里和发出的 HTML 用同样的间距规则。
- **Markdown 输入**（2026-10-25 调整）：支持 `# ` / `## ` / `### ` 标题、`**粗体**` / `__粗体__`、`*斜体*` / `_斜体_`、`~~删除线~~`、`[文字](https://example.com)`；列表和引用保留。使用 Tiptap 的输入快捷规则，行内强调在行首或空白后触发；块级语法在行首加空格触发。转换后直接编辑富文本，可立即退格还原语法或撤销。不新增 Markdown 源码编辑模式，草稿与发信仍使用现有 HTML 流程。
- **快捷键**用 Tiptap 默认值（如 `Cmd/Ctrl+B`、`I`、`U`），工具栏的悬停提示里写明。**换行扩展默认的 `Mod-Enter` 必须去掉**，只保留 `Shift+Enter`，否则会抢走两步发送的 `Cmd/Ctrl+Enter`。
- **链接**：`Cmd/Ctrl+K` 或工具栏按钮打开小浮层，填写或修改地址，也可移除。只接受 `http`、`https`、`mailto`；输入或粘贴网址自动识别成链接；在编辑器里点击链接不跳转，只打开编辑浮层。写信窗口没有打开外部链接的权限，这一点不变。
- **粘贴**：有 HTML 时仍优先使用净化后的富文本；只有纯文本时，通过一层剪贴板接入调用官方 `@tiptap/markdown` 的解析器，语法及空行采用官方行为。解析结果再经过已有邮件 HTML 粘贴过滤；Markdown 链接也使用 `http` / `https` / `mailto` 白名单。不再二次应用强调等粘贴规则。`Cmd/Ctrl+Shift+V` 跳过 Markdown 解析，沿用编辑器的纯文本粘贴行为。
- **官方 Markdown 的当前边界**：只使用已有邮件 schema，不为试用额外加入代码、表格或图片扩展。图片降为替代文字；混合内容中的代码、表格可能被官方解析器忽略，不承诺原文保留；解析结果完全为空时回退到原文。需要完整保留这些语法时使用纯文本粘贴。默认粘贴的段落分隔和连续空行遵循 Markdown 语义，不保证与逐行纯文本粘贴一致。草稿加载 / 保存仍是 HTML，只有剪贴板文本走 Markdown 解析。

### 工具栏

- 放在正文上方、岛内，没有边框和分割线，符合[界面设计](ui-design.md)。
- 全部用现有的 `IconButton`（图标加悬停提示；段落样式额外显示当前类型），格式处于激活状态时显示按下态并带 `aria-pressed`。
- 分组：粗体 / 斜体 / 下划线 / 删除线｜链接｜无序 / 有序列表｜引用｜清除格式。窗口变窄放不下时，靠后的分组收进"更多"菜单。
- 点击工具栏按钮不能让编辑器失去焦点和选区。
- 不做浮在选区旁边的工具栏：它在输入法组合输入时容易闪动或挡住候选框。

### 数据与核心

- **核心是唯一权威**：草稿保存 `body_html`。前端每次提交的 HTML，核心都按下面的白名单重新净化后再存；同时由核心从净化后的 HTML 生成 `body_text`，用于列表预览、空白判断、搜索和发信的纯文本部分。前端和以后的 MCP 都不能直接写 `body_text`。
- **净化白名单**：`p`、`br`、`strong`/`b`、`em`/`i`、`u`、`s`/`strike`/`del`、`a`（仅 `href`，仅 `http`/`https`/`mailto`）、`ul`、`ol`（可带 `start`）、`li`、`blockquote`。其他标签去掉标签保留文字（`script`、`style` 等连内容一起删除），所有其他属性（含 `style`、`class`、`on*`）一律删除。实现复用核心已有的 `ammonia`，与阅读端的净化规则分开配置。
- **旧草稿**：迁移 v9 给 `drafts` 加可空的 `body_html`。读取时 `body_html` 为空的旧草稿，由核心把 `body_text` 按行转成段落（转义后包 `<p>`），下次保存时写入 `body_html`。已入队的发送项保存的是 MIME 快照，不受影响。
- **限制**：`body_html` 不超过 2 MiB；生成的 `body_text` 仍受原来的 1 MiB 限制。
  - 兼容例外：旧纯文本草稿在 HTML 转义后可能超过 2 MiB。提交的正文与核心当前返回值逐字节相同时，允许仅修改收件人或主题并复用已保存的正文，仍可直接发送，不截断旧内容；新建或实际修改正文仍受上述限制。v9 的长度限制由应用服务执行，避免数据库约束挡住这类旧草稿的首次保存。

### 纯文本的生成规则

段落一行；空段落一个空行；换行转为换行符；段落内前导空格、连续空格和制表符保留；块元素之间的纯排版空白忽略。无序列表项前加 `- `，有序列表项前加 `1. `、`2. `……，嵌套每层缩进两个空格；引用每行前加 `> `，嵌套叠加；链接写成"文字 <地址>"，文字和地址相同时只写地址；粗体等格式去掉。

### 发出的 HTML 与 MIME

- 每封信都是 `multipart/alternative`：先 `text/plain; charset=utf-8`（上面的规则生成），后 `text/html; charset=utf-8`。传输编码由 `lettre` 按内容选择，整封 MIME 仍必须是 ASCII（未支持 SMTPUTF8）。
- HTML 由核心生成一个最小文档：带 `<meta charset="utf-8">`，正文外包一层 `div`，用内联样式设置系统字体、14px、行高 1.5 和 `white-space:pre-wrap`；`p` 内联 `margin:0`，空段落补 `<br>` 保留空行；`blockquote` 内联 `margin:0 0 0 0.8ex;border-left:1px solid #ccc;padding-left:1ex`；列表收紧上下外边距。不使用 `class`、`<style>` 和外部资源。

### 回复与转发

- 引用头按创建草稿时的有效语言生成并固化。桌面宿主读取 `effectiveLocale` 后传给 `create_draft_from_localized`；引用资源由 core 的纯文本函数消费，不由前端改写。切换语言不重写已有引用头，也不改变草稿 revision、dirty、发送确认或编辑器选区；日期字符串及 `Re:` / `Fwd:` 识别沿用现状。
- 回复：开头一个空段落（光标放在这里），然后使用当前语言的引用句（中文为"{日期}，{发件人} 写道："，英文为"On {date}, {sender} wrote:"），再接一个 `blockquote` 装原文。
- 转发：开头一个空段落，然后使用当前语言的转发标题和发件人、日期、主题、收件人标签，再接原文（不放进引用块）。中文标题为"---------- 转发的邮件 ----------"；具体译文由共享 `composeTemplates` 资源维护。
- 原文来源：原邮件有 HTML 时，用阅读端已缓存的 HTML 再过一遍上面的发信白名单，保留段落、强调、链接、列表和引用；标题 h1–h3 保留、h4–h6 降为 h3；原文的对齐、颜色和高亮不保留（第 15 节）；表格展开成逐格文字；图片去掉，有非空 `alt` 时按创建语言留下占位文字（中文"[图片：alt]"，英文"[Image: alt]"，模板为共享 `composeTemplates.imageAlt`）。`alt` 保留原值，不再次解释模板参数，整个占位文字经 HTML 转义并受既有 512 KiB 引用上限约束。只有纯文本时按行转段落。这样会丢掉原邮件的复杂排版，首版接受这一损失；以后可以改为"发信时由核心把原 HTML 附加在后面，不进入编辑器"。
- 引用的原文仍有 512 KiB 上限。

### 安全

- 编辑器从不接收未经净化的 HTML：初始内容来自核心（已按白名单净化），粘贴内容经编辑器结构解析。不使用 `dangerouslySetInnerHTML`，编辑器里没有"原样嵌入 HTML"的节点。
- 写信窗口的 CSP 保持不变（`style-src 'self'`）：设置 `injectCSS: false`，把 Tiptap 需要的几条基础样式写进我们自己的样式表；不加 `'unsafe-inline'`，也不需要 nonce。首版格式都不需要 `style` 属性，所以不受 CSP 影响。
- 编辑器只在写信窗口按需加载（动态导入），引擎不进入主窗口的初始包。识别到写信入口后立即加载，与草稿读取并行；同一 WebView 复用导入请求和已加载组件。加载完成后直接显示编辑器，失败可重试且不重新读取或覆盖草稿。开发模式下 Vite 启动时预热编辑器源码转换，减少第一次打开时的等待；预热不创建编辑器实例。

### 不做

纯文本 / 富文本切换、"默认写信格式"设置、AI 改写与建议修改、写信附件、签名。编辑器封装成一个独立模块，对外只暴露读写内容、选区和焦点等少量接口，为以后的 AI 建议修改留出位置。

## 15. 富文本第二批：标题、对齐、颜色（已实现）

2026-10-24 确认。在第 14 节基础上增加标题、段落对齐、文字颜色和高亮；表格暂缓，图片随写信附件单独立项。本节与第 14 节冲突处以本节为准，第 14 节"首版格式"表已同步当前范围。

### 范围

| 包含 | 仍暂缓 |
| --- | --- |
| 标题 1、标题 2、标题 3 | 标题 4–6、字体 / 字号 |
| 段落对齐：左、居中、右 | 两端对齐（Firefox 与 `pre-wrap` 冲突，邮件里也少用） |
| 文字颜色：固定色板 8 色 | 任意颜色、取色器 |
| 高亮（文字背景色）：固定色板 5 色 | 表格、图片、分隔线、代码 |

### 核心约束：写信窗口不允许 `style` 属性

写信窗口的 CSP 是 `style-src 'self'`，元素上的 `style` 属性会被拦下。Tiptap 官方的 `Color`（`@tiptap/extension-text-style`）、`TextAlign`（`@tiptap/extension-text-align`）和多色 `Highlight` 都把值写进 `style`，**不能直接使用**。因此：

- **编辑器里**：对齐、颜色、高亮只用固定的 `data-` 属性表示，取值是色板里的名字，不是颜色值。例如 `<p data-align="center">`、`<span data-color="red">`、`<mark data-highlight="yellow">`。实际的颜色由我们自己的样式表按属性值选择器给出，分别为浅色和深色界面配色。
- **核心白名单**只接受这些属性和固定的名字，其他取值一律删除。
- **发出的邮件**由核心把这些属性换成内联样式（邮件客户端只认内联样式），名字和颜色值的对应表是核心里的常量。

可以使用 MIT 包 `@tiptap/extension-heading`（StarterKit 已包含，重新启用即可）、`@tiptap/extension-text-align`、`@tiptap/extension-text-style`、`@tiptap/extension-highlight` 作为基础，但必须重写它们的属性解析与输出（`addAttributes` 的 `parseHTML` / `renderHTML`）改为 `data-` 属性；也可以完全自己写这三个小扩展。两种做法以"编辑器里不出现任何 `style` 属性"为准绳。

### 色板

名字是存储和传输的唯一形式；邮件中的颜色值固定，不随用户的界面主题变化。

| 名字 | 文字色（邮件） | 高亮色（邮件） |
| --- | --- | --- |
| `gray` | `#6b7280` | `#e5e7eb` |
| `red` | `#dc2626` | `#fecaca` |
| `orange` | `#ea580c` | — |
| `yellow` | `#ca8a04` | `#fef08a` |
| `green` | `#16a34a` | `#bbf7d0` |
| `blue` | `#2563eb` | `#bfdbfe` |
| `purple` | `#9333ea` | — |
| `pink` | `#db2777` | — |

- 文字色 8 种，高亮 5 种（`gray`、`red`、`yellow`、`green`、`blue`）。
- 编辑器里的显示色由前端样式表决定，深色界面下要换成可读的亮色；邮件里永远是表中的值。
- 默认文字色不写任何属性（"自动"），这样收件人的深色模式邮件客户端能正常反色。

### 标题

- 三级：`h1`、`h2`、`h3`。编辑器里和邮件中都是较大的粗体，行距与段落一致，上下不加外边距（与"回车即换行"一致）。邮件内联样式：`h1` 为 `font-size:20px`，`h2` 为 `18px`，`h3` 为 `16px`，都加 `margin:0;font-weight:bold`。
- 纯文本生成：标题原样输出一行，不加 `#` 等标记，与普通段落相同。
- 快捷键用 Tiptap 默认 `Cmd/Ctrl+Alt+1/2/3`；行首 `# ` / `## ` / `### ` 自动转换为对应标题（与第 14 节 Markdown 输入一致）。
- 回复与转发：引用原邮件时**不再把标题降为加粗段落**，`h1`–`h3` 保留，`h4`–`h6` 降为 `h3`。

### 对齐

- 只作用于段落和标题；列表项和引用里的段落也可以对齐。属性 `data-align` 取值 `center` 或 `right`；左对齐是默认值，不写属性。
- 邮件里转成 `text-align:center` / `text-align:right`，与该元素原有的内联样式（如 `margin:0`）合并在同一个 `style` 里。
- **不提供对齐快捷键**。Tiptap 默认的 `Cmd/Ctrl+Shift+L/E/R` 必须去掉：应用的 `installBrowserDefaultGuards`（`frontend/src/lib/browser-defaults.ts`）把带修饰键的 `R`（刷新）当作浏览器快捷键拦截，`Cmd/Ctrl+Shift+R` 根本到不了编辑器，只做 L、E 会让三个按钮行为不一致。对齐只用工具栏。
- 纯文本生成忽略对齐。
- 回复与转发：原邮件里的 `align` 属性或 `text-align` 样式**不保留**，避免把原邮件的排版带进来；首版接受这一损失。

### 颜色与高亮

- 文字色：`span`，属性 `data-color`；高亮：`mark`，属性 `data-highlight`。两者可以叠加，也可以和粗体等格式叠加。
- 邮件里：`span` 转为 `style="color:…"`；`mark` 转为 `style="background-color:…;color:inherit"`（`color:inherit` 避免部分客户端把 `mark` 的文字变成黑色）。
- 纯文本生成忽略颜色和高亮。
- 粘贴：外部内容里的颜色和背景色**全部丢弃**，不尝试映射到色板。用户需要颜色时自己用工具栏设置。
- 回复与转发：原邮件里的颜色同样不保留。
- "清除格式"同时清除颜色、高亮和对齐，不清除标题（标题是块类型，用"正文"按钮恢复）。

### 工具栏

在第 14 节的工具栏上调整，仍然全部用 `IconButton` 加悬停提示（含快捷键），不加边框和分割线：

- 最前面加一个**段落样式**下拉：正文 / 标题 1 / 标题 2 / 标题 3，显示当前块的样式。
- 粗体组后面加**文字颜色**和**高亮**两个按钮，各打开一个小色板浮层：色块 + 名字（悬停提示和读屏使用当前界面语言，如"红色" / "Red"），第一项是"自动"/"无"的对应译文，当前值打勾。存储的颜色名不随语言改变。色板用键盘可以操作（方向键选择、回车确认、`Esc` 关闭），关闭后焦点和选区回到编辑器。
- 列表组前面加**对齐**按钮组：左、居中、右，当前值显示按下态。
- 窄窗口时的收起顺序：先收对齐、引用、撤销重做，再收颜色组；段落样式和粗体组始终可见。

### 安全与数据

- 核心白名单在第 14 节基础上增加：`h1`、`h2`、`h3`、`span`、`mark`；属性只增加 `p`/`h1`/`h2`/`h3` 的 `data-align`（`center`、`right`）、`span` 的 `data-color`（8 个名字）、`mark` 的 `data-highlight`（5 个名字）。`span` 和 `mark` 没有合法属性时去掉标签保留文字。
- 前端粘贴过滤与编辑器结构同步：只放行上述属性和取值，其他一律删除，`style` 属性仍然永远不进入编辑器。
- 不需要新迁移：仍存于 `drafts.body_html`。旧草稿和已入队的发送项不受影响。
- 写信窗口的 CSP 不变，不加 `'unsafe-inline'`。

实现位置：前端 `mail-body-format-extensions.ts`、`mail-body-editor.tsx` 与本地样式表；核心 `core/src/drafts/body.rs`。没有新增依赖、数据库迁移或 DTO 字段。自动测试、浏览器预览与未验证范围见[验证记录](../development/validation.md)。

### 16.2 参考：其他开源客户端

下表据 Thunderbird Android（K-9）、Geary、Mailspring 的相关源码和 Thunderbird 桌面、Delta Chat、终端客户端的公开资料整理，只作取舍依据。

| 客户端 | 写信附件 | 待发队列 | 已发送副本 |
| --- | --- | --- | --- |
| Thunderbird 桌面 | 只记原文件路径，保存或发送时才读 | 完整 MIME 写入本地 mbox 文件夹 "Unsent Messages" | 追加到服务器已发送 |
| Thunderbird Android（K-9） | 按 MIME 分段入库，大于 16 KiB 的段写成磁盘文件 | 发件箱是本地文件夹，存完整邮件 | 移到已发送并追加到服务器 |
| Geary | — | 整封 RFC822 存在 `SmtpOutboxTable` 的列里 | 追加后删除本地行 |
| Delta Chat | 添加时复制进 blobdir，按哈希命名 | 生成好的 MIME 存在 `smtp` 表 | 不长期保留 |
| Mailspring | 复制进应用的 `files/` 目录，草稿只记 ID | 无持久队列，发送时生成 | 依赖服务器 |
| aerc / neomutt / himalaya | 只记路径 | 基本无离线队列 | 追加到服务器 |

取舍结论：

- 有离线队列的客户端都存"能直接发的完整邮件"，重试不重新生成。MailX 保留第 8 节的固定快照。
- 有离线草稿的客户端都把附件复制进来；只记路径在沙箱、跨重启草稿下会失效。MailX 添加时复制进 blob。
- 大块字节不进数据库。MailX 的快照改存 blob 文件，这也是存储设计原本的 `mime_blob_id`。
- 没有客户端把已发送副本永久留在本地。MailX 改为服务器对上后释放快照（第 16.7 节）。

### 16.3 附件进入草稿

- 来源只有两处：宿主打开的文件选择对话框，以及拖放到写信窗口的文件。宿主读取字节交给核心，本机路径不进 DTO，前端也拿不到。
- 核心收到字节后立即写入现有的内容寻址 blob（SHA-256、临时文件、同步、原子重命名），再写 `draft_attachments` 行；同一内容重复添加只多一行引用，不重复写文件。
- `draft_attachments`：草稿 ID、附件 ID、展示文件名、媒体类型、原始字节数、blob 哈希、是否内嵌（第一批恒为否）、内嵌时的 Content-ID（第二批）、来源（用户添加 / 转发预填）、创建时间。草稿删除时级联删除。
- 文件名保留原名用于展示和 MIME，只去掉控制字符和路径分隔符；不信任客户端提供的媒体类型，按内容嗅探并参考扩展名，识别不了用 `application/octet-stream`。不按类型拦截，服务器拒绝时按第 16.4 节反馈。
- 添加、移除附件和改正文一样提升草稿 `revision`、走乐观并发；草稿被锁定（第 7 节）时拒绝。
- 写信窗口第一批只列出与移除附件，不提供预览或另存。
- 附件字节不进入 AI 上下文和 MCP，命令不对这两者开放。

### 16.4 上限与"邮件过大"

- 上限暂定为单封邮件**附件原始字节之和 20 MiB**。base64 编码后整封约为 1.37 倍，20 MiB 附件约 27–28 MiB 的 MIME；单个附件不另设上限。数量上限暂定 20 个。
- 上限按账号解析为 `AttachmentPolicy`：先取默认值，以后按服务商元数据覆盖。服务器在 `EHLO` 声明的 `SIZE` 是实时的权威值，每次发送时记到账号上；写信窗口据此提示"该服务器上限约 X MB"（按 1.37 倍折算，只作提示）。
- 检查分三层：前端在添加时预检，只为体验；核心在添加和入队时校验，是权威；SMTP 会话照第 4 节在 `MAIL FROM` 前按 `SIZE` 比较完整 MIME。
- 服务器拒绝的映射（补现状的缺口：现在这些情况都落到通用 `server` 原因）：

| 时机 | 回复 | 归类 |
| --- | --- | --- |
| `MAIL FROM` 或 `DATA` 之前 | 增强状态码 `5.3.4` 或 `5.2.3` | `Permanent(messageTooLarge)` |
| 正文写完后的最终回复 | 增强状态码 `5.3.4` 或 `5.2.3` | 明确拒绝，原因为 `messageTooLarge` |
| 任意时机 | 只有 `552`、没有增强状态码 | 保持通用服务器原因（`552` 也表示对方邮箱已满） |

- 这几种都是确定失败，不是 `unknown`，不会重复发送。队列项变为 `failed`，草稿重新可编辑；提示写"邮件过大"，已知时带上服务器上限，用户移除附件后可再次发送。以后接入网盘时在这里给出"改用网盘链接"（第 16.10 节）。

### 16.5 MIME 结构

- 没有附件时结构不变，仍是 `multipart/alternative`（纯文本 + HTML），现有测试照常通过。
- 有附件时外层改为 `multipart/mixed`：第一段是原来的 `multipart/alternative`，其后每个附件一段，`Content-Disposition: attachment`，`Content-Transfer-Encoding: base64`，76 列换行。第二批的内嵌图片在 `alternative` 外再包一层 `multipart/related`。
- 文件名同时写 RFC 2231 的 `filename*=UTF-8''…` 与 RFC 2047 编码的 `name`，照顾老客户端。中文文件名在国内服务商网页端的显示在第 6 步核对；lettre 的默认输出不满足时自己构造头部。
- 快照仍是纯 ASCII，第 4 节的 `SMTPUTF8` 判定不变。

### 16.6 入队冻结与快照 blob

入队（第 8 节）改为：

1. 在服务锁外读出草稿全部附件 blob，读取时校验哈希。
2. 生成完整 MIME，写成快照 blob。
3. 一个事务内：核对草稿 `revision` 和附件集合未变，插入队列项（快照哈希、字节数），锁定草稿。核对失败就放弃，已写的快照 blob 无人引用，由启动 GC 回收。

之后：

- 草稿在 `accepted` 后照第 8 节删除，`draft_attachments` 级联删除，附件 blob 失去引用。稳定状态下只剩快照这一份字节；入队到发出之间短暂存在附件和快照两份。
- 发送从快照文件读取并校验哈希。快照缺失或损坏时在正文开始前失败（永久失败，不重新生成），不会出现 `unknown`。
- 现有超时只覆盖等待回复；写出大正文改用"无进展超时"（暂定 2 分钟内没写出任何字节即失败），不设总时长上限。实现时核对第 4 节的超时表。
- blob 回收沿用存储设计：业务删除只删数据库引用，启动 GC 把 `draft_attachments` 与队列项快照都算作存活引用，再回收孤立文件。
- 迁移：迁移脚本重建 `outbox` 表，新增快照哈希与字节数列，`mime` 列改为可空。旧行的字节由启动时一次幂等的外迁步骤写成 blob 后再清空该列，失败可以重跑。`mime` 列暂保留为可空、新行不再写入，留到之后的迁移删除。这超出了[数据库迁移](database-migrations.md)的纯 SQL 步骤，该文档已相应增加第 4.4 节（非 SQL 的启动外迁）并更新版本清单。

**A0–A3 的落地（2026-10-28）**：

- 迁移 v13 `0013_draft_attachments.sql`、v14 `0014_outbox_snapshot_blob.sql`（重建 `outbox`，保留自引用 `superseded_by` 与全部索引）。外迁为 `Storage::migrate_outbox_snapshots`，在 `Storage::open` 里位于迁移之后、启动 GC 与任何 worker 之前；启动 GC 的存活引用现在是 `message_bodies.raw_sha256`、`draft_attachments.blob_hash` 与 `outbox.snapshot_hash` 的并集。
- 附件核心接口：`MailxCore::add_attachment(request, bytes)`、`remove_attachment(request)`、`attachment_policy(account_id)`；请求类型 `AddAttachmentRequest` / `RemoveAttachmentRequest`，返回完整 `Draft`。文件名的清洗与媒体类型嗅探在 `core/src/drafts/attachments.rs`。
- 入队分三段：`AccountService::prepare_send`（持锁读取）→ `SendBuild::freeze`（不持锁：读 blob 并校验哈希、构造 MIME、写快照 blob）→ `commit_send`（一个事务内核对 `revision` 与附件 ID 列表、插入队列项并锁定草稿）。核对不符返回 `conflict`，已写的快照无人引用，留给启动 GC；`Core::queue_send` 按这三段调用。
- 发送从快照文件读取并校验哈希；缺失或损坏时以 `snapshotMissing` 永久失败，正文未开始，不重新生成。`failed` / 已撤销行的快照在该草稿被重新入队时清空并记 `snapshot_released_at`（同一事务）；发件箱中删除行本身的命令尚不存在，届时同样清空。
- 与本节原文的差异：附件 DTO 命名为 `DraftAttachmentSummary`（`mail::AttachmentSummary` 已用于已缓存邮件的附件）；新增错误码 `attachmentTooLarge` 与 `tooManyAttachments`；`AttachmentPolicy` 目前恒为默认值（单封 20 MiB、20 个），按账号覆盖与 `SIZE` 记录属 A4。

### 16.7 已发送快照释放

取代第 9 节原来的"永久留在本地"：

- `accepted` 后保留快照，直到头部同步按 Message-ID 把它对上"服务器已有"；之后清空快照引用、记录释放时间。Message-ID、信封、接受时间、服务器回复和对上的服务器邮件一直保留。
- 列表本来就只显示服务器那封，释放对用户不可见。
- 服务商不保存已发送时永远对不上，快照一直保留，"服务器没有时本地一定有"成立。
- 代价：对上之后服务器副本再被删除，本地也没有内容了；这和主流客户端一致。
- 有没有附件都按此处理。`queued`、`sending`、`unknown` 的快照绝不释放；`failed` 和已撤销的行的快照在该行从发件箱移除或被重新入队取代时释放。

清理与回收（2026-10-28 补充）：

| 情况 | 处理 | 批次 |
| --- | --- | --- |
| 草稿附件 | 草稿删除后引用随之删除，下次启动 GC 回收文件 | 第一批 |
| `failed` / 已撤销的快照 | 按上一条释放 | 第一批 |
| 已发送快照 | 头部同步按 Message-ID 对上后释放。对上逻辑原属第 12 节第 5 步，提前到附件第一批实现；本地副本的列表合并与阅读仍留在第 5 步 | 第一批 |
| 服务商不保存已发送，永远对不上 | 向服务器 IMAP APPEND 已发送副本，之后照常对上释放；仍属第 13 节待定，按第 6 步实测结果决定 | 后续 |
| 仍对不上的快照 | 设置页单独显示这部分占用，提供手动清理与"N 天后清理"选项，**默认关闭**；开启即放弃"服务器没有时本地一定有"，由用户主动选择 | 后续 |
| 运行中回收 | 第一批只在启动 GC 回收；之后在释放引用时删除已确认无人引用的文件，须先处理与正在写入的 blob 之间的竞争 | 后续 |

在后续几项落地前，服务商不保存已发送时，带附件的已发送邮件会一直占用本地磁盘，没有总量上限；存储设计中这部分本来就不参与缓存自动淘汰。

### 16.8 转发带原邮件附件

- 转发本来就要求原邮件的原始 MIME 已在本地。创建转发草稿时，核心从中取出非内嵌附件（复用附件保存取字节的路径），解码写入 blob，作为来源为"转发预填"的草稿附件。默认全部带上，用户可像普通附件一样移除。
- 只在首次创建时预填；`create_canonical` 的幂等不变，重复点击转发不会重复添加。
- 超过上限时照常创建草稿，附件栏标出超限并阻止发送，用户移除后可发。
- 原邮件里被 `cid:` 引用的内嵌图片第一批不带，第二批作为内嵌图片带上。
- 实现后第 1 节"原邮件的 N 个附件不会随转发发出"的提示不再需要。

### 16.9 宿主与权限

- 写信窗口的 capability 增加添加附件、列出附件、移除附件三条命令，只作用于本窗口的草稿；主窗口不获得这些命令。
- 文件选择对话框由宿主打开，前端只拿到 `AttachmentSummary`（附件 ID、文件名、媒体类型、字节数、来源）。
- 应用 API 的 `Draft` 增加附件列表、`FailureReason` 的 `messageTooLarge` 补充服务器上限，实现时同步[应用 API](../contracts/app-api.md)。

### 16.10 网盘链接（仅规划）

- 附件模型预留 `delivery: Embedded | Link`，在入队冻结时决定每个附件怎么发；MIME 构造只接收决定好的段列表，链接模式在纯文本和 HTML 两部分都插入链接说明。
- 上传等于对外发布，每次发送都要用户明确确认，AI 不能代为确认；网盘凭证进 `SecretStore`；上传走账号路由或单独的路由策略，代理失败不得回退直连。
- 上传在 SMTP 会话之前完成，上传失败即为发送前失败，不会出现 `unknown`。

### 16.11 第二批：内嵌图片

- 只允许 `src="cid:<uuid>"`：草稿白名单加入 `img`，属性过滤只放行这一种 `src` 和 `alt`，其他一律去掉。`data:` 和远程地址不允许。
- 插入图片先存为附件（标记为内嵌、生成 Content-ID），再把 `cid:` 写入编辑器；保存时核对每个 `cid:` 在本草稿附件里存在，找不到就去掉该图片并提示。
- 编辑器里用从命令取得的字节生成 blob URL 显示，不直接渲染 `cid:`。粘贴 HTML 里的图片继续去掉。
- 内嵌图片计入附件上限。
