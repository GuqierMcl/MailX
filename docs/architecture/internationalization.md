# 中英文文本适配

状态：**Implemented：首版中英文文本适配；区域格式化 Planned；三平台桌面验收待补** · 2026-10-25。当前代码已覆盖语言设置、主窗口与写信窗口同步、界面与错误文本，以及 Rust 生成的通知和回复 / 转发模板。资源、设置竞态与文本行为已有自动检查；打包后的 Windows / macOS / Linux 多窗口、原生通知和布局证据仍需分别补齐，不能据此宣称完整平台验收。

## 1. 目标与实施边界

首批覆盖简体中文与英文文本，支持用户选择语言、重启恢复、主窗口与独立写信窗口同步，以及 Rust 生成的系统通知和回复 / 转发模板文字。语言切换即时更新应用文案，不重新加载页面或重新挂载写信编辑器。

实现位于 `frontend/src/i18n/`、各功能组件、公共 `locales/`、`core/src/localization.rs`、`core/src/settings.rs` 及桌面宿主。设置文件沿用现有 v1 格式，不需要邮件数据库迁移。

以下内容继续按原数据展示：邮件原文、发件人、主题、附件名、用户自定义账号名和文件夹名。首批保留现有日期 / 时间、数字、文件大小、列表连接和文件夹排序规则，不引入新的区域格式化层。英文界面中的日期仍可能按原样显示中文月份或星期，这是本版的明确边界。

首批也不包含邮件翻译、繁体中文翻译资源、RTL 排版、翻译平台、在线下载词库或操作系统语言热切换。原生文件对话框、系统编辑菜单及操作系统自身的提示可能跟随系统语言，应用内语言设置不保证覆盖这些内容。

## 2. 首批产品规则

| 项目 | 当前规则 |
| --- | --- |
| 用户选择 | `system`、`zh-CN`、`en`；选择器显示“跟随系统 / 简体中文 / English” |
| 设置位置 | “通用”设置页中的语言选择器 |
| 新安装默认 | 没有设置文件时为 `system` |
| 已有设置迁移 | 已存在的合法设置文件缺少语言字段时补 `zh-CN`，保留升级前的显示语言；用户可再选择跟随系统 |
| 系统语言映射 | 启动时由宿主读取；中文语言标签（含 `zh`、简繁体及地区变体）映射到 `zh-CN`，英文及地区变体映射到 `en`，其他语言或读取失败回退到 `en` |
| 系统语言变化 | 首版重启后重新解析；应用内显式选择语言立即生效 |
| 缺失词条 | 使用中文资源回退；静态 key 类型与 CI 检查覆盖正式消息集合，未知错误使用受控通用提示 |
| 日期与其他格式 | 日期 / 时间排列、数字和文件大小格式、列表连接及文件夹排序沿用现状；“昨天”等显式文案可翻译，时间分段逻辑、时间戳与时区语义保持现状 |
| 计数文案 | 支持变量插值与英文单复数，例如 `1 new message / 2 new messages`；不因此改变数字本身的格式 |
| 已有草稿 | 保留内容；语言切换不改正文、主题、草稿 revision、dirty 状态或发送确认状态 |
| 已显示系统通知 | 不撤回、不重发；后续生成的通知使用生成时的有效语言 |
| 已显示应用 Toast | 正文和动作沿用出现时语言并按原生命周期消失；新提示使用当前语言，切换语言不重发提示或重置撤销倒计时 |

资源回退语言与系统语言不受支持时的默认语言是两项不同规则。前者用于遗漏或异常，后者用于首次选择；两种语言的正式词条应完整。

## 3. 资源与模块组织

前端采用 `i18next + react-i18next`，依赖由 `bun.lock` 锁定。资源随应用打包，初始化不依赖网络。当前资源分为 8 个 namespace；复数的不同分支按同一条逻辑消息检查。

当前结构：

```text
locales/
  zh-CN/
    common.json
    settings.json
    accounts.json
    mail.json
    composer.json
    errors.json
    notifications.json
    composeTemplates.json
  en/                       # 与上面相同的逻辑消息集合
frontend/src/i18n/
  index.ts                  # 实例、资源与启动初始化
  locale.ts                 # 浏览器预览映射、首屏缓存与文档语言
  errors.ts                 # 错误码、字段与操作上下文到文案
  settings-sync.tsx         # 两种窗口共用的设置订阅与语言同步
  settings-watch.ts         # 监听注册、生命周期与设置补读
  resources.d.ts            # 翻译 key 的 TypeScript 类型声明
core/src/localization.rs    # 支持语言与宿主输出所需的纯函数
desktop/src/locale.rs       # 系统语言读取与宿主注入
scripts/check-i18n.mjs      # 资源结构、参数与共享子集检查
```

资源放在仓库公共位置，core 不引用 `frontend/`。前端通过 Vite 的静态 glob 导入全部 JSON；Rust 用 `include_str!` 嵌入通知与模板资源。两端共享同一份词条，避免维护重复译文。

规则：

- 使用语义 key，如 `mail:yesterday`；不要把整段中文作为 key。
- 翻译完整句子，变量使用命名参数；计数传 `count` 并采用语言对应的复数形式，不拼接数字与名词。
- 模块级菜单、状态表和文件夹角色表保存 key；组件或文本辅助函数在使用时翻译，避免语言切换后保留旧字符串。现有格式化工具只按需要提取显式文案，不改日期、数字或排序规则。
- 组件使用 `useTranslation`；React 外部调用在实际执行时取当前语言。错误、通知状态等优先保存结构化数据，在展示时翻译。
- TypeScript 约束 key；资源检查另行验证语义消息集合和占位符。复数消息按逻辑消息对齐，分别校验中文和英文需要的分支，不能机械要求两种语言的原始 key 完全相同。
- `notifications` 与 `composeTemplates` 是 Rust 使用的共享子集，只允许明确的命名插值和首批语言所需的复数分支；不在 Rust 实现通用 i18next 解释器。
- Rust 通过有类型的文本生成函数消费共享子集，编译时嵌入资源。检查缺失 key、缺失或未知参数及英语单复数；列表参数沿用现有连接结果，插值按模板一次解析，变量内容不再作为模板求值。
- 翻译资源不提供执行脚本或读取 IPC 的能力。React 按文本渲染，草稿引用头按纯文本组合后走现有 HTML 转义路径。

## 4. 设置、初始化与跨窗口同步

### 4.1 当前设置契约

持久化设置增加独立节：

```ts
type LanguagePreference = 'system' | 'zh-CN' | 'en'
type SupportedLocale = 'zh-CN' | 'en'

type GeneralSettings = {
  language: LanguagePreference
}

// 在现有结构上增加字段，不替换其他设置节。
type SettingsSnapshotAdditions = {
  effectiveLocale: SupportedLocale
  revision: number
}

type SettingsChanged = {
  revision: number
}
```

`AppSettings` 增加 `general`，`SettingsPatch` 增加可选的 `general`。保存仍按节合并；同一节的局部编辑先与最新值合并。`effectiveLocale` 由偏好与宿主注入的系统语言计算，只出现在返回快照中，不持久化，也不能由前端提交。

core 只处理受支持语言和纯映射规则，不调用 Tauri 或平台 API。桌面宿主读取系统语言并将解析结果注入设置 / 应用服务；通知和草稿创建使用同一份有效语言。浏览器预览使用 `navigator.languages` 与相同映射规则，mock 客户端提供等价快照和变更订阅。

设置兼容规则需要区分“没有文件”“已有文件缺字段”和“语言值非法”：前两者按第 2 节处理；可解析文件中的非法语言值按字段回退到 `system`，保留其他合法设置。IPC 提交不支持的语言返回 `validation`，字段为 `general.language`。JSON 损坏及不可读文件继续遵守现有备份 / 恢复约定。

这是设置文件的兼容性扩展，不需要邮件数据库迁移。跨边界 DTO 由 Rust 导出并生成 TypeScript；新增字段后运行类型生成与漂移检查，不手工修改生成的 TypeScript。

### 4.2 快照修订号

`revision` 是当前宿主进程内的设置提交版本，不写入设置文件。它由设置存储在同一把锁内随成功提交递增，与该次返回快照保持一致；失败不递增。设置存储成功打开后在进程内复用，应用重启后窗口重新建立版本状态。

所有前端读取、保存响应和事件补读经过 `frontend/src/lib/settings-cache.ts` 的统一快照接收入口，拒绝比已接收版本更旧的结果。`useUpdateGeneral / Appearance / Security / Layout / Notifications / Compose` 均使用该入口；同一节保存串行处理，其他节可独立保存。

语言选择采用保存成功后应用，保存中禁用重复提交，失败时保留原语言并显示本地化错误。其他设置已有的乐观反馈继续保留，但已提交快照与待保存更改分开维护；较新的快照只叠加仍待保存的更改，失败只撤销该次更改，不恢复整个旧快照。

### 4.3 订阅与首次读取

1. 各可信窗口先建立 `mailx://settings-changed` 订阅，确认监听注册完成，再读取完整设置快照。`MailxClient.onSettingsChanged` 返回 `Promise<取消监听函数>`，表达注册完成，避免订阅与首次读取之间遗漏更新。
2. `settings_update` 成功写盘后，向可信主窗口和写信窗口发送 `{ revision }`；失败不广播。事件不包含凭证，也不向邮件正文 iframe 开放设置访问。
3. 窗口收到事件后重新读取快照；由统一入口按 revision 判断是否接收结果。事件只作失效通知，不作为唯一事实来源。
4. 窗口重新获得焦点时补读，恢复事件丢失后的状态。监听失败时仍读取快照，重新激活时重试订阅并补读。
5. 保存响应与事件到达顺序不作假设，旧响应不能覆盖较新快照；卸载时清理监听，兼容 React StrictMode。

### 4.4 首屏与运行时行为

`main.tsx` 在 React 首次渲染前，以 localStorage 的 `mailx.language` 中缓存的有效语言初始化同步打包的资源；无缓存时使用浏览器语言映射作临时选择。缓存包含偏好与有效语言，只用于首屏，不是事实来源。`SettingsSync` 挂在业务启动闸门之外，拿到宿主快照后统一更新语言、缓存和 `document.documentElement.lang`。宿主数据不可用时继续显示缓存 / 默认语言及可理解的错误。

语言切换通过上下文更新完成，不把 locale 放进应用、邮件阅读会话或编辑器的 React key，不清空数据查询缓存，不重新下载邮件正文。窗口默认标题、Tooltip、无障碍标签和命令面板文案随之更新；日期等格式化结果与文件夹排序沿用现状。带用户主题的窗口标题仍展示主题。

## 5. 各类文本的迁移方式

| 范围 | 主要落点与要求 |
| --- | --- |
| 通用界面 | `components/`、标题栏、启动页、设置；包含关闭按钮、读屏提示、加载态与失败态 |
| 账号 | 向导、连接表单、服务商登记、验证提示；服务商品牌和用户输入继续显示原值 |
| 邮件 | 导航、系统文件夹角色、搜索范围、命令面板、列表、阅读、正文下载、远程图片和附件提示 |
| 文本与现有格式工具 | `mail/format.ts` 中“昨天”、收件人预览中“等 N 位”等显式文案进入资源；现有日期 / 数字格式、列表连接及 `folder-tree.ts` 的排序规则保留 |
| 写信与发件箱 | 收件人、富文本工具栏、颜色名称、保存状态、两步发送、撤销倒计时、失败 / unknown 状态与操作 |
| 错误 | `AppError`、startup 错误、同步失败原因、正文 / 图片错误、发件箱原因和前端 transport / hostUnavailable；按稳定代码、field 和上下文映射 |
| 系统通知 | 新邮件单封 / 多封、隐藏预览、发送结果、测试通知；Rust 使用当前有效语言，继续执行原来的预览隐藏和静音规则 |
| 回复 / 转发 | core 创建草稿时接收有效语言，生成引用头及图片替代文字占位后立即固化；图片 alt 保留原值并转义，主题前缀识别与回复线程字段沿用现有协议行为 |

错误处理不通过匹配中文 `message` 决定行为。已知错误映射为当前语言；未知错误使用当前语言的通用提示。现有固定脱敏 `message` 可继续作为兼容或诊断信息保留，不能因此展示底层异常。如果某个错误码在不同操作中语义不同，优先增加操作上下文；仍不足时再按实际场景细分错误码并同步契约。

回复 / 转发模板只影响新创建的草稿。切换语言不改写已有引用头，也不触发自动保存、revision 增加、重新入队或自动发送。引用头中的标签、句子和带 alt 图片的占位标签翻译；alt 原文不翻译、不再作为模板求值，整个占位按现有路径转义并计入 512 KiB 引用预算。日期字符串继续使用现有格式与草稿创建时已有的时区输入，原邮件内容仍走现有净化与隔离路径。

## 7. 验证与验收

### 自动验证

- 设置：新文件默认、旧文件补中文、非法语言按字段恢复、IPC 非法输入、写盘失败及 revision 语义。
- 同步：监听建立与首次读取之间发生更新、旧响应晚到、保存响应和事件交错、事件丢失后焦点补读、多个设置节并发编辑、失败只回滚自身更改。
- 资源：两种语言的逻辑消息集合、需要的复数分支、参数、Rust 共享 key 和类型导出；不以“扫描到任何中文”为失败条件，注释、测试邮件和用户数据有明确边界。
- 前端：测试显式固定初始语言、重置 i18n 与缓存，关键流程覆盖中文和英文；不要通过将 `t` 原样返回 key 绕过真实翻译行为。
- 文本插值：验证数量 0 / 1 / 多个及英文单复数，变量值不丢失也不被二次解析。
- 既有格式行为：沿用相关回归测试，确认切换语言不改变日期 / 数字格式、列表连接、排序、时间戳和时区；“昨天”等显式翻译文案单独验证，不扩大为区域格式化重构。
- 编辑器：输入未保存内容后切换语言，选区、正文、dirty 状态和 revision 保持；发送确认不自动推进、撤销窗口不因翻译重新计时。
- Rust：通知预览关闭时不含发件人 / 主题；共享模板的特殊字符被转义；回复线程与发送状态行为回归。

现有检查入口包括 `bun run i18n:check`、`bun run typecheck`、`bun run lint`、`bun run frontend:test`、`bun run build`、`bun run types:check`、`bun run rust:fmt`、`bun run rust:clippy`、`bun run rust:test` 和 `git diff --check`。根 `bun run check` 包含资源门禁。2026-10-25 已确认资源门禁、前端类型与 lint、完整前端测试、生产构建、Rust workspace 测试、格式、clippy 和类型漂移检查通过，浏览器 mock 已检查基本语言持久化和写信预览同步。具体证据见[验证记录](../development/validation.md#2026-10-25-中英文文本适配)，不能据此推定三平台桌面验收通过。

### 手动验证

使用浏览器 mock 的主窗口和写信窗口，检查英文长文案、最小窗口、缩放、命令面板、Tooltip、富文本工具栏、读屏名称与中英文混合的真实数据布局。

桌面分别记录 Windows / macOS / Linux 打包版本的主窗口 + 多个写信窗口同步、关闭再打开、启动失败、系统语言映射、通知和默认窗口标题。不能从一个平台通过推断其他平台通过。通知使用测试通知或合成事件，发信回归优先使用受控本地 SMTP 服务；真实发信仍遵循现有授权边界。

## 8. 后续区域格式化

状态：**Planned**。日期 / 时间本地化、相对日期算法、数字与文件大小格式、符合语言习惯的列表连接和排序作为后续独立任务。届时再评估给现有格式工具显式传入 locale、统一使用 `Intl` 的范围，以及日历边界、时区和排序变化对选中项的影响。

首版仅保留清晰的语言来源和文本资源边界，不预建空的 `format.ts` 或改造这些工具的调用链。后续区域格式化不作为 P0–P4 文本适配的完成条件。
