# 工具层与调用入口

状态：**Planned** · 尚未实现；决定见 [ADR 0004](../adr/0004-shared-tool-layer.md)。本文工具名、模块位置和策略数值均为草案，实现时可调整并同步更新。

## 1. 分层

```text
内置 Agent / 固定工作流 ──────────────── 进程内调用 ─┐
本地外部 Agent → stdio bridge → 本机受控 IPC → MCP 适配层 ─┤→ 工具层 → 应用服务 → 存储 / 协议
远程外部 Agent → HTTPS Streamable HTTP ──→ MCP 适配层 ─┘
```

- **工具层**（core，候选位置 `core/src/tools/`）：工具定义、schema 校验、按调用方的可见性与策略、授权检查、结果整形和错误码。与传输无关，不依赖 Tauri、Axum 或 UI。
- **MCP 适配层**：把工具层中对 MCP 可见的工具映射为 MCP 工具，处理 initialize、版本协商、工具列表、取消与 JSON-RPC 错误。桌面核心与服务端进程托管同一份实现，只换底层传输。候选为 core 内的协议模块或桌面 / 服务端共用的独立 crate，M0 验证 `rmcp` 依赖后再定，任何一种都不能把 Tauri 或 Axum 带入 core。
- **传输**：本地 IPC 监听由桌面宿主创建；远程 HTTP 路由由服务端宿主挂载。stdio bridge 只完成配对握手后转发字节，不解析工具。
- **内置 Agent**：AI Runtime 直接调用工具层，工具调用结果作为不可信材料回填给模型，不经 MCP 序列化。

## 2. 工具定义

每个工具包含：

| 字段 | 说明 |
| --- | --- |
| 标识 | 工具层内部稳定 ID，例如 `search_emails`；MCP 适配层对外加 `mailx_` 前缀 |
| 输入 / 输出 schema | 拒绝未知字段，ID 与字符串有长度上限，字段采用 camelCase，与应用 DTO 一致 |
| 可见入口 | `builtinAgent`、`mcp` 的组合；未声明即不可见，MCP 必须显式声明 |
| 所需动作 | 例如 `accounts:read`、`mail:read`、`draft:create`，授权检查依据 |
| 按入口策略 | 输出上限、账号范围来源、是否需要用户确认等，见第 4 节 |
| 行为注解 | 只读 / 会写本地数据 / 需用户确认；只帮助调用方理解，不作为安全控制 |
| 处理函数 | 接收 `RequestContext` 与已校验输入，经应用服务执行 |

处理函数不感知入口；入口差异全部体现在 `RequestContext` 与策略上，不为不同入口复制实现。

## 3. RequestContext

宿主为每次调用构造 `RequestContext`，调用方输入不能自报额外权限：

| 调用方 | 主体 | 账号范围来源 |
| --- | --- | --- |
| 内置 Agent | runId、模型提供商与模型 | 本次 Run 的选定内容与该提供商的披露授权 |
| 本地 MCP | clientId（经配对凭据认证） | 该客户端的授权记录 |
| 远程 MCP | 远程授权主体与 clientId | 远程授权范围（待设计） |

现有代码只有发送路径中的 `Caller` 枚举（`Composer`、`MainWindow`、`Mcp`、`Model`），用于拒绝非写信窗口确认发信；实现工具层时将其扩展或并入 `RequestContext`，保留“只有写信窗口能确认发信”的检查。

每次调用都重新检查授权状态，撤销后后续调用立即拒绝。已知 `emailId` 也要先确认其账号在范围内，不能绕过账号授权。调用记录主体、工具、资源 ID、结果与 requestId，不记录完整工具结果。

## 4. 工具集（草案）

工具池按“相交”组织：两侧共享领域工具，各自另有专属工具。

| 工具 | 内置 Agent | MCP | 说明 |
| --- | --- | --- | --- |
| `list_accounts` | ✓ | ✓ | 范围内账号 id、显示名、状态 |
| `search_emails` | ✓ | ✓ | 本地检索，限量摘要与游标 |
| `read_email` | ✓ | ✓ | 纯文本片段、发件方、附件元信息，按字符分页 |
| `create_draft` | ✓ | ✓ | 只建本地草稿，不代表发送；UI 标出创建来源 |
| `get_ui_context` | ✓ | | 当前选中的邮件或正在编辑的草稿引用 |
| `propose_draft_edit` | ✓ | | 对编辑器中的草稿提出修改，带 revision，由用户接受 |
| `present_suggestions` | ✓ | | 摘要、待办等结构化建议展示到界面 |
| `request_user_confirmation` | ✓ | | 请求用户在界面中确认高风险动作；只能请求，不能批准 |
| `show_email_in_app` | | ✓ | 让 MailX 窗口定位并打开某封邮件，交给用户查看 |
| `get_grant_scope` | | ✓ | 返回当前客户端被授权的账号与动作 |

前四项的输入输出与限制见 [MCP 草案](../contracts/mcp.md)。其余为候选，进入实现前单独补齐 schema。MCP 的 resources / prompts 等协议特有能力若后续提供，只存在于 MCP 适配层。

没有任何入口提供可直接发信的工具；未来内置 Agent 推进发信只能经 `request_user_confirmation` 一类工具交给用户确认，确认与完整内容哈希 / 草稿版本绑定，规则见 [发送架构](sending.md)。

## 5. 按入口策略

同一工具对不同入口可取不同策略，示例：

| 策略 | 内置 Agent | MCP |
| --- | --- | --- |
| 账号范围 | 本次 Run 的选定内容；需要检索更大范围时须先取得该提供商对相应账号的披露授权 | 客户端授权账号；授权界面可再收窄 |
| `read_email` 输出上限 | 受 Run 输入预算约束（初案 32,000 字符） | 默认 8,000、单次上限 32,000 字符 |
| 正文未缓存 | 返回 `BODY_NOT_CACHED`，界面可提示用户获取 | 返回 `BODY_NOT_CACHED`，引导到 UI 获取，不隐式下载 |
| 结果去向 | 发送给所选模型提供商，属于内容披露 | 返回给外部客户端，MailX 无法约束其后续处理 |

内置 Agent 的工具结果会进入模型请求，因此每次工具调用都按 [AI Runtime](../ai-runtime/README.md) 的披露规则计入范围；MCP 侧的风险提示在授权界面说明。

## 6. 结果与错误

- 邮件正文、主题和发件显示信息作为不可信材料返回，不能被当作系统指令拼接。
- 结果不包括 API Key、邮箱密码、refresh token、本地路径或无关账号信息。
- 业务失败返回稳定错误码与简短建议；MCP 适配层把参数或协议错误映射为 JSON-RPC 错误，把业务失败映射为工具错误结果。
- 纯文本分页按 Unicode 字符计数，不切断编码；读取不自动标记已读。

## 7. 实施顺序

1. 工具层骨架、`RequestContext` 与授权记录。
2. 共享工具的应用服务支撑：纯文本读取接口、草稿来源标记。
3. 内置 AI 固定工作流接入工具层。
4. 本地 MCP：MCP 适配层、桌面 IPC 监听、stdio bridge 与配对界面。
5. 服务端：同一 MCP 适配层挂到 Streamable HTTP，远程授权另行设计。

各阶段仍按[路线图](../roadmap/README.md)的完成标准验收。
