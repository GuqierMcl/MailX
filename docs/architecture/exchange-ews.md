# 自建 Exchange 邮箱接入

本页定义自建 Exchange 的 EWS 接入边界。它与使用 OAuth 和 IMAP/SMTP 的 Microsoft 365 入口分别配置；自动测试及真实服务器验证范围记录在[验证记录](../development/validation.md)。

感谢 [Arilt](https://github.com/Arilt) 在 [PR #141](https://github.com/GuqierMcl/MailX/pull/141) 提供的初版 EWS 实现、自建服务器使用反馈及 NTLM、自动发现和文件夹兼容性排查。这些前期工作为本功能的接入方向和验证场景提供了依据；后续实现按 MailX 当前账号、路由、同步与发件箱架构整合。原 PR 保留用于继续补充问题和讨论。

## 1. 账号类型与兼容

添加账号提供独立的「Exchange（自建服务器）」入口，复用既有三步向导、账号资料、网络路由与凭据管理。普通邮箱预设、通用 IMAP/SMTP 和 Microsoft OAuth 的登录流程不参与 EWS 自动发现。

`MailConnection` 表达两种真实连接：旧的 `ImapSmtp { imap, smtp }` 与带 `backend: "ews"` 的 `Ews { ews: { url, username } }`。旧账号的 JSON 仍直接包含 `imap`、`smtp`，旧恢复日志可读取；EWS 不生成占位 IMAP/SMTP 端口。创建请求的旧 canonical 序列化保持一致，避免旧 requestId 的幂等重放失效。

EWS 使用一个 NTLM 密码配置，输入仍沿用 `password/shared` 与 `SecretUpdate`，返回 `ewsNtlm` 凭据摘要。实际秘密只存在 SecretStore，SQLite 保存引用。账号保存本身不联网。第一期拒绝在已有账号上切换协议；用户应新增相应类型的账号。

## 2. 来源与信任

协议、规范化主机和端口、实际路径、登录身份参与 EWS 凭据信任。URL 必须为 HTTPS，不接受 userinfo、查询串、fragment 或无效端口；路径不转换大小写、不随意删去尾斜杠。同邮箱域名和有效 TLS 证书不自动扩大可接收密码的目标。

更改 EWS 端点或登录身份会建立新 `mailboxSourceId`；只改密码、代理或资料不更换来源。`keep` 保留密码原有受信范围，新目标需要重新提供凭据。账号配置版本和代理版本仍按既有规则推进，在途读取必须通过来源与版本检查后才能提交。

数据库以新增迁移增加 `mail_backend`、`ews_connections`、`ews_items` 与 `ews_folder_state`。旧 `mail_connections` 的约束和历史迁移不修改。EWS ItemId 映射到本地持久化、单调分配的代理 UID，按账号来源和文件夹隔离；ChangeKey 是可更新版本，不作为本地邮件身份。共用邮件表、搜索索引、正文 blob 和草稿。

## 3. 自动发现

用户在 Exchange 入口填写邮箱地址并主动继续后，核心按邮箱域名生成有限的 HTTPS 候选，并遵守当前表单路由。未提交凭据时，401 是可能需要认证的中间结果，不直接解释为密码错误；404 视为未找到，其他服务器错误按协议错误报告。已提交凭据后的 401/403 才判为凭据被拒，不再重复索要密码。服务器未返回登录名时，结果保留用户填写的用户名。查找失败或超时可继续手动填写，已有输入保留。

发现凭据仅能用于核心签发的短期、一次性目标授权。授权绑定邮箱和确切目标；响应中的其他 EWS 地址、HTTP 重定向或 XML redirect 只能成为待展示候选，不继承上一个目标的凭据。用户在表单中看到目标并继续登录即表达该次授权。后台不以域名相同为由在多个主机间轮流提交密码。

路由无效不发请求，自定义代理失败不直连。表单输入、模式或目标变化使迟到结果失效。发现不创建账号、不写 SecretStore、不改变已有连接；XML 使用有界解析并禁止 DTD，响应与日志不包含密码、NTLM token 或原始服务器错误文本。

## 4. 网络与认证

EWS 通过既有 `net::connect` 建立直连、SOCKS5 或 HTTP CONNECT 流，再用系统信任库验证 HTTPS。NTLMv2 握手与后续请求保持同一 HTTP/1.1 连接，不使用跨账号连接池，不自动重放提交请求。

认证使用现有维护的 SSPI 实现，密码学和 XML 解析依赖库完成。TLS 握手保留实际连接的服务端证书信息用于 channel binding；不提供关闭证书验证或关闭服务器扩展保护的开关。具体 NTLM/EPA 组合、证书拓扑与企业代理仍需真实环境验证。

`Negotiate` 是协商入口，不能仅凭这个响应头断定为 Kerberos-only。除直接 NTLM 外，支持由 SSPI 完成的 SPNEGO 协商，协议列表明确限定为 NTLM；不会自动选择 Kerberos 或访问域控制器。握手有轮数上限并检查最终协议，仍使用同一连接与通道绑定。不实现 EWS Basic 收发、Kerberos、EWS OAuth、共享邮箱或代理邮箱；Autodiscover 的 Basic 仅用于用户已授权的 HTTPS 目标。

## 5. 业务接入

同步管理器继续负责账号任务生命周期、前后台轮询、退避和取消。EWS 单独执行协议请求，不启动 IMAP IDLE；文件夹与邮件更新通过原事件刷新界面和通知。新增邮件入库和已有邮件的标记更新分别处理，待写回的本地意图优先。

同步使用有界的时间窗口和分页。达到上限时明确标记覆盖不完整；截断列表不得用来推断远端删除。非邮件条目占用分页位置但不入库，不能被当作空页。已有本地副本的邮件不再重复读取收件人，已读和星标状态仍来自每轮列表；ItemId 映射只在变更标记变化时写入，角色文件夹在一次 GetFolder 中查询。列表预览按批合并 GetItem，中途失败时保留已取得的预览。邮件正文和附件按需通过 MIME 获取并进入共用缓存、渲染和隔离阅读流程。列表预览及通知验证码读取也按账号类型分派，不借助假的 IMAP 配置。

已读、星标与删除复用原有持久化队列、撤销期限和失败恢复。标记成功只确认本次写入的目标值；不能误清除用户随后改变的意图。删除区分移到已删除与经过确认的永久删除，结果和失败恢复沿用原事件出口。网络、超时、协议错误或 Exchange 繁忙等不针对单封邮件的故障结束本轮并保留全部待写回项，不消耗重试次数；只有服务器拒绝具体邮件才计入失败恢复。

发件箱在同一账号服务边界生成 SMTP 或 EWS 发送计划，计划失败不能回退另一协议。EWS 消费已冻结的 MIME 和完整收件人集合，密送收件人通过 EWS 属性表达，不能遗漏或写进可见 MIME。连接认证成功后，在实际提交前可靠写入发送阶段标记；标记写入失败不发信，提交请求的等待时间随 MIME 大小放宽，避免大附件在慢速上行中被固定时限截断；提交结果不明进入 `unknown`，不自动重发。EWS 接受结果不伪造 SMTP 状态码。

服务器已发送副本与本机快照继续按确定身份对账；服务器改写 Message-ID 或缺少足够证据时保留本机副本，不依据主题、时间猜测，也不触发重新发送。

新建和已保存账号都提供 EWS 连接诊断。诊断显示单条 Exchange 结果，仅代表登录和实际测试的读取操作，不证明邮件投递成功。
