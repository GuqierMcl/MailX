# 系统凭据库的存取方式：单条目保险库

状态：**设计草案，未实现**。目标是让 macOS 用户无论配置多少账号，每次启动最多面对一次钥匙串授权，而不是每个账号一次。实现代码预计只落在 `desktop/src/secret_store.rs`，核心库的 `SecretStore` trait 和凭证 journal 逻辑不变。

## 1. 问题

当前每个密码是系统凭据库里的独立条目（service `MailX`，account 为 `mailx/<账号 ID>/<随机 ID>`），启动后同步、列表、发信会分别读取。macOS 钥匙串对每个条目有独立的访问控制列表（ACL）：应用不在条目的可信列表里，就对该条目弹一次授权窗。

实测（2026-10-25，本机）：

- 安装版 `/Applications/MailX.app` 是 ad-hoc 签名，`TeamIdentifier` 为空，指定要求是 `cdhash H"…"`；每次构建、每次升级都变成另一个应用，必须重新授权。
- 旧服务名下 3 个条目的可信应用记录分别有 91、81、6 条，几乎全是各次构建的 `target/debug`、`target/release` 路径。
- 用 `security` 命令迁移出来的新条目，可信应用只有 `security` 和一个 debug 二进制，不含安装版，所以安装版首次读取必弹窗。应用自己创建的条目，创建者默认可信，不属于这种情况。

所以：3 个账号 = 3 次弹窗，账号越多越多。正式签名（Developer ID）能让升级后“还是同一个应用”，是根治办法，但依赖付费账号和第 4 阶段的签名工作；单条目设计与它互补，不依赖它。

## 2. 方案

整个应用只在系统凭据库里放**一个**条目：service `MailX`，account `vault`，内容是 JSON 的保险库：

```json
{ "version": 1, "secrets": { "<key>": "<value>", "…": "…" } }
```

`key` 就是核心今天使用的 `secret_ref`（`mailx/<账号 ID>/<随机 ID>`），不改格式，所以数据库、journal 和核心逻辑一律不动。

`SystemSecretStore` 变成对这个条目的读改写代理：

| 操作 | 行为 |
| --- | --- |
| `get(key)` | 首次使用时读取并缓存整个保险库（一次系统调用，至多一次授权）；之后从内存返回 |
| `set(key, value)` | 取互斥锁 → 修改内存副本 → **先写回系统凭据库，成功后才更新缓存并返回** |
| `delete(key)` | 同上；不存在时幂等成功 |

保持 `SecretStore` 现有契约：`Ok(None)` 只表示确认不存在，`set` 返回前已持久化，`delete` 幂等，错误仍映射为 `Locked` / `Unavailable` / `Failed`，且不转发提供方的错误文本。

## 3. 需要处理的问题

**并发与丢失更新。** 读改写必须在同一把互斥锁内完成，写回失败时缓存不变。单进程内由锁保证；跨进程已有 `mailx.lock` 保证同一数据目录只有一个实例，开发版与安装版共用同一个保险库时同样受它约束。

**缓存与新鲜度。** 缓存只在本进程生命周期内有效，外部修改（用户在钥匙串里手动删除）要到重启才生效。读不到整个保险库时（锁定、未授权）不缓存失败结果，下一次访问重试，保持“可重试”的启动语义。

**容量与一致性。** 保险库随账号数增长；Windows 凭据管理器的 `CredentialBlob` 不能超过 `CRED_MAX_CREDENTIAL_BLOB_SIZE`（5×512 = 2560 字节，见 [CREDENTIALW 文档](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala)），超过会写入失败。预计每个账号两三个短密码，几十个账号才会逼近，但这是 Windows 上的**硬限制，需要设计应对**：Windows 与 Linux 继续用现有的逐条目存储（这两个平台没有这个问题），单条目只用于 macOS。通过 `#[cfg(target_os = "macos")]` 切换实现，其他平台行为不变。

**旧条目迁移（首次启动，一次性）。**

1. 读保险库条目；不存在则进入迁移。
2. 枚举数据库里所有 `secret_ref`（账号配置里引用的 key），逐个从旧的逐条目存储读取，合并写入保险库；任何一个读取失败就整体中止，不删除任何旧条目。
3. 写入保险库并读回校验全部 key 后，旧条目**不立即删除**，留到下一次启动再清理（成功读取保险库一次后），保证中途崩溃或回退版本都不会丢密码。
4. 迁移期间旧条目的读取会各弹一次窗（只发生这一次）；此后每次启动只读一个条目。

这一步要求 `SystemSecretStore` 能拿到“有哪些 key”：由宿主在构造时从数据库读取引用列表（只读，不涉及密码值），或迁移时对每个 key 回退读旧条目。后者更简单，不引入核心库依赖：`get(key)` 在保险库缺失该 key 时回退读取旧条目，命中则写入保险库——即**惰性迁移**。缺点是迁移期间仍可能多次弹窗；优点是实现小、可回退。倾向惰性迁移，启动时再主动对数据库里全部引用做一次预热迁移（同样只是调用 `get`），把弹窗集中在启动那一刻。

**回退与降级。** 新版写入保险库后，旧版本读不到新创建的密码。alpha 阶段可接受，写进 `CHANGELOG.md`。

**自动更新与签名。** 保险库条目由应用自己创建，创建者可信，所以正式签名后升级不弹窗；未签名阶段每次升级仍需授权一次，但只有一次。

**与 `credential_journal` 的配合。** journal 通过 `SecretStore` 接口读写，所以逻辑不变：`commit` 里的“先写密码、再确认存在、再应用配置”在单条目下仍成立，而且一次保险库写入比多次独立写更不易产生半途状态。

## 4. 备选方案

| 方案 | 结论 |
| --- | --- |
| 保持逐条目，只在列表时不读密码 | 同步启动时仍要读所有密码，只是推迟弹窗，放弃 |
| 数据保护钥匙串（Data Protection Keychain） | 彻底无提示，但需要 entitlement 与描述文件，第 4 阶段签名稳定后再评估 |
| 应用自己加密本地文件，主密钥放钥匙串 | 同样是一次钥匙串访问，但要自己负责加密、密钥轮换和备份，风险更大，不选 |
| 全平台统一单条目 | Windows 单条上限使它不安全，不选 |

## 5. 验证计划

- 单元测试（用可注入的后端替身，不碰真实钥匙串）：读改写并发、写回失败不更新缓存、`get` 缺失 key 回退旧条目并迁移、`delete` 幂等、旧条目不在迁移中被删除、错误码映射和日志不含密码。
- 默认忽略的真机测试：在已解锁的 macOS 桌面上创建、读取、迁移、删除合成条目（沿用现有 `native_secret_store_roundtrip` 的做法），结果单独记录。
- 手动验证：多账号冷启动只出现一次授权；重启不弹窗；迁移后旧条目仍在；模拟中途崩溃后仍能读到密码。
- Windows 与 Linux 的行为没有改动，仍由原有测试覆盖；macOS 之外的结论不外推。
