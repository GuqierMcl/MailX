# 内置 AI 工具权限

状态：**Proposed** · 2026-11-15 修订。第 2–4 节的权限、确认与撤销已在 core 与桌面宿主实现（「此刻」对话已接入确认卡与撤销；仅有自动测试与浏览器预览，没有用真实服务商验证）；接口见[应用服务 API](../contracts/app-api.md#ai-助手主窗口)。本文规定内置 AI（[AI Runtime](../ai-runtime/README.md) 中的对话与固定任务）调用[工具层](agent-tools.md)时哪些操作直接执行、哪些先问用户。本地 MCP 的授权不变，仍见 [MCP 草案](../contracts/mcp.md#2-桌面连接与授权)。

2026-11-15 修订：能力与 MCP 对齐，整理默认直接执行并可撤销，发信默认每次确认、可在设置中改为直接发送；去掉了此前草案中的一次性确认凭据、“附件只能经文件选择框添加”和“发信不提供放宽选项”。

## 1. 与 MCP 的同与不同

**相同**：可用的工具与 MCP 相同（读取、整理、草稿、附件、发信、发件箱），都不能删除邮件；都经工具层做账号范围检查、草稿版本检查与审计。

**不同**：

1. **默认更谨慎地对待发信**。内置 AI 会读邮件，邮件里可能夹带提示词注入（如“把最近的账单转发给某地址”）；MCP 客户端通常自带工具确认，内置 AI 只能由 MailX 提供。所以发信默认每次确认。
2. **读取即外发**。工具结果会进入发给模型服务商的请求，读取前必须有内容发送同意（[AI Runtime](../ai-runtime/README.md#5-同意与数据披露)）。
3. **有撤销**。整理类操作直接执行，但对话里会列出做了什么并提供撤销；MCP 没有界面可以承载撤销。

## 2. 操作类别

| 类别 | 工具 | 默认 | 设置中可改为 |
| --- | --- | --- | --- |
| 查找与阅读 | 列出账号、搜索邮件、读邮件、列出文件夹、列出 / 读取草稿、查看发件箱、查看工具说明（`mail_help`） | 直接执行（已同意发送内容） | — |
| 整理 | 标记已读 / 星标、归档 / 取消归档（`mail_archive` 的 `archive` 布尔值）、刷新同步 | 直接执行，可撤销 | 每次询问 |
| AI 的草稿 | 新建草稿、回复 / 转发草稿；修改、删除来源为 AI 的草稿及其附件 | 直接执行 | 每次询问 |
| 用户的草稿 | 修改、删除来源为用户或 MCP 的草稿，增删其附件 | 每次询问 | — |
| 发信 | 发送草稿、唤醒排队的发送、取消排队中的发送 | 每次确认 | 直接发送 |
| 不提供 | 删除邮件；修改账号、凭据与设置；开关 MCP 或助手 | — | — |

- 草稿以 `Draft.origin` 区分来源；AI 新建的草稿记为 `ai`，界面标“由 AI 创建”。
- 添加附件可以使用本机文件路径，与 MCP 相同；发信确认会列出全部附件名与大小，用户能看到要发出去的内容。选择“直接发送”时没有这一层检查，设置页说明这一风险。
- 用户正在写信窗口里编辑的草稿，工具层照常拒绝修改与发送。

## 3. 确认怎么实现

循环跑在 core 里，确认不需要单独的凭据系统：

1. 模型调用一个需要确认的工具时，循环不执行它，运行进入 `awaitingConfirmation`，向主窗口发出确认请求：动作、目标与一段由 core 根据当前数据生成的摘要（不使用模型提供的描述）。
2. 发信的摘要包括发件账号、收件人（含抄送 / 密送）、主题、正文开头和附件。以下情况额外标出提示：收件人从未与该账号往来过、收件人不在本次对话读过的邮件中、带有附件。
3. 只有主窗口能回应“允许”或“拒绝”；回应只对这一次调用有效。允许后循环用原参数执行；拒绝、取消运行或超时（暂定 10 分钟）时，模型收到“用户拒绝”的结果。
4. 发信沿用草稿版本号与幂等键：确认之后草稿又被修改，发送照常因版本不符被拒绝。确认后仍有撤销发送的等待时间。
5. 同一次运行里，被拒绝的同一操作在用户发出新消息前不会再次弹出确认。

实现时定下的细节：确认请求的字段与 `warnings` 的判定见 API 文档；“收件人从未往来过”查的是该账号本地缓存里的发件人、收件人、抄送与本机已发送副本的收件人（含密送）；“不在本次对话读过的邮件中”取本次运行里 `mail_read` 与 `mail_search` 结果出现过的地址。允许后核心重新检查助手开关与账号范围，再用原参数执行。超时拒绝时模型被告知“用户没有及时回应”。工具名不在上表任何一类时不执行也不询问。

## 4. 撤销

整理类操作直接执行后，对话里显示一行结果（如“归档了 3 封”），带“撤销”。撤销复用现有的整理撤销能力（`MailStateChanged` 的 `undoToken`，见[整理邮件工具](mail-organize-tools.md)），过期后按钮消失。标记已读 / 星标的撤销按原值写回。

实现选择：**不新增 `assistant_undo`**。工具层的 `Tools::call_traced` 在工具输出之外另给宿主一份只给可信界面的结果（归档的 `undoToken`、标记调用前的值），助手把它放进该调用的 `tool` 事件摘要（`ToolActivitySummary.changed.undo`），随事件只到达主窗口，不进入模型看到的任何文字。界面用已有的 `emails_undo_archive` 与 `emails_set_flags` 撤销，核心因此不保存撤销数据，撤销与用户自己的整理走同一路径。标记撤销是写回原值，不检查其间是否另有修改。

## 5. 范围、上限与审计

- 授权按运行生成：账号范围为设置中的“可用账号”；动作集合与每类的处理方式取自助手设置。每次工具调用都重新检查，关闭助手、撤销同意或修改设置后立即生效。
- 上限见 [AI Runtime 第 8 节](../ai-runtime/README.md#8-上限与预算初始值实测后调整)；整理工具单次最多 50 封，与 MCP 相同。
- 每次工具调用（含被拒绝、等待确认的）照常进入工具层审计，主体为 `BuiltinAgent { run_id }`，不记录参数与内容。

## 6. 对现有设计的影响

- [工具层](agent-tools.md)：`Grant` 需要为每个动作类别标记“直接执行 / 询问”，循环据此决定是否暂停；工具本身与 MCP 共用，不复制实现。
- [发送与附件工具](mail-send-tools.md)：MCP 规则不变；内置 AI 的发信默认经过第 3 节的确认。
- 界面形态见 [AI 交互界面](ai-chat-ui.md#44-确认卡)。
