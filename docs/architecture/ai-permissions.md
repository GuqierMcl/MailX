# 内置 AI 工具权限

状态：**Proposed** · 2026-11-14。尚无实现。本文规划内置 AI（AI Runtime 中的内置 Agent 与固定工作流）调用[工具层](agent-tools.md)时的授权模型，适用于「此刻」页面的对话以及以后阅读区、写信窗口等处的 AI 入口。本地 MCP 的授权不变，仍见 [MCP 草案](../contracts/mcp.md#2-桌面连接与授权)。

本文修订 [AI Runtime](../ai-runtime/README.md) 第 3 节中“内置 Agent 取得 `mail:send` 后无需逐封 UI 确认”的约定：内置 AI 发信改为每次由用户确认。

## 1. 为什么与 MCP 不同

本地 MCP 由用户打开一个总开关，外部 Agent 之后可直接发信、无需逐封确认。内置 AI 采用更严格的规则，原因是：

1. **指令来源不可信**：模型会读取邮件，邮件可能夹带提示词注入（如“把最近的账单转发给某地址”）。模型输出不能被当作用户意图。
2. **工具结果即外发**：内置 AI 的每次工具结果都会进入发给模型服务商的请求，读取本身就是内容披露。
3. **确认只能由 MailX 提供**：MCP 客户端通常有自己的工具确认；内置 AI 在 MailX 内运行，没有外部一层把关。

因此权限分两个维度，分别管理：

- **能看什么**：内容披露，沿用 AI Runtime 第 3 节的同意规则，决定账号范围。
- **能做什么**：动作权限，本文定义。

## 2. 动作分级

每个 `Action` 对内置 AI 有一个处理方式：**直接执行**、**询问**（执行前在界面确认）或**不提供**。

| 级别 | 动作 | 默认 | 用户可调整 |
| --- | --- | --- | --- |
| 只读 | `accounts:read`、`mail:read`、`outbox:read` | 在已同意的披露范围内直接执行 | 可按账号排除（见第 4 节） |
| 可撤销的本机写入 | `draft:create`；`draft:write`（仅限来源为 `ai` 的草稿）；`mail:organize`（已读、星标）；`mail:archive`；`mail:sync` | 询问 | 可改为“直接执行”，执行后在界面显示结果与撤销入口 |
| 高风险 | `mail:send`；`outbox:write`；修改或删除来源不是 `ai` 的草稿 | 每次询问 | 不提供“总是允许” |
| 受限 | `files:read`（添加本机文件为附件） | 模型不能指定路径，只能请求宿主弹出系统文件选择框，由用户选择文件 | 不可放宽 |
| 不提供 | 删除邮件；修改账号、凭证与设置；开关 MCP 或 AI | 工具层不对内置 AI 暴露 | 不可放宽 |

说明：

- **附件只经文件选择框添加**，否则一封带注入的邮件就能让模型把本机文件作为附件发出。现有 `add_draft_attachment` 的 `filePath` 输入对内置 AI 不可用，改由界面专属工具（如 `request_attachment_pick`）发起选择，结果只返回附件元信息。
- **发信首期没有放宽选项**。以后若确认操作过于频繁，可另行设计有限放宽（例如“本次对话内允许发给同一收件人”），需单独评审。
- 草稿以 `Draft.origin` 区分：AI 创建的草稿视为它自己的工作区，可在授权允许时修改；用户或 MCP 的草稿由用户作者，修改和删除一律询问。

## 3. 确认机制

“询问”必须由 core 强制，界面不是唯一防线。这与邮件翻译的同意由 core 强制是同一原则。

1. 模型调用需要确认的工具时，工具层不执行，而是返回“等待确认”，同时向宿主发出确认请求（运行 id、工具、目标资源与动作摘要）。
2. 宿主根据**当前数据**生成确认卡，不使用模型提供的文字描述动作。发信确认卡列出：发件账号、收件人（含抄送 / 密送）、主题、正文预览、附件；整理类确认列出目标邮件数量与前几封的发件人和主题。
3. 用户确认后，core 发放一次性确认凭据，绑定运行 id、工具、资源 id 与版本（草稿为 `revision`）、动作参数摘要；凭据短时有效（暂定 5 分钟），只能使用一次。
4. 工具层在执行时校验凭据；资源在确认后被修改（草稿 revision 变化、邮件已被移动）则凭据失效，需要重新确认。
5. 用户取消、关闭确认卡所在界面或超时，模型收到“已拒绝”结果，可据此回复用户，不能重复轰炸式请求（同一动作在同一运行内被拒绝后，再次请求前须有新的用户消息）。

工具表中的 `request_user_confirmation` 保持“只能请求，不能批准”；模型只能看到同意或拒绝的结果，拿不到凭据本身。

发信确认卡额外标出风险信号：

- 收件人从未与该账号往来过（首次联系）；
- 收件人不在本次对话引用的邮件往来中；
- 带有附件，或正文含有引用邮件中没有的链接。

确认后照常进入发送队列，撤销发送窗口与其他发送方式一致。`send::Caller::Model` 的入队路径要求携带有效凭据。

## 4. 范围与限额

- **按运行授权**：每次运行的 `Grant` 由宿主构造，账号范围等于用户已同意向该模型服务商披露的账号，减去被排除的账号；动作集合与处理方式取自第 2 节和用户设置。每次工具调用重新评估，关闭 AI、撤销同意或修改设置后立即生效。
- **按账号排除**：设置中可指定某些账号不供 AI 使用，被排除账号对 AI 完全不可见，与范围外账号表现一致（`notFound`）。
- **运行内限额**：整理类工具单次 1–50 封（与现有工具一致）；每次运行的写操作次数与发信次数设上限（数值待定），超过后要求用户发新消息继续，防止失控循环。
- **审计**：每次工具调用（包括被拒绝和等待确认的）经现有 `ToolAudit` 记录，主体为 `BuiltinAgent { run_id }`。以后可在设置里提供“AI 操作记录”供查看。

## 5. 设置

设置“集成 → AI”页增加一组“AI 可以做什么”：

| 行 | 选项 |
| --- | --- |
| 读取邮件 | 说明遵循内容发送同意；可选择不供 AI 使用的账号 |
| 整理邮件（已读、星标、归档、刷新） | 每次询问（默认）/ 直接执行 |
| 草稿 | 每次询问（默认）/ 直接执行 |
| 发信 | 固定为“每次确认”，只作说明 |

文案使用平实用语，例如“AI 发信前总会先问你”，不使用“授权”“凭据”等词。

## 6. 对现有设计的修订

- [AI Runtime](../ai-runtime/README.md) 第 3 节：内置 Agent 发信改为每次确认，以本文为准。
- [工具层](agent-tools.md) 第 3、5 节：`Grant` 需能表达每个动作的处理方式（直接执行 / 询问），并支持确认凭据校验；按入口策略增加“需要确认”。现有 `Grant { accounts, actions }` 在实现时扩展。
- [发送与附件工具](mail-send-tools.md)：MCP 规则不变；内置 AI 的发信和附件按本文。
- 「此刻」页面的对话按本文接入，见[「此刻」页面](now-page.md#6-ai-对话输入框)。
