# 桌面应用内更新

状态：**Implemented**。本文记录应用内更新的检查时机、自动下载、缓存、安装、网络路径、发版规则与交互。第 10 节保留验证方法与历史证据；功能实现不等于各平台安装包已验证，实际平台覆盖和后续结果统一见[验证记录](../development/validation.md)。

## 1. 目标与边界

- 桌面版固定检查新版本，默认在后台下载并验签，完成后提醒用户重启；也可在正常退出时安装。不会为了更新自动重启或打断工作。
- 只覆盖桌面宿主（`desktop/`）。核心库不感知更新；`server/` 以后另行设计。
- 不包含代码签名（macOS 公证、Windows Authenticode）。未签名阶段 macOS 更新后会被当作新应用，钥匙串会再请求一次授权（凭据已合并为单条目，所以只有一次），这一点已接受。
- “自动更新”只控制自动下载与相应的退出安装，不关闭版本检查；关闭后仍可手动下载。取消下载可暂停本次运行中的该版本，不提供永久“跳过此版本”或独立测试通道。

## 2. 发版规则：Pre-release 标记就是推送开关

- 应用只认 GitHub **Latest Release**：检查地址是 `https://github.com/GuqierMcl/MailX/releases/latest/download/latest.json`。GitHub 的 Latest 是最近一个非草稿、非 pre-release 的 Release，按 Release 所基于提交的时间排序。
- 因此规则只有一条：**发布时不勾 Pre-release = 推送给所有用户**，与版本后缀（`alpha`、`beta`、`rc`）无关。想发一个不推送的测试版，就勾上 Pre-release。
- 发版工作流**不再按后缀自动勾 Pre-release**，草稿默认是普通 Release，由维护者在发布时决定。发布说明开头的“预发布版本”提示仍按后缀显示。
- 更新器只在远端版本按 SemVer **高于**当前版本时提示，所以不会降级；`0.2.0-rc.1 < 0.2.0`，装了 rc 的用户会正常收到正式版。
- **撤回**：发出的版本有严重问题时，把它改回 Pre-release 或草稿，Latest 回到上一个版本；后续成功检查时更新目标或移除已撤回的待安装包。已经完成下载的运行中实例可能在下一次检查前退出并安装，因此撤回不保证即时阻止所有安装；已更新的用户不会被降级，仍需发更高版本号的修复版。
- 只维护一条版本线，总在最新 `main` 上打标签，Latest 总会指向最新版本。以后若给旧版本线补发修复，发布时用 `make_latest=false`。
- 已发布的 `v0.1.0-alpha.1`、`v0.1.0-alpha.2` 没有内置更新器公钥，**永远不会自动更新**，这些用户需要手动安装第一个带更新器的版本。

## 3. 签名密钥

- 更新器签名用 Tauri 的 minisign 密钥对。公钥（密钥 ID `B0DE08C9ED9EA8E9`）写入 `desktop/tauri.conf.json` 的 `plugins.updater.pubkey`，随应用发布。
- 私钥与密码只放在 GitHub `release` 环境的 secrets：`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，私钥由维护者离线保管。已有发布产出四平台签名，见第 10 节；修改密钥配置后需重新验证构建与更新。
- 按[发版流程](../development/release.md#8-更新器签名)记录，`release` 环境的部署分支 / 标签已限制为 **`v*` 标签和 `main` 分支**。构建任务都在这个环境里跑；打开 `createUpdaterArtifacts` 后没有私钥的构建会失败，因此 `workflow_dispatch` 的试跑同样需要它。从 `main` 触发允许，从其他分支触发会被环境拒绝。这是 GitHub 环境设置，代码里不配置。
- 私钥或密码丢失：已安装用户无法再自动更新，只能手动安装带新公钥的版本。更换公钥同理，需要过渡版本。

## 4. 产物与 `latest.json`

- `bundle.createUpdaterArtifacts: true`，构建时为可更新的格式生成更新包和 `.sig` 签名：macOS 为 `.app.tar.gz`，Windows 为 NSIS `-setup.exe`，Linux 为 `.AppImage`。`.deb`、`.rpm` 不能自更新，这部分 Linux 用户仍需手动安装。
- 构建任务的签名 secrets 只在 `environment: release` 下提供；手动触发（`workflow_dispatch`）的试跑也需要签名时同样走该环境。
- 发版工作流生成 `latest.json`，作为 Release 附件上传：

  ```json
  {
    "version": "0.2.0",
    "notes": "<CHANGELOG.md 中该版本的小节，不含安装说明页脚和预发布提示>",
    "pub_date": "2026-11-01T08:00:00Z",
    "platforms": {
      "darwin-aarch64": { "signature": "<.sig 文件内容>", "url": "https://github.com/GuqierMcl/MailX/releases/download/v0.2.0/MailX.app.tar.gz" },
      "darwin-x86_64": { "signature": "…", "url": "…" },
      "windows-x86_64": { "signature": "…", "url": "…" },
      "linux-x86_64": { "signature": "…", "url": "…" }
    }
  }
  ```

  文件名由 `scripts/release-assets.mjs` 统一改为 `MailX_<版本>_<平台><扩展名>`，平台取发布矩阵的名字（`macos-arm64`、`macos-x64`、`windows-x64`、`linux-x64`），`.sig` 跟随同名：`MailX_0.1.0-alpha.4_macos-arm64.dmg`、`MailX_0.1.0-alpha.4_windows-x64-setup.exe`、`MailX_0.1.0-alpha.4_macos-x64.app.tar.gz`。用户按操作系统选下载，架构只在名字里体现。缺任何一个平台都让工作流失败，不发出不完整的 `latest.json`。
- 更新说明取自 `notes`：一次请求同时拿到版本与说明，不访问 GitHub API。在网页上修改 Release 正文不会同步到 `notes`，正本仍是 `CHANGELOG.md`。

## 5. 网络路径

- 更新请求由桌面宿主发出，走应用自己的 HTTP 客户端（`tauri-plugin-updater` 内置），**不经过核心的账号路由，也不读取任何账号的代理设置**。账号代理只服务该账号的邮件协议连接。
- 应遵循系统代理；TUN 在网络层生效，无需处理。**对锁定版本源码的核实结论**（`tauri-plugin-updater` 2.14.0、`reqwest` 0.13.5、`hyper-util` 0.1.21，源码在 `~/.cargo/registry/src/*/` 下）：**macOS 与 Windows 默认读取系统代理，无需额外配置**。
  - `tauri-plugin-updater-2.14.0/Cargo.toml` 的默认特性含 `system-proxy`，它打开 `reqwest/system-proxy`；`desktop/Cargo.toml` 使用默认特性，未关闭。
  - `tauri-plugin-updater-2.14.0/src/updater.rs:584`、`:842`：用 `ClientBuilder::new()` 建客户端，只有显式配置 `no_proxy` / `proxy` 才改变行为（`:35-41`），本应用不配置。
  - `reqwest-0.13.5/src/async_impl/client.rs:310`：`auto_sys_proxy` 默认 `true`；`:417-418`：为真时追加 `ProxyMatcher::system()`。
  - `hyper-util-0.1.21/src/client/proxy/matcher.rs:238-247`（`from_system`）：先读环境变量（`HTTPS_PROXY` / `NO_PROXY` 等），再按平台读系统设置——macOS 走 `mac::with_system`（SystemConfiguration 的代理设置），Windows 走 `win::with_system`（注册表 Internet Settings）。
  - **Linux 只读环境变量**，不读桌面环境（GNOME / KDE）的代理设置；Linux 用户需要代理时应通过 `HTTPS_PROXY` 启动应用。这是结论，不是已验证的行为（本机未在 Linux 上运行）。
  - 宿主不使用 `core/src/net`，也不读任何账号的代理；自定义账号代理失败“不得回退直连”的规则只约束邮件协议连接，与更新请求无关。
- 只请求 `github.com` 的 Release 下载地址（含其重定向目标）；不新增其他域名。

## 6. 检查与自动更新设置

| 触发 | 规则 |
| --- | --- |
| 启动检查 | 启动约 30 秒后检查一次 |
| 定时检查 | 运行期间每 6 小时一次 |
| 手动检查 | 设置 → 关于 →“检查更新”，检查或下载正在进行时不并发启动；已有就绪包时直接打开其详情 |

启动和定时检查始终开启，与“自动更新”无关。自动检查失败静默保留已有状态，等待下一轮；手动检查失败提供原因与重试。发现版本后仍保留定时检查，以便识别被替代或撤回的版本；检查和下载不并发，退出期间不开始新的更新工作。

设置 → 关于提供“自动更新”（`general.autoUpdate`，默认 true）：

- 开启：发现可安装的新版本后后台下载并验签；完成后提醒用户重启，或在正常退出时安装。不会自动重启。
- 关闭：继续检查，只提示可用版本；用户可手动下载。关闭时停止自动发起的在途下载，并取消自动下载包的退出安装安排；已经完整下载的包仍可由用户主动重启安装。
- 用户主动下载表示同意这次更新；其下载和退出安装安排不随自动更新开关关闭而取消。
- 取消下载会暂停本次进程内该版本的自动下载；手动下载或关闭后重新开启自动更新会解除暂停。不把取消算作网络失败。
- 旧设置仅有合法 `autoCheckUpdates` 时迁移其布尔值；原 false 变为 `autoUpdate=false`，原 true 变为 true。新字段优先，缺少新旧字段时取 true；后续保存只写新字段。旧关闭选择保留为手动下载，但自动检查从此固定运行。
- macOS、Windows 与 AppImage 提供自动更新；deb / rpm 的 `canInstall=false`，开关禁用并说明手动安装渠道。

## 7. 下载、缓存与安装

### 7.1 下载与重试

自动更新开启时，从检查结果直接进入下载，不先弹“发现新版本”的通知，也不自动打开更新弹窗。用户可继续使用邮件工作台，通过标题栏入口查看进度与更新说明。关闭自动更新时，用户在弹窗点击“下载更新”才开始下载。

检查请求的总超时为 30 秒，单次完整下载的总超时为 20 分钟。自动下载的临时网络失败最多尝试三次，首个失败后等待 1 分钟，第二个失败后等待 5 分钟；普通定时检查不会重置同一目标的预算。签名校验和本地存储失败不自动重试。达到上限后保留失败状态与手动重试入口，不能无限后台重下或重复弹出错误通知。

### 7.2 完整包缓存

只有下载完整且签名有效的安装包才提交到本地缓存。缓存记录目标版本、下载地址、签名及是否由用户主动下载；部分下载不落为可用包，不支持断点续传。取消或过期下载的迟到结果不能重新提交为已同意安装的更新。

进程重新启动后，先成功获取新的发布清单，再匹配缓存身份并重新验签；匹配后可直接恢复就绪状态，无须重复下载。离线启动时不会仅凭磁盘缓存恢复可安装状态，后续成功检查才可复用。被替代、撤回或身份不匹配的包不按旧目标安装；具体缓存读写由 `desktop/src/updater/cache.rs` 管理，不触及邮件数据库。

### 7.3 安装与工作保护

下载完成后，用户可选“立即重启”，或“稍后（退出时安装）”。后者只在 `installOnQuit=true` 时显示；关闭自动更新而取消自动包的退出安装安排后，按钮只显示“稍后”。主窗口隐藏到后台不等于退出，不触发安装。

- 主动重启和正常退出安装都走[安全退出协调器](desktop-lifecycle.md#安全退出)：保存所有写信窗口和界面改动，暂停领取新的发送任务，等待在途发送结果落盘；保存失败、用户取消或退出超时则取消该轮退出与更新重启。
- 有邮件正在发送时拒绝主动重启，并在弹窗或通知操作后显示原因。用户仍可继续工作，发送完成后再重启。
- Windows 安装会运行 NSIS 安装程序并结束应用，可能短暂显示安装进度窗口；不承诺各平台安装过程完全不可见。
- 安装前持久化尝试记录。下一次仍运行旧版本且上次安装未完成时，恢复 `failed / install` 状态及该版本说明，提示手动重试或前往 GitHub；不会自动反复安装同一失败目标。重试重新准备已验证的包，随后再次由退出或主动重启执行安装。
- 定时检查与跨进程缓存核对可以发现目标撤回，但不是下载完成到安装之间的原子撤回保证；运行中已验证的包可能在下一轮成功检查前安装。当前不提供已安装程序或数据库的自动回滚。

## 8. 界面

全部文字中英两套，经过 `i18n:check`。写信窗口不显示任何更新界面，也不能触发检查、下载或安装。

### 8.1 Toast

- **需要手动下载或安装的新版本**：弹一个**不自动关闭**的 toast，标题“MailX 0.2.0 可用”，按钮“查看更新”。自动下载直接开始时不弹此通知；同一版本每次运行只提示一次，关闭后靠标题栏图标提醒。
- **手动检查**：结果有目标版本时直接打开对应弹窗，包括可用、下载中、就绪或失败，不额外弹 toast；没有新版本时在“关于”页显示“已是最新版本”。初始查询或检查响应晚到时，不覆盖已经收到的新状态事件。
- **下载完成且弹窗已关闭**：弹 toast“0.2.0 已下载”，按钮“立即重启”，同一版本每次运行只提示一次。重启被发送状态阻止或调用失败时明确显示原因；应用在后台时不主动弹出主窗口或抢焦点。
- **上次安装未完成**：显示可关闭的安装失败通知，点击“查看更新”阅读说明并重试；同一失败版本每次运行只提示一次。

### 8.2 更新弹窗

- 标题含新版本号，副标题为当前版本 → 新版本，以及发布日期（若有）。
- 正文是渲染后的更新说明（见 8.4），可滚动。
- 更新说明、当前版本与发布日期在下载中、就绪、下载或安装失败及重试时持续显示，关闭后重新打开弹窗也保留。宿主查询和状态事件平铺携带 `current`、`notes`、`date`，界面直接读取当前快照，不依赖之前收到过“发现更新”事件；只有 `notes` 为空时显示“这个版本没有提供更新说明。”。检查失败没有目标版本或说明。
- 底部按钮随阶段变化：发现时“下载更新”与“稍后”；下载中显示进度条、“后台继续”和“取消下载”；就绪时“立即重启”与按 `installOnQuit` 决定的“稍后（退出时安装）”或“稍后”；失败时显示原因与“重试”。`canInstall=false` 时只提供说明、GitHub 链接与关闭按钮。
- 提供“在 GitHub 查看”链接，用系统浏览器打开对应 Release 页面。

### 8.3 标题栏图标

- 位置：标题栏右侧 `trailing` 插槽，明暗模式按钮左边；与它**同尺寸的纯图标按钮**，悬停显示提示文字，不展开、不改变宽度，避免标题栏抖动。
- 有目标版本时才出现，失败后也保留处理入口：

  | 阶段 | 外观 | 提示文字 |
  | --- | --- | --- |
  | 发现 | 普通前景色的上箭头圆圈图标，右上角主色小圆点 | “MailX 0.2.0 可用” |
  | 下载中 | 同尺寸的圆形进度环 | “正在下载 0.2.0（45%）” |
  | 就绪 | 同一图标整体改为主色 | “重启以更新到 0.2.0” |
  | 下载或安装失败 | 同一图标改为错误色 | “更新至 0.2.0 需要处理” |

- 无闪烁、无脉冲动画；`aria-label` 与提示文字一致，包含版本号。
- 点击任一阶段都打开同一个更新弹窗。
- 不在设置齿轮上加小圆点，同一件事只有一个常驻提示。

### 8.4 更新说明的轻量 Markdown 渲染

- 自行实现，不引入 Markdown 库。支持：`#`–`###` 标题、段落、`- ` / `* ` 列表、`> ` 引用、`**粗体**`、`` `代码` ``、`[文字](https://…)` 形式的链接。其余语法按原文显示。
- 渲染为 React 元素，**不使用 `dangerouslySetInnerHTML`，原始 HTML 一律按文本显示**。
- 链接只接受 `https:`，点击后由宿主用系统浏览器打开；其他协议（含 `javascript:`、`data:`、`file:`）按纯文本显示。
- `notes` 超过 20 000 字符时截断并提示可在 GitHub 查看完整说明。
- `latest.json` 本身没有签名（签名只覆盖安装包），所以说明按不可信文本处理。

### 8.5 设置 → 关于

- 品牌与当前版本下方的“软件更新”区显示状态行：已是最新 / 正在检查 / 有可用更新（点击打开更新弹窗）/ 失败原因与重试；提供“检查更新”按钮。**不显示上次检查时间**。
- 提供“自动更新”开关，说明自动下载、退出安装、不会自动重启与关闭后仍检查的行为；不支持应用内安装时禁用并提示使用发布页或原包管理渠道。
- 关于页项目链接与更新说明共用 `MailxClient.openExternalLink`，仍通过 `updater_open_link` 的 HTTPS 校验和系统浏览器打开；界面布局见[界面设计](ui-design.md)。

## 9. 权限与安全

- 更新相关命令只允许主窗口调用，在 `desktop/src/window_access.rs` 的白名单里与现有命令同样处理；邮件正文 WebView 与写信窗口都不能调用。
- 前端不直接使用插件的 JS API，统一经宿主命令和事件，保持与其他功能一致的 IPC 校验方式；不在 capabilities 中授予 `updater:default` 给任何窗口，除非实现时证明必须且仅限主窗口。
- 下载包由插件用内置公钥验签，验签失败拒绝安装并报错。
- 日志与错误信息不包含签名、下载地址以外的敏感内容；不记录 `notes` 全文。

## 10. 验证计划

- **自动测试**：Markdown 渲染（含 HTML 注入、`javascript:` 链接、超长截断）；固定检查调度、设置迁移、自动与手动下载、关闭开关和取消、重试预算、版本替换与撤回；完整缓存验签与复用、迟到写入隔离及未完成安装恢复；前端静默下载、就绪通知去重、手动检查响应顺序、重启失败反馈和能力限制；`latest.json` 生成与窗口白名单。
- **工作流**：先用手动触发验证签名能成功、`.sig` 与 `latest.json` 生成正确，再打标签。

## 11. 服务端兼容

状态：**规划，未实现**。未来服务器 / Web 版只做“提示有新版本并显示更新说明”，不下载、不安装；界面上用 `canInstall: false` 表达这一点。

- **能力开关而不是写死安装**：宿主发给前端的更新状态带 `canInstall`（macOS、Windows、AppImage 为 `true`，deb / rpm 为 `false`）。前端所有更新界面（标题栏图标、弹窗、通知、关于页）都经 `MailxClient` 取状态，并按 `canInstall` 分支：为 `false` 时弹窗只有版本、渲染后的更新说明和“在 GitHub 查看”链接，没有下载 / 重启按钮与进度，标题栏图标只会出现“有新版本”一种状态。前端测试覆盖了 `canInstall: false` 不出现任何下载 / 安装控件。
- **检查由服务端进程发起，浏览器不检查**：避免把访问者的 IP 暴露给 GitHub（隐私），也不需要放宽页面的 CSP。检查沿用标准代理环境变量（`HTTPS_PROXY` / `NO_PROXY` 等），不使用任何邮箱账号的代理。
- **可由服务端配置关闭自动检查**：离线或自托管部署必须能关掉，不留任何出站请求。
- **读同一份 `latest.json`**：服务端只读 `version`、`notes`（可选 `pub_date`），不要求 `platforms`；版本比较与清单解析是桌面宿主里不依赖 Tauri 的纯函数（`desktop/src/updater/policy.rs`），日后可原样移到 `core` 供服务端使用，当前**没有**移动。
- **统一版本号的副作用**：只改桌面端的发布也会让服务端用户收到“有新版本”。CHANGELOG 条目可以用 `[桌面端]` / `[服务端]` 前缀，让更新说明里一眼看出与自己有无关系。
