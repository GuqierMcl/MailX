# 账号配置与凭证生命周期

状态：**账号配置、协议连接与独立收发登录诊断已有实现 / 通用 OAuth 基础已有实现，生产服务商接入仍未开放**。当前提供桌面的创建、列表、详情与修改；保存本身不联网，持久化的 `connectionStatus` 仍为 `unverified`。用户可在添加向导测试当前填写的 IMAP / SMTP 登录，也可在账号设置验证已保存配置版本的登录，诊断结果仅在当前界面使用，不代表真实邮件投递。代码位于 `core/src/accounts/`、`core/src/storage/`、`desktop/src/` 和 `frontend/src/features/accounts/`；验证方法见[验证策略](../development/validation.md)。

## 1. 对象与身份

| 对象 | 当前职责 | 关系与约束 |
| --- | --- | --- |
| `accounts` | 稳定本地 ID、显示名称与邮箱地址、提供商标识、服务商图标偏好、配置版本、邮箱来源标识 | 邮箱地址不作主键；修改密码保留账号 ID |
| `mail_connections` | 每账号一条 IMAP 和一条 SMTP 的主机、端口、TLS、登录用户名 | 各自引用认证配置；复合外键保证连接与认证配置属于同一账号 |
| `auth_profiles` | 认证类型、配置版本、凭证世代、后端凭证引用、受信端点 | 收发可共享一份或各自持有一份；不跨账号共享 |
| `network_routes` | 账号路由及其版本、可选代理认证与端点信任 | 每账号一条；代理秘密只存引用 |
| `SecretStore` | 实际密码、授权码和代理密码 | 由宿主注入；仅后端访问，不是可供 UI 读取的表 |

账号的显示邮箱地址、协议登录用户名、OAuth 授权主体与目标邮箱资源分别表达。一个用户可能授权共享邮箱，同一邮箱也可能有多个别名；不能靠字符串相等判断 OAuth 重新授权是否指向原邮箱。当前尚无别名管理或共享邮箱适配；OAuth 身份验证必须由受信服务商适配器实现，生产注册表目前为空。

创建和修改连接时，IMAP / SMTP 登录用户名分别去掉首尾空白（Unicode `White_Space` 加 `U+FEFF`，前后端一致）；为空时使用本次提交并校验后的邮箱地址，明确填写的用户名保留大小写。后端在幂等配置、邮箱来源和凭证信任比较之前完成此规范化，保存并返回实际有效的用户名，不持久化“跟随邮箱地址”状态。之后只改邮箱地址而保留已保存的用户名，不会自动改动协议登录身份；重新清空用户名再保存才会使用新的邮箱地址。空 SMTP 用户名同样解析为邮箱地址，不表示免认证，收发共享或独立密码的语义不变。

`accountId` 是本地数据归属，`mailboxSourceId` 是接收来源世代。当前更改 IMAP 主机、端口或登录用户名会分配新来源 ID；更改名称、密码、SMTP 或路由不改变来源。仅更改 TLS 不改变来源，但可能改变凭证信任。后续远端映射、游标、待写 flags 必须包含来源 ID，防止另一个服务器复用相同 UID 时污染旧缓存。

## 2. 认证与写入型秘密

当前 `AuthenticationInput` 支持密码类配置：普通密码、邮箱授权码和应用专用密码在这里都属于 `password`，QQ / Foxmail、网易 163 / 126 / yeah.net、139 已有各自的授权码引导，iCloud 与 Gmail 分别提供 Apple 和 Google 应用专用密码引导。`mode=shared` 让收发引用同一认证配置；`mode=separate` 使用独立配置。

秘密修改必须明确选择：

```ts
type SecretUpdate =
  | { action: "keep" }
  | { action: "replace"; value: string };
```

创建时必须提供新密码。修改时 `keep` 保留后端原值，`replace` 必须包含有效值；空白或掩码占位不能充当密码。由共享切为独立时，可以复制原密码到账号内新的独立配置；由独立切为共享并选择保留时，以原 IMAP 凭证为共享凭证，表单明确说明这一语义。未来 OAuth grant 不适用这种复制方式。

输入 DTO 与输出 DTO 分开。结果仅含认证配置 ID、`generation`、`passwordConfigured` 和 `trust` 等元数据，不返回密码或内部 `secretRef`。客户端也不能指定这些后端引用。Rust `SecretValue` 不实现输出序列化，Debug 脱敏并在释放时清理内存。前端仅短暂保留密码输入，提交后清空，不写入浏览器持久存储。

`revision` 是连接配置（地址、服务器、凭证、路由）的版本，用于乐观锁，同步与正文下载也以它判断工作是否过期；认证 `generation` 表达凭证版本，两者职责不同。名称、标识颜色、发件人名称和 `useProviderIcon` 属于资料，有单独的修改请求，不推进 `revision`、不修改凭证、不重启同步。`useProviderIcon` 只控制是否使用可用的服务商图标，创建省略时默认 `true`；v12 将已有账号的对应列初始化为开启，旧账号快照或 journal 缺少此字段时也按 `true` 读取。连接提交（含崩溃后重放的日志）只写连接相关的列，不会覆盖之后修改的资料，已关闭的图标偏好不会因修改连接或恢复旧日志而重新开启。当前更换密码属于配置操作，会同时推进相应版本；后续后台 token 刷新仅推进凭证版本，不应制造用户表单冲突。

QQ / Foxmail、网易 163、网易 126、网易 yeah.net 分别以 `qq`、`netease163`、`netease126`、`neteaseYeah` 保存服务商标识。三个网易入口使用各自的 `imap` / `smtp` 域名与 993 / 465 隐式 TLS 端点，向导默认完整邮箱登录名和共享客户端授权码；预设只初始化新账号，不覆盖已有手动配置、独立用户名、路由或图标偏好。免费网易入口分别只接受精确的 `163.com` / `126.com` / `yeah.net`，VIP 和企业邮箱暂用各自手动端点。授权码长度说明仅为引导，通用秘密模型不增加网易专属长度限制，也不改写输入字符。

iCloud 入口以 `icloud` 保存服务商标识，新建时精确接受 `icloud.com` / `me.com` / `mac.com`。默认接收端为 `imap.mail.me.com:993` 隐式 TLS，发送端为 `smtp.mail.me.com:587` 强制 STARTTLS，收发使用完整邮箱用户名并共享 Apple 应用专用密码；高级设置允许分别覆盖用户名与凭证。引导说明主邮箱开通、双重认证，以及主密码修改或重置会撤销全部应用专用密码；不约束秘密长度、不删除连字符。入口使用本地打包的官方 iCloud Mail 图标，复用服务商图标开关；素材来源见[图标说明](../../frontend/src/assets/providers/README.md#icloud-mail)。iCloud+ 自定义域使用手动入口；别名和历史域地址的实际兼容性仍按账号独立验收，Apple 授权登录尚未实现。此预设不增加协议特判、认证类型或数据库迁移，也不将已有手动账号自动改为 `icloud`。

Gmail 入口以 `gmail` 保存服务商标识，新建时精确接受 `gmail.com` / `googlemail.com`。接收端为 `imap.gmail.com:993`、发送端为 `smtp.gmail.com:465`，均为隐式 TLS；收发使用完整邮箱用户名并共享 Google 应用专用密码，高级设置允许分别覆盖。引导说明两步验证、粘贴时去掉分组空格、修改 Google 账号密码会撤销应用专用密码，以及安全密钥专用、高级保护和组织账号无法生成应用专用密码；秘密输入不被改写。入口使用本地打包的官方 Gmail 图标，来源见[图标说明](../../frontend/src/assets/providers/README.md#gmail)。Google 组织账号与 OAuth 登录不在此预设范围，评估见 [Gmail 接入评估](../reference/gmail-integration.md)。此预设不增加协议特判、认证类型或数据库迁移。

添加向导的“测试登录”直接验证当前内存配置，不创建临时账号、不读取或写入 SecretStore、不写数据库、不启动同步。新配置的收发及代理秘密必须由本次输入提供（`replace`）；不允许 `keep` 借用已有账号的凭据。测试沿用创建配置的规范化与字段校验、所选路由与 TLS，点击测试仅表示用户授权向当前填写端点进行登录探测。结果不会变成持久化的信任或连接状态；测试可跳过，输入变化、离开连接步骤或关闭向导即取消并丢弃旧结果。

## 3. 端点信任与路由

凭证信任绑定协议、规范化主机、端口、TLS 和登录用户名。首次输入或明确替换密码时，将当时的对应端点记录为受信范围。仅改端点并保留密码不会扩大信任：该连接返回 `needsConfirmation`。代理协议、端点或用户名变化同样不能自动继承原代理密码的信任。

已有针对已保存账号的独立连接诊断，没有单独的“信任新端点”命令；诊断不能扩大凭证信任。用户可以重新输入密码以建立新配置的信任关系。`trusted` 仅表示凭证适用于所配置的接收方，不证明服务器可达、证书有效或密码正确。连接器在认证前检查信任并验证 TLS，不能将旧凭证直接发往新端点。

支持保存 `direct`、`inherit` 与 `custom` 路由；自定义代理为 SOCKS5 或 HTTP CONNECT，目标 DNS 策略固定为 `proxy`。主机字段接受主机名或 IP，不接受带协议、路径或 userinfo 的 URL。邮件 TLS 只允许隐式 TLS 或强制 STARTTLS。

自定义路由新增 `imageProxyDns`（默认 false），对应“通过此代理加载 HTTPS 图片”。显式开启时，写入请求同时带临时 `confirmImageProxyDns=true`；该标记不出现在读取 DTO 或持久化配置中。已有许可只在代理类型、主机、端口与认证用户名均相同时保留；变化后即使输入沿用旧 true，也需新的明确确认，否则保存为关闭。前端编辑这些字段会自动关闭选择；同一身份下替换代理密码可保留许可。策略变更推进连接及路由版本，旧正文/头像绑定失效；邮件显示许可和头像开关独立管理。HTTPS 的原始域名证书仍验证，代理最终解析地址由受信出口负责，见[网络与安全](network-security.md)。

路由配置或代理凭证变化推进 `routeRevision`。`inherit` 当前解析为应用默认直连，返回 `defaultRouteRevision=1`；尚无可修改的全局代理设置。后续默认路由变化必须使继承它的连接失效，即使账号配置版本未变。实际网络连接、不回退直连和代理 DNS 行为仍须通过协议探针验证。

## 4. SQLite 与凭据库的一致性

桌面使用以产品名命名的 `MailX` user-data-dir（位于 Tauri `app_data_dir()` 的同级，见 `desktop/src/storage_location.rs`），核心接受宿主注入的目录。系统凭据 service 固定为 `MailX`。两者都不依赖应用 identifier，所以更换标识不需要迁移数据或凭据；`0.1.0-alpha.2` 之前的开发构建曾使用 `dev.mailx.desktop` 目录和同名凭据，没有自动迁移。生产数据不存仓库或当前工作目录；测试使用独立临时目录。目录内当前有 `mailx.sqlite3`、SQLite 自己管理的 WAL/SHM 文件、`mailx.lock`，以及应用偏好 `settings.json`（无法读取时保留为 `settings.json.bak`），偏好不含秘密。一个目录只由一个 `AccountService` 持有独占锁。

当前使用 `rusqlite` 单连接、外键、WAL、`synchronous=FULL` 和带 SHA-256 校验的版本化 schema。打开较新版本、校验不符或非空无版本数据库时拒绝继续，保留原数据。核心接口是同步的，宿主在阻塞工作线程执行并串行访问服务。

SQLite 与系统凭据库不能共用事务，因此使用不含秘密的 `credential_journal`：

1. 先持久化更新意图：目标配置快照、预期版本、新引用与待清理引用。
2. 向 SecretStore 写入新秘密；逐一确认新配置引用的秘密存在。
3. 在 SQLite 事务中提交配置及 journal 的已应用状态。
4. 只删除不再被有效配置引用的旧秘密，然后删除 journal。清理失败可延后，不撤销已持久化的新配置。

打开核心和执行写操作前恢复遗留 journal。全部秘密存在且预期版本匹配时补提交；存在确定缺失或版本不再匹配时，仅清理未被引用的新秘密并保留有效旧配置。凭据库锁定或暂不可用是错误，不能当作秘密不存在后执行破坏性清理。`get/list` 只读已提交配置，不触发恢复；同一进程保存失败后重新加载可能仍看到旧配置，下一次写入先恢复再检查预期版本，旧表单因此可能得到冲突。

凭据存储故障或响应丢失后，保存结果可能需要重新读取确认。创建请求的 `requestId` 用于去重：账号仍在首次 revision、规范化配置与秘密匹配时返回同一账号；参数不同、秘密不同或账号已被修改时返回 `idempotencyConflict`。修改使用 `expectedRevision`；旧版本提交返回 `conflict`，不会覆盖最新配置。

这一 journal 协议处理本地凭证提交。OAuth 运行中遇到密钥库暂时写入失败，会保留待持久化的轮换值，先重试保存再发布 access token；若进程在远端轮换后、本地确认落盘前崩溃，仍可能需要重新授权，不能承诺远端回滚。

## 5. 通用 OAuth 基础与开放边界

`core/src/auth/` 已实现授权码 + PKCE、严格 `state` / 回调校验、按账号路由的 token 交换与刷新，以及邮件协议 XOAUTH2。生产服务商列表（`core/src/providers/oauth.rs`）目前只有两个 Microsoft 条目 `microsoft-personal` 与 `microsoft-work`（规则见[服务商兼容层](provider-compatibility.md#41-microsoftcoresrcprovidersmicrosoftrs)和 [Microsoft 接入评估](../reference/microsoft-integration.md)）；核心只通过 `OAuthProvider` trait 与唯一查找函数访问服务商条目，不能使用 Gmail 或任意自定义 OAuth 端点；未知 `providerId` 在绑定监听器、读取代理凭证或打开浏览器前返回 `unsupported`。普通创建 / 修改接口仍不能接受调用方提供的 OAuth 身份作为有效授权。

授权请求与回调遵循以下与服务商无关的规则：

- **固定回调路径。** 服务商只忽略回环地址重定向的端口，所以注册项带 `redirectPath`（空表示无路径）。`redirect_uri` 由核心拼成一次文本（空路径时为 `http://127.0.0.1:{port}`，无结尾斜杠），授权请求与 token 请求逐字节复用。空路径时浏览器请求 `/`（或 `/?…`）即被接受。CSRF 防护仍由 `state` + PKCE 承担，监听器仍是一次性、仅回环、有大小与时间上限。
- **授权请求附加项。** 注册项可声明静态附加参数（如 `prompt`），不得覆盖流程自己设置的参数；也可声明使用 `login_hint`，值只来自已校验的账号邮箱。调用方的输入不会进入授权地址。申请 `openid` scope 时，每个会话生成新的 `nonce`。
- **回调页面。** 浏览器看到的是无脚本、严格 CSP 的最小 HTML 页，同一页用英文和中文说明登录已完成、可返回 MailX；回调带 `error` 时显示另一段“未能完成登录”的文字，不回显任何回调参数。
- **身份验证拿到完整 token 响应。** 部分服务商签发的 access token 客户端不应解析，身份来自 OIDC `id_token`。`IdentityVerifier` 收到 `IdentityEvidence`（access token、可选 `id_token`、请求所用 `nonce`、客户端 ID，以及用户要添加的目标邮箱 `expected_mailbox`，后者只供验证器向邮件服务器求证，不是证明）；`id_token` 只在验证期间持有，不保存、不记录。通用辅助函数解码 JWT 载荷并核对 `aud`（多受众时要求 `azp`）、`exp`（允许 2 分钟时钟偏差）、`nonce`、`iss` 与 `sub`。不验证签名：该 token 由本客户端直接经 TLS 从 token 端点取得，OIDC Core 3.1.3.7 允许以此代替签名校验；任何其他来源的 `id_token` 都不得交给该函数。
- **issuer 不是常量。** 多租户端点下 `iss` 因租户而异，所以 issuer 由验证器返回并保存在 grant 绑定中，`OAuth2Configuration.issuer` 展示的是这个已验证值。注册项匹配只比较提供商、注册标识、客户端 ID、resource 与 scopes；重新授权要求已验证的 `(issuer, subject)` 与原绑定一致。同一客户端 ID 可对应多个注册项（例如个人账号与工作账号端点不同），注册项由自己的标识区分。

开始 OAuth 授权时，核心用受信注册项的 IMAP / SMTP 服务器与登录名覆盖请求中的同名字段（`ProviderRegistration::mail_connections`），前端只需提供邮箱地址和网络路由。授权使用的路由与同步、发信相同：`inherit` 当前解析为直连（应用默认路由固定为 direct），自定义代理原样带入，失败不回退直连；将来应用默认路由可变时，授权、同步与发信三处必须一起改（`accounts::oauth::authorization_route`、`AccountService::image_route`、`draft_connection`），测试 `sign_in_uses_the_same_route_as_saved_accounts` 守住当前一致性。

授权会话由核心持有目标账号配置、路由、PKCE 秘密和 IPv4 `127.0.0.1` 临时监听器。最多八个会话、总有效期五分钟；宿主只打开受信注册生成的授权地址，网页仅收到不透明 `sessionId`。到期定时释放未消费的已完成授权结果及任务，不依赖宿主再次调用；完成和取消为一次性操作，取消会中止回调、交换与验证；只有身份适配器验证的主体和目标邮箱与预期一致，结果才可消费为账号。浏览器收到回调只表示回调已收到，不证明账号授权或创建成功。

客户端注册项与账号 grant 分开持久化，当前注册必须与受信策略完整匹配，没有开放任意客户端配置。邮件目标归一化后须核对受信 IMAP / SMTP host、port、TLS 和邮箱 / 固定登录身份策略，创建、重新授权与恢复均再次核对，不能把 bearer 交给调用方任意服务器。`targetMailboxResource` 表达经验证的邮箱目标，token 的 resource / scope 另由后端策略管理。

一份 grant 由账号内唯一凭证所有者持有，IMAP / SMTP 共享刷新协调器而不复制 refresh token。access token 按 grant、resource 和规范化 scope 集合隔离缓存，不同目标通过同一 grant 的最新 refresh token 串行轮换。并发刷新合并为同一个在途刷新，结果持久化成功后才交付新 access token；网络故障保留重试能力，明确撤销或授权失效与网络故障分别处理。IMAP / SMTP 服务器拒绝本地尚未过期的 access token（提前撤销、轮换或服务端有效期更短）时，只丢弃该缓存值，刷新后在同一次连接流程中重试一次；新 token 仍被拒时，同步记为 `signInRequired`、发信记为 `signInRequired`，界面提示用户重新登录，不自动标记整个 grant 需要重新授权，以免单一协议被关闭时连带阻塞另一协议。token 响应按 RFC 6749 §5.1 解析：缺少 `expires_in` 时按 30 分钟有效期处理；回显的 `scope` 可省略 `offline_access`、`openid`、`profile`、`email` 等元 scope，资源 scope 仍必须授予。**凭据库只保存恢复所需的最少内容：** refresh token、已授予的 scopes 与目标。access token 只在内存中，重启后的首次使用会先刷新。原因是 Windows 凭据管理器单个条目最多 2560 字节（keyring 按 UTF-16 存储，约 1280 个字符），部分服务商的 access 与 refresh token 加起来会超限。单个 refresh token 本身仍超过该上限时，写入返回存储错误而不是截断，原值保持不变，轮换值留在内存中等待重试，详见[系统凭据库](secret-vault.md)。

token 端点的 `invalid_grant`、`interaction_required`、`consent_required`、`login_required` 视为需要重新登录，其余错误保持为无效响应。服务商适配器还可以按结构化字段（协议、SMTP 回复码与增强状态码、IMAP 响应码）把邮件服务器拒绝识别为“管理员已关闭此协议”；此类拒绝记为 `providerPolicy`，不触发刷新重试，也不把 grant 标记为需要重新授权，界面提示联系管理员，不含服务器文字。

刷新存在远端轮换与本地写入之间的不可回滚边界，本地持久化失败不能保证恢复旧 refresh token。移除账号使本机协调器失效并按凭证清理流程删除本机秘密，不调用服务商撤销端点。journal 恢复提交同样使旧凭证所有者失效；存在在途写入的已退役 grant 保留持久化清理意图，补偿删除失败时由后续恢复重试，不提前确认清理完成。

`Account.authentication` 是 `kind=password | oauth2` 的联合类型。密码摘要保留 `mode` 和 `passwordConfigured`；OAuth 摘要包含受信配置、`state` 与协议级 `credentialConfigured` / `trust`，不返回 token 或秘密引用，也不把 OAuth 当作共享 / 独立密码。旧无 `kind` 的密码快照兼容读取，写出时带显式 `kind`。OAuth 连接编辑当前不可用，资料编辑与本机移除仍沿用现有流程；核心与宿主提供绑定账号及预期 revision 的专用重授权会话，核对稳定主体、邮箱、issuer、提供商与客户端注册后更新凭证 generation 和账号 revision。账号设置里的“重新登录”调用该会话，账号需要时以醒目警示呈现。

正式退出会先取消未完成授权，停止发件箱、同步、正文和预览任务，并关闭新凭证解析及新刷新准入，再等待包括已退役 grant 在内的 refresh token 持久化收尾，之后才销毁桌面异步运行时；不依赖核心 Drop 的短时等待保护凭证轮换。已收到但尚未落盘的轮换值，在明确写入失败后最多重试三次，每次串行等待真实凭据库调用结束；持续失败会返回结构化存储错误并记录固定脱敏原因后退出。整个收尾（等待后台任务结束和凭证持久化）最多 20 秒，超时同样返回存储错误并继续退出，不无限阻止退出；超时时尚未落盘的轮换值会丢失。操作系统凭据库调用本身可能阻塞，持续凭据库故障或强制终止仍可能需要重新授权，远端轮换不能回滚。

身份验证器可以向邮件服务器求证邮箱：中立函数 `imap::prove_mailbox_access` 用刚取得的 bearer 沿账号路由以 XOAUTH2 登录受信 IMAP 端点后退出，登录被拒映射为 `OAuthError::MailboxRefused`，网络、代理、TLS 与超时沿用既有 OAuth 网络错误。

服务商开放仍需审核注册、公开客户端资格、授权端点、scope / 资源、身份验证适配器和真实收发证据；受控测试不能替代公开分发验证。系统浏览器使用自身网络设置，MailX 只控制 token、身份查询和邮件连接的账号路由。

## 6. 操作与后台任务契约

当前开放创建、读取、修改和移除本机账号。停用及服务商重授权界面仍为后续设计；移除不调用服务商撤销授权，也不删除服务端邮件。

| 操作 | 配置与凭证 | 本地缓存与在途操作 |
| --- | --- | --- |
| 创建（当前） | 生成账号、来源、认证与路由 ID；完成凭证和配置持久化 | 不连接邮箱；返回尚未验证 |
| 修改密码（当前） | 保持账号和来源；推进配置与凭证版本，延后清理旧秘密 | 后续新连接使用新版本，不删除缓存 |
| 修改接收来源（当前配置部分） | 保持账号，分配新来源；旧凭证不自动获得新端点信任 | 后续创建新的远端映射；旧缓存不得冒充新来源，旧 flags 不迁移 |
| 修改路由（当前配置部分） | 推进路由版本；继承路由还依赖默认版本 | 后续停止旧连接准入并重建，按下述类型收尾 |
| 重新授权（后续） | 指定认证配置及预期版本，提供商验证授权主体与目标邮箱 | 同一邮箱保留来源；身份无法确认时不得静默接入旧数据 |
| 停用（后续） | 禁止新任务，保留配置和凭证；不等于撤销授权 | 缓存可读；停止连接，但仍保存已发生的刷新或发送结果 |
| 移除（当前） | 主窗口交互确认，核对连接 revision；同事务记录删除收据、创建请求墓碑和凭证清理意图，再删除配置 | 有 `sending` 项返回 `alreadySending` 且零删除；否则清理所有来源的缓存记录、草稿与发件记录，退休后台任务并撤销阅读权限，不删除服务端邮件 |

移除接口为 `MailxCore::remove_account` → `AccountService::remove`，输入 `accountId` 与 `expectedRevision`。重复相同移除返回同一收据；旧版本冲突，未知账号且无收据为 `notFound`。v11 的 `account_removals` 保存账号 ID、连接版本与实际删除的草稿 ID；`removed_create_requests` 保留已消费的创建请求 ID，防止迟到的创建重放重新生成账号。删除事务收集当前配置及全部待恢复 journal 的凭证引用，删除旧 journal；不能先恢复待应用的创建/连接快照。

`secret_gc` 只保存不透明凭证引用，提交后经 `SecretStore::delete` 幂等清理；凭据库不可用时本机移除仍成功并返回 `credentialsPending=true`。启动、后续账号创建/修改和移除重试会继续清理；清理前检查引用仍未被有效配置使用，已提交删除不因后续清理失败而回滚。

移除后停止账号的同步、标记写回、正文下载、空闲发信 worker 和连接诊断；账号退休记录阻止先前提交的 create/update 在延迟启动时重新注册任务。SMTP 正在执行时拒绝移除，保留原发送尝试；`unknown` 可经明确提示后移除，本地记录清除不表示消息未送达。主窗口与写信窗口收到 `mailx://account-removed`；仅实际删除的 `draftIds` 对应窗口停止自动保存并直接关闭，其它账号窗口刷新发件账号列表。

数据库中的邮件与正文引用立即不可读。原始 MIME 按内容哈希跨账号共用，仍通过下次启动的引用 GC 回收孤立文件；不在运行中调用启动 GC。共享图片缓存沿用现有淘汰策略；本操作不承诺对磁盘或备份安全擦除。应用偏好中的默认发件账号失效时沿用首个可用账号回退，静音列表残留 ID 不授予权限。

旧任务的结果不能一律丢弃。只读同步仅向匹配的来源世代提交批次与游标；未来 token 刷新按 grant 和凭证版本接管，临时停用不能丢失已经轮换的有效 token。SMTP 已接受或结果不明的事实必须写入原发送尝试，不能因为配置变更而遗失或自动重发；当前移除以拒绝 `sending` 并明确确认终态记录清除来维护此边界。

认证状态、收发连接状态和同步进度随后分别建模，由 UI 汇总。当前唯一连接状态 `unverified` 不表达“没有邮件”“认证失败”或“离线”；本地保存成功更不代表邮箱登录成功。
