# 账号配置与凭证生命周期

状态：**账号配置、协议连接与独立收发登录诊断已有实现 / OAuth 为后续设计**。当前提供桌面的创建、列表、详情与修改；保存本身不联网，持久化的 `connectionStatus` 仍为 `unverified`。用户可在账号设置验证该配置版本的 IMAP / SMTP 登录，诊断结果仅在当前界面使用，不代表真实邮件投递。代码位于 `core/src/accounts/`、`core/src/storage/`、`desktop/src/` 和 `frontend/src/features/accounts/`；验证方法见[验证策略](../development/validation.md)。

## 1. 对象与身份

| 对象 | 当前职责 | 关系与约束 |
| --- | --- | --- |
| `accounts` | 稳定本地 ID、显示名称与邮箱地址、提供商标识、服务商图标偏好、配置版本、邮箱来源标识 | 邮箱地址不作主键；修改密码保留账号 ID |
| `mail_connections` | 每账号一条 IMAP 和一条 SMTP 的主机、端口、TLS、登录用户名 | 各自引用认证配置；复合外键保证连接与认证配置属于同一账号 |
| `auth_profiles` | 认证类型、配置版本、凭证世代、后端凭证引用、受信端点 | 收发可共享一份或各自持有一份；不跨账号共享 |
| `network_routes` | 账号路由及其版本、可选代理认证与端点信任 | 每账号一条；代理秘密只存引用 |
| `SecretStore` | 实际密码、授权码和代理密码 | 由宿主注入；仅后端访问，不是可供 UI 读取的表 |

账号的显示邮箱地址、协议登录用户名、未来 OAuth 授权主体与目标邮箱资源分别表达。一个用户可能授权共享邮箱，同一邮箱也可能有多个别名；不能靠字符串相等判断 OAuth 重新授权是否指向原邮箱。当前尚无别名管理、共享邮箱适配或服务商身份验证。

创建和修改连接时，IMAP / SMTP 登录用户名分别去掉首尾空白（Unicode `White_Space` 加 `U+FEFF`，前后端一致）；为空时使用本次提交并校验后的邮箱地址，明确填写的用户名保留大小写。后端在幂等配置、邮箱来源和凭证信任比较之前完成此规范化，保存并返回实际有效的用户名，不持久化“跟随邮箱地址”状态。之后只改邮箱地址而保留已保存的用户名，不会自动改动协议登录身份；重新清空用户名再保存才会使用新的邮箱地址。空 SMTP 用户名同样解析为邮箱地址，不表示免认证，收发共享或独立密码的语义不变。

`accountId` 是本地数据归属，`mailboxSourceId` 是接收来源世代。当前更改 IMAP 主机、端口或登录用户名会分配新来源 ID；更改名称、密码、SMTP 或路由不改变来源。仅更改 TLS 不改变来源，但可能改变凭证信任。后续远端映射、游标、待写 flags 必须包含来源 ID，防止另一个服务器复用相同 UID 时污染旧缓存。

## 2. 认证与写入型秘密

当前 `AuthenticationInput` 支持密码类配置：普通密码、邮箱授权码和应用专用密码在这里都属于 `password`，产品引导可随后按服务商区分。`mode=shared` 让收发引用同一认证配置；`mode=separate` 使用独立配置。

秘密修改必须明确选择：

```ts
type SecretUpdate =
  | { action: "keep" }
  | { action: "replace"; value: string };
```

创建时必须提供新密码。修改时 `keep` 保留后端原值，`replace` 必须包含有效值；空白或掩码占位不能充当密码。由共享切为独立时，可以复制原密码到账号内新的独立配置；由独立切为共享并选择保留时，以原 IMAP 凭证为共享凭证，表单明确说明这一语义。未来 OAuth grant 不适用这种复制方式。

输入 DTO 与输出 DTO 分开。结果仅含认证配置 ID、`generation`、`passwordConfigured` 和 `trust` 等元数据，不返回密码或内部 `secretRef`。客户端也不能指定这些后端引用。Rust `SecretValue` 不实现输出序列化，Debug 脱敏并在释放时清理内存。前端仅短暂保留密码输入，提交后清空，不写入浏览器持久存储。

`revision` 是连接配置（地址、服务器、凭证、路由）的版本，用于乐观锁，同步与正文下载也以它判断工作是否过期；认证 `generation` 表达凭证版本，两者职责不同。名称、标识颜色、发件人名称和 `useProviderIcon` 属于资料，有单独的修改请求，不推进 `revision`、不修改凭证、不重启同步。`useProviderIcon` 只控制是否使用可用的服务商图标，创建省略时默认 `true`；v12 将已有账号的对应列初始化为开启，旧账号快照或 journal 缺少此字段时也按 `true` 读取。连接提交（含崩溃后重放的日志）只写连接相关的列，不会覆盖之后修改的资料，已关闭的图标偏好不会因修改连接或恢复旧日志而重新开启。当前更换密码属于配置操作，会同时推进相应版本；后续后台 token 刷新仅推进凭证版本，不应制造用户表单冲突。

## 3. 端点信任与路由

凭证信任绑定协议、规范化主机、端口、TLS 和登录用户名。首次输入或明确替换密码时，将当时的对应端点记录为受信范围。仅改端点并保留密码不会扩大信任：该连接返回 `needsConfirmation`。代理协议、端点或用户名变化同样不能自动继承原代理密码的信任。

已有针对已保存账号的独立连接诊断，没有单独的“信任新端点”命令；诊断不能扩大凭证信任。用户可以重新输入密码以建立新配置的信任关系。`trusted` 仅表示凭证适用于所配置的接收方，不证明服务器可达、证书有效或密码正确。连接器在认证前检查信任并验证 TLS，不能将旧凭证直接发往新端点。

支持保存 `direct`、`inherit` 与 `custom` 路由；自定义代理为 SOCKS5 或 HTTP CONNECT，目标 DNS 策略固定为 `proxy`。主机字段接受主机名或 IP，不接受带协议、路径或 userinfo 的 URL。邮件 TLS 只允许隐式 TLS 或强制 STARTTLS。

自定义路由新增 `imageProxyDns`（默认 false），对应“通过此代理加载 HTTPS 图片”。显式开启时，写入请求同时带临时 `confirmImageProxyDns=true`；该标记不出现在读取 DTO 或持久化配置中。已有许可只在代理类型、主机、端口与认证用户名均相同时保留；变化后即使输入沿用旧 true，也需新的明确确认，否则保存为关闭。前端编辑这些字段会自动关闭选择；同一身份下替换代理密码可保留许可。策略变更推进连接及路由版本，旧正文/头像绑定失效；邮件显示许可和头像开关独立管理。HTTPS 的原始域名证书仍验证，代理最终解析地址由受信出口负责，见[网络与安全](network-security.md)。

路由配置或代理凭证变化推进 `routeRevision`。`inherit` 当前解析为应用默认直连，返回 `defaultRouteRevision=1`；尚无可修改的全局代理设置。后续默认路由变化必须使继承它的连接失效，即使账号配置版本未变。实际网络连接、不回退直连和代理 DNS 行为仍须通过协议探针验证。

## 4. SQLite 与凭据库的一致性

桌面使用以产品名命名的 `MailX` user-data-dir（位于 Tauri `app_data_dir()` 的同级，见 `desktop/src/storage_location.rs`），核心接受宿主注入的目录。系统凭据 service 固定为 `MailX`。两者都不依赖应用 identifier，所以更换标识不需要迁移数据或凭据；`0.1.0-alpha.2` 之前的开发构建曾使用 `dev.mailx.desktop` 目录和同名凭据，没有自动迁移。生产数据不存仓库或当前工作目录；测试使用独立临时目录。目录内当前有 `mailx.sqlite3`、SQLite 自己管理的 WAL/SHM 文件、`mailx.lock`，以及应用偏好 `settings.json`（无法读取时保留为 `settings.json.bak`），偏好不含秘密。一个目录只由一个 `AccountService` 持有独占锁。

当前使用 `rusqlite` 单连接、外键、WAL、`synchronous=FULL` 和带 SHA-256 校验的版本化 schema。打开较新版本、校验不符或非空无版本数据库时拒绝继续，保留原数据。核心接口是同步的，宿主在阻塞工作线程执行并串行访问服务。

SQLite 与系统凭据库不能共用事务，因此使用不含秘密的 `credential_journal`：

1. 先持久化更新意图：目标配置快照、预期版本、新引用与待清理引用。
2. 向 SecretStore 写入新秘密；逐一确认新配置引用的秘密存在。
3. 在 SQLite 事务中提交配置及 journal 的已应用状态。
4. 只删除不再被有效配置引用的旧秘密，然后删除 journal。清理失败可延后，不撤销已持久化的新配置。

打开核心和执行写操作前恢复遗留 journal。全部秘密存在且预期版本匹配时补提交；存在确定缺失或版本不再匹配时，仅清理未被引用的新秘密并保留有效旧配置。凭据库锁定或暂不可用是错误，不能当作秘密不存在后执行破坏性清理。`get/list` 只读已提交配置，不触发恢复；同一进程保存失败后重新加载可能仍看到旧配置，下一次写入先恢复再检查预期版本，旧表单因此可能得到冲突。

凭据存储故障或响应丢失后，保存结果可能需要重新读取确认。创建请求的 `requestId` 用于去重：账号仍在首次 revision、规范化配置与秘密匹配时返回同一账号；参数不同、秘密不同或账号已被修改时返回 `idempotencyConflict`。修改使用 `expectedRevision`；旧版本提交返回 `conflict`，不会覆盖最新配置。

这一协议处理本地密码保存，不代表已解决远端 OAuth refresh token 轮换的全部风险。远端已轮换而本地未能持久化时，未来可能只能要求重新授权，不能承诺必定回滚。

## 5. OAuth 扩展边界

`OAuth2Configuration` 当前只预留 `providerId`、`issuer`、`clientRegistrationId`、`authorizationSubject` 和 `targetMailboxResource`；`oauth2` 输入返回 `unsupported`，不保存可用授权，也不发起网络请求。实际 OAuth 上线仍需增量迁移与提供商适配。

后续设计遵循以下规则：

- 授权码 + PKCE、设备授权等取得授权的流程，与 XOAUTH2 / OAUTHBEARER 等邮件协议机制分别建模。
- 提供商验证授权主体及目标邮箱资源；重新授权需指定 `authProfileId` 和预期版本，不能只传账号 ID 后任意替换身份。
- 一份 grant 有唯一凭证所有者；刷新按实际 grant 协调，不把同一个 refresh token 复制成多个独立刷新者。跨账号共享授权另行设计。
- token 按资源、权限和过期时间管理，校验实际获授 scope。网络失败与明确撤销分别处理，不能都要求重新登录。
- token 交换和刷新走账号路由；系统浏览器仍使用自身的网络设置。提供商端点变更属于凭证信任变更。

## 6. 操作与后台任务契约

当前开放创建、读取、修改和移除本机账号。停用、重新授权和 OAuth 刷新收尾仍为后续设计；移除不调用服务商撤销授权，也不删除服务端邮件。

| 操作 | 配置与凭证 | 本地缓存与在途操作 |
| --- | --- | --- |
| 创建（当前） | 生成账号、来源、认证与路由 ID；完成凭证和配置持久化 | 不连接邮箱；返回尚未验证 |
| 修改密码（当前） | 保持账号和来源；推进配置与凭证版本，延后清理旧秘密 | 后续新连接使用新版本，不删除缓存 |
| 修改接收来源（当前配置部分） | 保持账号，分配新来源；旧凭证不自动获得新端点信任 | 后续创建新的远端映射；旧缓存不得冒充新来源，旧 flags 不迁移 |
| 修改路由（当前配置部分） | 推进路由版本；继承路由还依赖默认版本 | 后续停止旧连接准入并重建，按下述类型收尾 |
| 重新授权（后续） | 指定认证配置及预期版本，提供商验证授权主体与目标邮箱 | 同一邮箱保留来源；身份无法确认时不得静默接入旧数据 |
| 停用（后续） | 禁止新任务，保留配置和凭证；不等于撤销授权 | 缓存可读；停止连接，但仍保存已发生的刷新或发送结果 |
| 移除（当前） | 主窗口交互确认，核对连接 revision；同事务记录删除收据、创建请求墓碑和凭证清理意图，再删除配置 | 有 `sending` 项返回 `alreadySending` 且零删除；否则清理所有来源的缓存记录、草稿与发件记录，退休后台任务并撤销阅读权限，不删除服务端邮件 |

移除接口为 `MailxCore::remove_account` → `AccountService::remove`，输入 `accountId` 与 `expectedRevision`。重复相同移除返回同一收据；旧版本冲突，未知账号且无收据为 `notFound`。v11 的 `account_removals` 保存账号 ID、连接版本与实际删除的草稿 ID；`removed_create_requests` 保留已消费的创建请求 ID，防止迟到的创建重放重新生成账号。删除事务收集当前配置及全部待恢复 journal 的凭证引用，删除旧 journal；不能先恢复待应用的创建/连接快照。

`secret_gc` 只保存不透明凭证引用，提交后经 `SecretStore::delete` 幂等清理；凭据库不可用时本机移除仍成功并返回 `credentialsPending=true`。启动、后续账号创建/修改和移除重试会继续清理；清理前检查引用仍未被有效配置使用，已提交删除不因后续清理失败而回滚。

移除后停止账号的同步、标记写回、正文下载、空闲发信 worker 和连接诊断；账号退休记录阻止先前提交的 create/update 在延迟启动时重新注册任务。SMTP 正在执行时拒绝移除，保留原发送尝试；`unknown` 可经明确提示后移除，本地记录清除不表示消息未送达。主窗口与写信窗口收到 `mailx://account-removed`；仅实际删除的 `draftIds` 对应窗口停止自动保存并直接关闭，其它账号窗口刷新发件账号列表。

数据库中的邮件与正文引用立即不可读。原始 MIME 按内容哈希跨账号共用，仍通过下次启动的引用 GC 回收孤立文件；不在运行中调用启动 GC。共享图片缓存沿用现有淘汰策略；本操作不承诺对磁盘或备份安全擦除。应用偏好中的默认发件账号失效时沿用首个可用账号回退，静音列表残留 ID 不授予权限。

旧任务的结果不能一律丢弃。只读同步仅向匹配的来源世代提交批次与游标；未来 token 刷新按 grant 和凭证版本接管，临时停用不能丢失已经轮换的有效 token。SMTP 已接受或结果不明的事实必须写入原发送尝试，不能因为配置变更而遗失或自动重发；当前移除以拒绝 `sending` 并明确确认终态记录清除来维护此边界。

认证状态、收发连接状态和同步进度随后分别建模，由 UI 汇总。当前唯一连接状态 `unverified` 不表达“没有邮件”“认证失败”或“离线”；本地保存成功更不代表邮箱登录成功。
