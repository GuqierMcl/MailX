# 账号、同步与发信

状态：**文件夹与邮件头同步、按需正文、IMAP IDLE、标记 / 删除写回、本机归档和 SMTP 发送已有实现**。IMAP 与 SMTP 均经账号路由；平台与服务商证据见[验证记录](../development/validation.md)。账号配置详见[账号配置](account-configuration.md)，状态与参数可随验证修订。

## 已实现：文件夹同步

- `MailxCore` 为每个账号运行一个 tokio 后台任务：读取同步计划 → 不持存储锁完成 IMAP 登录、`ID`（服务器提供时）和完整 `LIST "" *` → 短事务写入目录。目录首次及每 10 分钟到期后刷新；只有匹配 tagged OK 的完整结果可触发删除对账，逐目录 STATUS 失败不影响目录发现。
- 凭证只用于其确认时的端点；服务器、TLS、用户名或代理变化后报告 `credentialUntrusted`，不会把旧密码发往新端点。
- 登录被拒、凭证缺失 / 不受信任、服务器不支持 STARTTLS 时不自动重试，直到账号被修改；网络、代理、TLS 与超时按 §2 退避重试。明确的服务商安全策略拒绝（`providerPolicy`）也停止头部同步与标记写回，保留缓存和待写队列；处理后手动同步或修改连接可建立新任务世代，前后台切换及新增标记不解除暂停，旧任务迟到结果不能阻止新世代。
- 角色识别顺序：INBOX 名称 → SPECIAL-USE 属性 → 顶层（或 INBOX 下）的常见名称；每个角色只分配给一个文件夹。层级由服务器分隔符得出，`INBOX.Sent` 这类系统文件夹与收件箱并列显示。
- 文件夹按账号的 `mailboxSourceId` 隔离：切换服务器后旧列表不再显示，旧服务器迟到的结果会被丢弃；同一服务器名称在多次同步间保持本地 ID。
- 尚未实现：OBJECTID 改名识别、NOTIFY；服务商矩阵尚未验证。

## 已实现：所有可选文件夹邮件头同步

- `SyncManager` 按账号调度，账号间并发、暂不设全局账号并发上限；每账号正常使用一条连接，收件箱先、其余目录按稳定顺序串行处理。每轮结束后的等待时间由应用是否在前台决定（见下一条），文件夹多或网络慢时会增加轮询总周期。每目录先 STATUS 更新计数；若 UIDVALIDITY、UIDNEXT、MESSAGES、UNSEEN 均与该目录上次完整处理时相同，且距上次完整处理不足 10 分钟，则跳过 EXAMINE、SEARCH 与标志对账（服务器不返回 UIDNEXT 时从不跳过）。每 10 分钟的完整处理补上 STATUS 看不到的变化，例如 `\Flagged`。STATUS 快照只保存在同步任务内存中，任务启动或某目录本轮失败后，下一轮总是完整处理。
- **自适应的轮询间隔**：宿主通过 `MailxCore::set_activity(Activity)` 告诉核心窗口是否在前台，核心据此决定每轮结束后的等待（`sync/cadence.rs`，纯函数，不碰时钟和网络）。前台每 20 秒一轮；后台从 3 分钟起，连续两轮没有任何变化后逐轮翻倍，上限 10 分钟，某一轮发现了新邮件或任何读者可见的变化，就回到 3 分钟。回到前台立即开始一轮并清零“连续安静”计数，但距上一轮结束不足 10 秒时等满 10 秒，避免来回切换窗口变成连续登录；手动刷新不受这个间隔限制。已经在等待中的一轮在前后台切换时重新按新规则计算截止时间（仍从上一轮结束算起）。失败仍走各自的指数退避，与前后台无关。判断“有没有变化”看的是账号的文件夹列表修订号与各文件夹数据修订号之和是否在这一轮里增加。
- **锁屏和休眠**：锁屏时窗口失去焦点，算后台，继续按慢节奏检查；休眠时系统不执行同步，唤醒后到期的轮询恢复。IDLE 另有睡眠检测与主动重连，见下节；不提供睡眠中收信。
- 同步 LIST 中全部可选文件夹，包括已发送、草稿、归档、垃圾邮件、回收站和自定义目录；不可选容器仅显示层级。使用 `EXAMINE` 和 `BODY.PEEK[HEADER.FIELDS (DATE SUBJECT FROM TO CC REPLY-TO MESSAGE-ID CONTENT-TYPE CONTENT-DISPOSITION IN-REPLY-TO REFERENCES)]`（另加端点兼容策略声明的字段），同时读取 UID、FLAGS、INTERNALDATE、RFC822.SIZE 与 BODYSTRUCTURE；不读取正文或附件内容，不发送 SELECT、STORE 或其他写命令。
- STATUS 以 tagged OK 完成但没有可匹配数据（例如服务器把中文目录名返回成 `???`），或缺少请求的计数时，改用原始目录名执行只读 EXAMINE，从 EXISTS 取得总数，再用完整的 `UID SEARCH UNSEEN` 结果计算全目录未读数；不使用无法匹配的 STATUS 行，也不把 EXAMINE 的 `[UNSEEN n]` 序号当作计数。完整处理复用这次 EXAMINE；取得的 UIDVALIDITY、UIDNEXT 与计数仍参与上述快速跳过判断。此路径只接受命令完整成功，不对拒绝或损坏连接降级。
- 明确消费完成的单目录命令拒绝只使该目录本轮失败，保留缓存并继续其他目录；STATUS 及其兼容路径失败时保留上次计数，新发现目录显示计数未知。超时、EOF、BYE 或不完整响应使会话失效，丢弃旧连接并退避重连，从下一未处理目录继续，避免一直卡在首个坏目录。认证 / 信任失败及明确的服务商安全策略拒绝仍停止整个账号。
- `mail-parser` 启用 `full_encoding`，解码 UTF-8、GBK、GB2312、GB18030 等编码的主题和地址显示名。收件时间依次取 INTERNALDATE、Date 头和同步时间，保存为 UTC 毫秒时间；缺失或损坏字段按空值兜底，不记录原始邮件头。
- 头部同步读取 `In-Reply-To` 与 `References` 并存入 `messages`（迁移 0027），写入批次之后立即尝试归并会话（`conversation_id`，账号内）：先按 `References` / `In-Reply-To`（取最近 20 个引用；命中被引用的邮件，也命中引用了同一根邮件的兄弟邮件，根邮件未缓存时同样成立），再对没有任何线索头部的邮件做主题兜底，兜底只接受 30 天内、同一对象之间、至少一封己方发出且一封对方发来的双向往来（≤20 封）；单向通知即使主题相同也不成会话。归并失败只留下无会话的邮件，不影响同步。会话规则变化时递增 `threading_version`（迁移 0028 清空旧值），后台按批（每批 200 封、批间释放服务锁、先旧后新）对旧版本的邮件重新归并，出错不影响使用，下次启动继续。已缓存邮件通过 `policy_key` 升级（`default:v2`、`qq:v2`）逐文件夹补抓这两个头部，见[邮箱服务商兼容层](provider-compatibility.md#33-存储与恢复)。
- 附件标志来自 BODYSTRUCTURE：附件 disposition，或 multipart 下既非 text / multipart 且非 inline 的叶子部分，视为有附件；纯文本、HTML、multipart/alternative 中的正文部分不因此成为附件。头部同步本身不建立附件记录或正文预览。
- 邮件与游标存入 `messages` / `folder_sync_cursors`，经 `emails_list` / `emails_get` 提供本地只读查询。任意目录可搜索、筛选未读和分页；统一收件箱只汇总 inbox 角色。逐目录提交后更新数据版本，前端刷新受影响的查询，无关目录结果不会打断当前分页和选中。
- 每目录状态区分等待、同步、成功和失败；数量受限通过 coverage 单独表示，不能将未完整覆盖一律显示为“正在同步”。缺主题显示“（无主题）”，缺摘要不留摘要行，详情按需下载正文，成功后更新纯文本摘要。
- 新增 / 删除目录在下一次完整目录刷新后体现；无 OBJECTID 时改名按旧目录消失、新目录出现处理。目录变为不可选后隐藏旧消息；外部移动按源目录删除、目标新增对账，按各自窗口最终收敛，不保证跨目录瞬时一致。
- 尚未实现：同步窗口之外的历史回填、同步窗口设置、CONDSTORE / QRESYNC 与 Gmail 标签语义。附件保存、标记写回、IDLE 和发信已有实现，分别见本文后续章节及[写信与发送](sending.md)。

## 已实现：按需正文

- 打开缺少正文的邮件时，独立短连接按账号路由登录，EXAMINE 所在目录并核对 UIDVALIDITY，再用 `UID FETCH <uid> (UID BODY.PEEK[])` 下载完整 MIME，不改变已读标记。已缓存内容只读本地。
- 同一邮件的请求共享结果；每账号正文串行，与头部同步分开。来源、账号 revision、可选目录、UIDVALIDITY、present 与任务代际在开始、提交和读取时验证；账号修改会取消旧任务。网络、MIME 解析和 blob I/O 不持全局服务锁。
- 已知 RFC822.SIZE 超过 100 MiB 时不发 FETCH；接收层在超限 literal 预分配前拒绝，累计 payload 同样受限。正文 FETCH 预算为 `max(30s, size / 64 KiB/s)`，最多 10 分钟；未知大小用 10 分钟硬上限，其余命令仍为 30 秒。
- 下载完成后净化并缓存正文、附件元数据和摘要，HTML 只经隔离协议提供。失败持久化受控原因码（包括 `providerPolicy`），界面保留手动重试；升级客户端不会自动重试此前失败的正文。缓存、图片与隔离边界见[存储设计](storage-search.md)和[网络安全](network-security.md)。

## 已实现：列表预览

- 列表预览与正文下载是两条独立通道。前端把当前可见行的 id 交给 `emails_request_previews`，核心为每个账号打开一条独立短连接（同 `open_body_session`：账号路由、TLS、认证和接收预算完全一致，代理失败不回退直连），EXAMINE 目录并核对 UIDVALIDITY，每个目录每批至多 50 个 UID 发一条 `UID FETCH <set> (UID BODY.PEEK[HEADER.FIELDS (CONTENT-TYPE CONTENT-TRANSFER-ENCODING MIME-VERSION)] BODY.PEEK[TEXT]<0.16384>)`。PEEK 不改变已读标记。
- 部分范围不可信：QQ 邮箱等服务器会忽略 `<0.16384>` 并返回完整 TEXT。核心因此接受不超过单封上限 `PREVIEW_FALLBACK_BYTES`（1 MiB）的 TEXT，在本地截取前 16 KiB 再提取；超过上限的邮件记为 failed，预览保持空白，直到用户打开邮件下载完整正文。
- 按大小分批：响应预算由本批自身计算——每封取 min(存储的 RFC822.SIZE, 1 MiB)（大小未知按 1 MiB）加头部余量，再加少量协议余量。`size` 超过 1 MiB 的邮件单独成批，不与其他邮件同批；其余邮件同批时，各封 min(size, 1 MiB) 之和（未知按 1 MiB）不超过每批字节上限 `PREVIEW_BATCH_BYTES`（4 MiB），放不下的留在队列里顺延到后面的批次；服务器若遵守范围则代价很小，若忽略则只让这一封 failed（单封批次 `TooLarge` 只记该封为 failed）。若多封批次仍 `TooLarge`（存储的大小有误），逐封单独重试，只有超限的那封 failed，其余照常。
- 抓回的头字段与截断正文拼成临时 MIME 交给 mail-parser：优先第一个 text/plain，否则 text/html 走与完整渲染相同的净化与纯文本转换，再折叠空白并截断到与正文下载一致的 200 个字符。base64 / quoted-printable 在中途截断时由解析器丢弃不完整的尾部，未结束的 multipart 在解析前补上结束分隔符。
- 结果：有文字 → `previewState=ready`；解析成功但没有文字（只有样式、空正文）→ `failed`；网络、认证、代理、超时或服务器错误 → 不写库，行保持 `missing`，该账号尚未开始的队列一并放弃，避免对不通的服务器逐批重试。UIDVALIDITY 已变或邮件已不在服务器上的行同样保持 missing，等头部同步处理。
- 每账号一个“想要的”待处理集合，**最新请求取代尚未开始的旧集合**；运行中的批次会完成。写库时再次核对来源、账号 revision、UIDVALIDITY 与 present，且只更新 `body_state != 'ready'` 的行，完整正文的摘要永远不会被部分抓取覆盖；`body_commit` 总是把 `preview_state` 置为 ready。完成后以 `CoreEvent::Previews` 推送 `{ emailId, preview, previewState }`。
- 预览有自己的闸门，不取正文通道的信号量，所以用户打开邮件时的正文下载不会排在预览之后。读取通道分别为头部同步、按需正文与预览；写回与 IDLE 还会使用独立连接，见下节。账号停用、缺少凭证或连接设置变化时不启动或取消预览任务。

## 已实现：IMAP IDLE

目的：收件箱新邮件在数秒内被发现，而不是等下一轮轮询。IDLE 只负责“叫醒”：监视任务检测到变化后唤醒该账号已有的同步工作线程，真正的同步、对账、通知与存储不变；监视任务本身不读写存储。因此 IDLE 不可用、断开或被关闭时，只是延迟回到原来的轮询，不影响正确性。

- 每个账号一个监视任务（`core/src/sync/idle.rs`），与同步工作线程同生命周期：账号停用或删除、凭证、路由、邮箱来源变化、核心关闭时一并停止或重启，关闭时先发 `DONE` 与 `LOGOUT`（最多等几秒，超时则中止）。连接经账号路由建立，代理失败不直连。
- 连接后要求服务器声明 `IDLE`，随后 `EXAMINE INBOX`（只读，与同步一致）并进入 IDLE。只把 `EXISTS`、`EXPUNGE`、`FETCH`、`RECENT`、`VANISHED` 视为变化，`* OK Still here` 等其他推送忽略。IDLE 自己的收发不经 1 MiB 的累计接收预算（该预算只用于按需正文这类一次性连接）。
- 防抖 1.5 秒：窗口自第一次变化起计，不顺延，一阵连发只唤醒同步一次，长突发的延迟也有上限。
- 每 10 分钟（以本机计时，不被服务器保活重置）发 `DONE` 再重新 IDLE，避开服务器约 30 分钟的空闲断开，也刷新网关与代理的连接状态。
- 每次成功（重新）连接后额外唤醒同步一次，补上断线期间可能漏掉的邮件。
- 断开或出错：按指数退避重连，沿用写回队列的退避；连接维持不足 1 分钟不重置退避。变化推送超过每分钟 60 次视为异常，断开并退避。
- 服务商拒绝（`ProviderPolicy`）、认证失败或凭证缺失：本次运行内停用该账号的 IDLE，不再重连，靠轮询兜底。服务器不声明 `IDLE`：状态为 `Unsupported`，不重试。账号配置重启后重新尝试。
- 健康状态 `Starting` / `Live` / `Reconnecting` / `Unsupported` / `Disabled` 存在核心内存里，不对外暴露、不持久化。仅 `Live` 时前台轮询间隔由 20 秒拉长到 3 分钟（其他文件夹仍靠轮询）；后台 3–10 分钟不变；非 `Live` 时间隔与此前完全一致。状态变化会叫醒同步线程重算等待，`Live` 掉线后不会留在 3 分钟的等待里。
- 睡眠检测：核心里一个 30 秒的定时器比较墙钟与单调时钟的增量，墙钟多走超过约 60 秒视为机器睡过：立即让所有 IDLE 监视任务重连，并唤醒所有同步线程。单调时钟在睡眠期间是否停走因平台而异（macOS / Linux 按预期；Windows 未验证），检测不到时仍靠服务器断线或 TCP 超时后的普通重连。

已知限制：

- 只监视 INBOX；其他文件夹仍靠轮询（前台 3 分钟）。
- 每个账号多一条常驻连接，现在是头部同步 1 + 按需正文 1 + 预览 1 + 写回 1 + IDLE 1。QQ、163、139 等服务商的并发连接上限未验证，可能触发拒绝；拒绝会按上文停用该账号的 IDLE。
- 代理或网关可能静默切断空闲 TCP，此时要等 10 分钟的重新 IDLE 或系统层面的超时才发现；睡眠检测与手动刷新能缓解。
- 没有用户可见的开关，也没有界面上的 IDLE 状态。
- 新邮件到达、睡眠唤醒、代理、切网及服务商连接限制的证据见[验证记录](../development/validation.md)第 25 节。

## 1. 账号生命周期

账号服务提供创建、查看、修改、移除及独立连接验证。IMAP 与 SMTP 可使用不同主机、用户名与凭证；保存成功不代表连接成功，配置状态仍为 `connectionStatus=unverified`，连接验证结果单独返回。实际配置模型、邮箱来源世代、端点信任及移除契约见[账号配置](account-configuration.md)。

当前用独立的 `AccountSyncState` 表达后台收件同步状态；连接验证分别报告 IMAP 与 SMTP 结果，发送队列另有每次尝试的状态。网络不通与授权被撤销分别处理；一个连接失败不禁止读取本地缓存。保存前与已保存账号的连接测试均已实现，不发送测试邮件。

停用应阻止新任务、关闭连接并按操作类型收尾；删除需显式处理缓存、授权与在途任务，不删除服务端邮件。不能把“停止调度”理解为丢弃已轮换的凭证或已经发生的 SMTP 结果。
统一的 `canRead`、`canSend`、`canSetSeen`、`canSetFlagged`、`supportsIdle` 能力模型仍为后续候选；当前各协议任务依据服务器声明和实际响应处理能力。预设只是建议配置，不能替代实际探测。

## 2. 连接与任务预算

当前账号之间并发，暂不设全局账号并发上限。每账号头部同步使用一条 IMAP 会话，目录与批次串行；按需正文、列表预览、写回与 IDLE 各有独立通道，因此正常邮件任务可同时使用五条 IMAP 连接。显式连接验证还会建立临时连接。一个账号失败不阻塞其他账号；服务商连接限制仍需实测，尚无统一连接池调度。

普通 IMAP 命令为 30 秒超时，按需正文使用随大小调整的预算，IDLE 单独维护重连与保活周期。认证、凭证信任与明确服务商策略拒绝会停止相应自动重试；网络故障按各任务的退避规则处理。SMTP 的会话、串行发送、重试和不确定结果规则见[写信与发送设计](sending.md)，不套用只读任务的重试策略。

## 3. 首次同步与增量同步

当前同步窗口在首次建立游标或 UIDVALIDITY 变化时确定：`window_start` 为当日 UTC 日期减 30 天，之后沿用该起点，**不是每天滚动的最近 30 天**。IMAP `SEARCH SINCE` 使用服务器日期语义，时区边界可能相差一天。

1. 按账号路由登录，必要时刷新文件夹目录；选择全部可选文件夹，收件箱优先，其余稳定遍历。优先用 `STATUS` 更新总数和未读数，再用 `EXAMINE` 获取 UIDVALIDITY；STATUS 完整成功但数据不可用时，改用 `EXAMINE` + `UID SEARCH UNSEEN` 取得计数并复用已打开的目录。缺少 UIDVALIDITY 时本轮失败，不写入邮件；兼容路径缺少 EXISTS 或完整未读搜索结果时不覆盖计数。
2. 没有游标或 UIDVALIDITY 改变时，在短事务内将旧代际的 `present` 邮件标记为 `stale`，重建游标，设置固定窗口起点、`highest_uid=0`、`backfill_done=0`。旧代际不再对查询可见。
3. 每轮重新执行完整 `UID SEARCH SINCE <window_start>`，对所有匹配 UID 排序，选取最大的 1,000 个。超过上限时设置 `window_capped=1`；此上限是每轮选择范围，不是本地总记录上限。
4. 只抓取选定集合中尚无当前 `present` 记录的 UID，按新到旧每批最多 200 封。每批邮件与 `highest_uid` 在同一事务提交，重复写入保留本地 ID；选定集合头部全部取得，且删除与 flags 对账成功后，才标记 `backfill_done=1`。取消、断线或写库失败保留已提交批次，下一轮按实际缓存继续，最大 UID 不代表其之前都已缓存。
5. 只有完整 SEARCH 成功后，才把当前代际中 `received_at >= window_start`、却不在**完整搜索结果**中的本地 `present` UID 标记为 `deleted`。不得拿截取后的 1,000 个 UID 判断删除；窗口外缓存不对账、不自动清理。
6. 对选定集合中已有的 UID 重新读取 FLAGS，每条命令最多 500 个 UID，更新已读、星标和原始 flags；不修改服务器标志。已缓存但后来退出最新 1,000 个集合的邮件仍保留，头部总量可超过 1,000；这些记录不再参与本轮 flags 刷新。
7. 邮件批次、flags、删除与既有游标推进事务核对账号当前 `mailboxSourceId`、文件夹归属与 UIDVALIDITY，任一不匹配就拒绝写入迟到结果。文件夹计数只核对来源与归属，代际初始化事务负责建立或切换 UIDVALIDITY。每目录提交后发布数据版本，整轮全部成功才更新账号成功时间；部分失败保留目录失败信息。worker generation 和账号 revision 在阻塞任务实际取得存储锁后再次校验，已取消任务不能靠排队中的写操作恢复旧结果。

UID 只在文件夹及其 `UIDVALIDITY` 世代内有效，不能拿序号或邮件头 `Message-ID` 当唯一远端主键。[RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html)。MailX 使用 `(accountId, mailboxSourceId, folderId, uidValidity, uid)` 表达远端位置，本地 `emailId` 是独立 UUID；更换接收来源后建立新来源，即使远端使用相同文件夹名和 UID，也不复用旧映射。

服务端 UID 不连续是正常情况；搜索得到明确的 UID 集合后再抓取，不用 `UIDNEXT - 1000` 推算数量，也不将 UIDNEXT 当作本地已提交进度。IDLE 已用于唤醒收件同步，CONDSTORE / QRESYNC 仍可在后续优化完整搜索和 flags 获取成本。

<a id="已实现删除邮件自动测试覆盖经-macos-用户手测"></a>

## 已实现：删除邮件

- 用户删除后，核心在 `message_deletions` 写一行，邮件立即从所有列表、计数、搜索和详情中隐藏（`VISIBLE_MESSAGES` 过滤），不改 `remote_state`，因此撤销窗口内的头部同步不会让它重新出现。行在 `DELETE_UNDO_WINDOW`（5 秒）后到期；未开始前可整批撤销，邮件原样恢复。
- 语义：不在“已删除”中且账号有可选的 Trash 角色文件夹 → 移到 Trash；已在 Trash 中，或账号没有 Trash → 永久删除，核心要求调用方声明用户已确认（否则 `confirmationRequired`），永久删除同样有撤销窗口。
- 执行由每账号的写回任务承担：先推送已读 / 星标，再领取到期删除（领取后撤销返回 `alreadyDeleting`）。有尚未到期的删除时，写回任务按最早到期时间定时唤醒；应用退出时未执行的删除保留，重启后照常执行。
- 服务器命令按来源文件夹与目标分组：有 `MOVE` 用 `UID MOVE`；否则在 `UIDPLUS` 下用 `UID COPY` + `UID STORE +FLAGS.SILENT (\Deleted)` + `UID EXPUNGE`；永久删除为 `\Deleted` + `UID EXPUNGE`。**从不发送普通 `EXPUNGE`**，它会连带删掉其他客户端标了 `\Deleted` 的邮件；能力不足时不碰服务器，邮件恢复显示并提示。
- `SELECT` 后核对 UIDVALIDITY，不一致则不执行、恢复显示；Trash 文件夹消失、账号换了来源世代同样恢复。服务器拒绝按次计数，`MAX_DELETION_ATTEMPTS`（5）次后恢复显示；网络、认证失败不计次，邮件保持隐藏直到下次能连上。恢复的数量随 `CoreEvent::Deletions` 的 `givenBack` 推送，前端提示用户。
- 成功后源记录变为 `deleted` 墓碑并移出搜索索引，丢弃该邮件仍在排队的标记变更，并唤醒该账号的头部同步刷新 Trash 和计数。移到 Trash 的邮件在 Trash 中是新的本地记录（正文缓存不随之迁移）；不在 Trash 同步窗口内的旧邮件不会出现在 MailX 的 Trash 中。尚未使用 `COPYUID` 保留本地身份。
- 已知竞态：若某轮头部同步在 MOVE 之前取得 UID 列表、在本地记为墓碑之后才写库，该邮件可能短暂重新出现，下一轮对账会再次移除。
- 撤销窗口内被隐藏的未读邮件不计入未读数，期间服务器计数不覆盖本地值。
- 移动到指定服务器文件夹、服务器归档、界面多选批量操作与“标记为垃圾邮件”尚未实现。本机归档见下节，MCP 已支持批量标记与本机归档。

<a id="已实现本地归档仅本机自动测试覆盖经-macos-用户手测"></a>

## 已实现：本地归档（仅本机）

- 归档不碰服务器：不发 IMAP 命令，不写回；邮件仍在 INBOX。状态存于 `message_archives`（账号、`mailbox_source_id`、归档键、时间），列表与计数在读取时按此过滤。
- 归档键为 `Message-ID` 头（`m:` 前缀），因此 UIDVALIDITY 重置导致邮件行重建、本地 id 改变后仍是已归档；没有 `Message-ID` 的邮件用本地 id（`i:` 前缀），重置后会回到收件箱。记录带邮箱来源，账号指向新来源时旧记录不再生效。新到达的邮件只有在其 `Message-ID` 曾被归档时才显示为已归档，新邮件通知不受影响。
- 只有收件箱角色文件夹的邮件算已归档：邮件被其他客户端移出收件箱后不再属于任何收件箱视图；之后带同一 `Message-ID` 回到收件箱会显示为已归档。共用一个 `Message-ID` 的两封收件箱邮件一起视为已归档。
- 收件箱未读数 = 服务器 `STATUS` 未读数 − 本机已归档的未读邮件（不低于 0），在读取文件夹时计算，库中仍存服务器原值，同步更新不受影响；“已归档”视图的未读数由本地计算。
- 删除已归档邮件走原删除流程；邮件成为 `deleted` 墓碑后不在任何视图出现。
- 已知限制：其他设备和网页版仍在收件箱显示该邮件；服务器侧未读数在其他设备读过后与本机扣减可能短暂不一致；界面尚无多选批量归档（MCP 已支持批量归档），也不支持“同时移到服务器归档文件夹”。

## 4. 本地变更与恢复

当前已实现已读、星标与删除写回，以及仅本机的归档；任意服务器文件夹移动尚未实现。标记意图存于 `flag_changes`，删除意图与撤销期限存于 `message_deletions`，归档存于 `message_archives`。写回前核对账号来源、文件夹与 UIDVALIDITY，服务端 flags 与待写本地意图分开处理。

- 同一邮件的同类待写操作可合并，按账号串行应用；成功后重新读取服务端状态。
- 当前按待写意图应用已读 / 星标，后续同步对账服务端状态；CONDSTORE 条件写尚未实现，不宣称具备跨设备强一致性。
- 远端已删除或 UID 世代变化时失败并提示，不按主题或 `Message-ID` 猜测重放。
- SQLite 写入失败不推进同步游标；磁盘满时停止新增缓存、保留草稿并报告可恢复错误。
- 进程重启恢复未完成的只读同步；发送与写操作按各自状态处理，不把所有任务一律重跑。
- 配置变化后，读取批次与游标仅向匹配来源世代提交；OAuth 刷新按 grant/凭证版本接管，SMTP 结果始终关联原发送尝试。删除准入规则应阻止旧任务复活账号。

## 5. 本地草稿与可靠发送

状态：已有实现。富文本草稿、独立写信窗口、两步发送按钮、附件与内嵌图片、SMTP 会话阶段、重试、撤销发送与已发送副本的细节见[写信与发送设计](sending.md)；本节保留可靠性总纲。真实服务商与平台证据单独记录，不由实现推定全部通过。

草稿只存本地，含 `accountId`、正文、收件人、附件引用和单调递增 `revision`。回复 / 全部回复依据原邮件 Reply-To、From 和收件人集合构建，排除当前身份，界面始终展示完整 To / Cc / Bcc。构造邮件时拒绝地址和主题中的头部注入。

写信窗口本身完整展示所用账号、全部收件人、正文与附件，不另弹确认框；发送按钮需两次点击确认，但这只防误触，不是安全边界。MCP / Agent 可凭宿主授予的发送权限直接发信，无需逐封 UI 确认。核心验证当前 revision、账号能力和调用主体授权，固化 MIME 快照与附件摘要，再以 `clientMutationId` 创建唯一队列项。草稿排队后不可原地修改；编辑应先取消队列或另建草稿。

```text
draft → queued → sending → accepted
          │         ├── failed（明确失败）
          │         └── unknown（可能已被服务器接受）
          └── canceled
```

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| queued | 用户已确认，等待网络、队列或撤销等待期 | 可取消；按该快照发送；消息内容发出前的临时错误回到此状态并按退避自动重试 |
| sending | 已进入一次 SMTP 尝试 | 禁止并发重复提交；中途取消不保证撤回 |
| accepted | 收到 SMTP 提交成功响应 | 显示“服务器已接受”，不等同收件人已收到 |
| failed | 明确未被接受 / 明确拒绝，或自动重试耗尽 | 标记错误；用户处理后创建新的发送尝试 |
| unknown | DATA 提交后断线，或重启时无法证明是否已接受 | 不自动重发；引导检查已发送后再确认 |
| canceled | 在提交前取消 | 永不发送该队列项 |

应用幂等只能防止自身重复入队，无法使 SMTP 具备跨网络故障的 exactly-once 保证。SMTP 规范对最终响应和超时重试有明确语义，因此本设计保守保留 `unknown`。[RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html)。

同一 `clientMutationId` 和相同快照返回同一队列结果；键复用但内容不同报 `IDEMPOTENCY_CONFLICT`。新一次人工确认重试使用新键，历史结果不可覆盖。重启后遗留 `sending` 按 `unknown` 处理，除非持久化阶段能证明尚未提交消息内容：写出消息内容前先持久化“正文已开始”标记，没有该标记的 `sending` 回到 `queued`。

任一收件人在 RCPT 阶段被拒绝时，在 DATA 前中止整次发送并报告拒绝名单，不静默只发给部分人。发送被接受后，MailX 本地保留已发送副本；服务器已发送文件夹出现匹配身份时只显示服务器那一份。匹配优先使用原生 `Message-ID`，服务商改写时由[兼容层](provider-compatibility.md)校验原始标识；已有缓存可分批补抓头部，发送结果和服务器副本按任意顺序入库都能对账。当前不向服务器 APPEND，以后加入时，APPEND 结果不确定要先查询副本再决定是否追加。副本未匹配、归档失败或不确定均不能触发再次 SMTP 发送。

## 6. 邮件聚合与线程

统一收件箱是各账号 INBOX 已缓存邮件的查询视图，按 `(receivedAt, emailId)` 降序游标分页。当前不做跨文件夹去重；Gmail 标签映射成多个文件夹时，同一内容可能有多个位置，UI 应保留账号和文件夹来源。

会话聚合已有数据层实现（见第 1 节末尾的归并规则）：账号内按 `References` / `In-Reply-To`（含引用同一未缓存根邮件的兄弟邮件）关联；主题兜底只用于双向往来，不能仅凭同主题合并；缺失或无法判断时保持独立，也不跨账号合并正文供 AI 使用。`getConversation` 把同一 `Message-ID` 的多份副本只列一次。线程摘要始终标明实际纳入的邮件集合。
