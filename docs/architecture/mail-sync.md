# 账号、同步与发信

状态：**文件夹与全部可选目录邮件头同步已有实现 / 正文与发送仍为 Initial draft** · 2026-10-19。已实现经账号路由的 IMAP 连接、邮件头缓存与只读查询；真实服务商已有部分冒烟证据，完整兼容性待验证，执行证据见[验证策略](../development/validation.md)。账号配置详见[账号配置](account-configuration.md)，状态与参数可随验证修订。

## 已实现：文件夹同步

- `MailxCore` 为每个账号运行一个 tokio 后台任务：读取同步计划 → 不持存储锁完成 IMAP 登录、`ID`（服务器提供时）和完整 `LIST "" *` → 短事务写入目录。目录首次及每 10 分钟到期后刷新；只有匹配 tagged OK 的完整结果可触发删除对账，逐目录 STATUS 失败不影响目录发现。
- 凭证只用于其确认时的端点；服务器、TLS、用户名或代理变化后报告 `credentialUntrusted`，不会把旧密码发往新端点。
- 登录被拒、凭证缺失 / 不受信任、服务器不支持 STARTTLS 时不自动重试，直到账号被修改；网络、代理、TLS 与超时按 §2 退避重试。
- 角色识别顺序：INBOX 名称 → SPECIAL-USE 属性 → 顶层（或 INBOX 下）的常见名称；每个角色只分配给一个文件夹。层级由服务器分隔符得出，`INBOX.Sent` 这类系统文件夹与收件箱并列显示。
- 文件夹按账号的 `mailboxSourceId` 隔离：切换服务器后旧列表不再显示，旧服务器迟到的结果会被丢弃；同一服务器名称在多次同步间保持本地 ID。
- 尚未实现：OBJECTID 改名识别、NOTIFY；服务商矩阵尚未验证。

## 已实现：所有可选文件夹邮件头同步

- `SyncManager` 按账号调度，账号间并发、暂不设全局账号并发上限；每账号正常使用一条连接，收件箱先、其余目录按稳定顺序串行处理。每轮结束后等待 60 秒，文件夹多或网络慢时会增加轮询总周期。每目录先 STATUS 更新计数；若 UIDVALIDITY、UIDNEXT、MESSAGES、UNSEEN 均与该目录上次完整处理时相同，且距上次完整处理不足 10 分钟，则跳过 EXAMINE、SEARCH 与标志对账（服务器不返回 UIDNEXT 时从不跳过）。每 10 分钟的完整处理补上 STATUS 看不到的变化，例如 `\Flagged`。STATUS 快照只保存在同步任务内存中，任务启动或某目录本轮失败后，下一轮总是完整处理。
- 同步 LIST 中全部可选文件夹，包括已发送、草稿、归档、垃圾邮件、回收站和自定义目录；不可选容器仅显示层级。使用 `EXAMINE` 和 `BODY.PEEK[HEADER.FIELDS (DATE SUBJECT FROM TO CC REPLY-TO MESSAGE-ID)]`，同时读取 UID、FLAGS、INTERNALDATE、RFC822.SIZE 与 BODYSTRUCTURE；不读取正文或附件内容，不发送 SELECT、STORE 或其他写命令。
- 明确消费完成的单目录命令拒绝只使该目录本轮失败，保留缓存并继续其他目录；STATUS 失败保留上次计数，新发现目录显示计数未知。超时、EOF、BYE 或不完整响应使会话失效，丢弃旧连接并退避重连，从下一未处理目录继续，避免一直卡在首个坏目录。认证 / 信任失败仍停止整个账号。
- `mail-parser` 启用 `full_encoding`，解码 UTF-8、GBK、GB2312、GB18030 等编码的主题和地址显示名。收件时间依次取 INTERNALDATE、Date 头和同步时间，保存为 UTC 毫秒时间；缺失或损坏字段按空值兜底，不记录原始邮件头。
- 附件标志来自 BODYSTRUCTURE：附件 disposition，或 multipart 下既非 text / multipart 且非 inline 的叶子部分，视为有附件；纯文本、HTML、multipart/alternative 中的正文部分不因此成为附件。不建立附件记录或正文预览。
- 邮件与游标存入 `messages` / `folder_sync_cursors`，经 `emails_list` / `emails_get` 提供本地只读查询。任意目录可搜索、筛选未读和分页；统一收件箱只汇总 inbox 角色。逐目录提交后更新数据版本，前端刷新受影响的查询，无关目录结果不会打断当前分页和选中。
- 每目录状态区分等待、同步、成功和失败；数量受限通过 coverage 单独表示，不能将未完整覆盖一律显示为“正在同步”。缺主题显示“（无主题）”，缺摘要不留摘要行，详情显示“正文尚未下载”。
- 新增 / 删除目录在下一次完整目录刷新后体现；无 OBJECTID 时改名按旧目录消失、新目录出现处理。目录变为不可选后隐藏旧消息；外部移动按源目录删除、目标新增对账，按各自窗口最终收敛，不保证跨目录瞬时一致。
- 尚未实现：正文和附件获取、标记写回、历史回填、同步窗口设置、IDLE、CONDSTORE / QRESYNC、Gmail 标签语义与发信。

## 1. 账号生命周期

当前账号服务只创建、查看和修改配置，返回 `connectionStatus=unverified`。IMAP 与 SMTP 可使用不同主机、用户名与凭证；保存成功不代表连接成功。实际配置模型、邮箱来源世代、端点信任及后续停用/删除契约见[账号配置](account-configuration.md)。

当前用独立的 `AccountSyncState` 表达后台收件同步状态；后续连接测试与发送接入后，配置状态、认证状态、收发连接状态和同步进度分别表达，由 UI 汇总：例如 IMAP 正常同步、SMTP 被禁用、本地缓存可读可以同时成立。网络不通与授权被撤销分别处理；不得因为一个连接失败就禁止读取本地缓存。连接测试分别报告收信和发信能力。

停用应阻止新任务、关闭连接并按操作类型收尾；删除需显式处理缓存、授权与在途任务，不删除服务端邮件。不能把“停止调度”理解为丢弃已轮换的凭证或已经发生的 SMTP 结果。
能力由连接探测产生：`canRead`、`canSend`、`canSetSeen`、`canSetFlagged`、`supportsIdle` 等。预设只是建议配置，不能替代实际探测。

## 2. 连接与任务预算

当前账号之间并发，用户选择暂不设全局账号并发上限；每账号正常只有一条 IMAP 会话，目录与批次串行。普通命令 30 秒超时，沿用现有连接超时和失败退避。下列连接池、IDLE、正文 / 附件及 SMTP 配额属于后续候选，不代表已经启用。

- 每个账号默认最多 2 条 IMAP 连接：1 条收件箱 IDLE / 轮询，1 条获取正文与历史；最多 1 个 SMTP 发送任务。
- 全局并发限制暂不启用；若后续资源或服务商证据需要，再评估连接预算。一个账号失败不阻塞其他账号。
- 初始连接超时 15 秒，普通命令 30 秒；大附件按持续无进度 60 秒超时并允许取消。IDLE 单独维护心跳与重连，不套用普通命令超时。
- 可重试网络读取采用带抖动的指数退避，基准 1 秒、上限 5 分钟；成功后复位。认证错误停止自动重试并提示重新授权，避免反复撞密码。
- 所有值是初始配置预算，M1 用故障注入验证；服务商限制更严时采用较低连接数。

## 3. 首次同步与增量同步

当前同步窗口在首次建立游标或 UIDVALIDITY 变化时确定：`window_start` 为当日 UTC 日期减 30 天，之后沿用该起点，**不是每天滚动的最近 30 天**。IMAP `SEARCH SINCE` 使用服务器日期语义，时区边界可能相差一天。

1. 按账号路由登录，必要时刷新文件夹目录；选择全部可选文件夹，收件箱优先，其余稳定遍历。先用 `STATUS` 更新总数和未读数，再用 `EXAMINE` 获取 UIDVALIDITY；缺少 UIDVALIDITY 时本轮失败，不写入邮件。
2. 没有游标或 UIDVALIDITY 改变时，在短事务内将旧代际的 `present` 邮件标记为 `stale`，重建游标，设置固定窗口起点、`highest_uid=0`、`backfill_done=0`。旧代际不再对查询可见。
3. 每轮重新执行完整 `UID SEARCH SINCE <window_start>`，对所有匹配 UID 排序，选取最大的 1,000 个。超过上限时设置 `window_capped=1`；此上限是每轮选择范围，不是本地总记录上限。
4. 只抓取选定集合中尚无当前 `present` 记录的 UID，按新到旧每批最多 200 封。每批邮件与 `highest_uid` 在同一事务提交，重复写入保留本地 ID；选定集合头部全部取得，且删除与 flags 对账成功后，才标记 `backfill_done=1`。取消、断线或写库失败保留已提交批次，下一轮按实际缓存继续，最大 UID 不代表其之前都已缓存。
5. 只有完整 SEARCH 成功后，才把当前代际中 `received_at >= window_start`、却不在**完整搜索结果**中的本地 `present` UID 标记为 `deleted`。不得拿截取后的 1,000 个 UID 判断删除；窗口外缓存不对账、不自动清理。
6. 对选定集合中已有的 UID 重新读取 FLAGS，每条命令最多 500 个 UID，更新已读、星标和原始 flags；不修改服务器标志。已缓存但后来退出最新 1,000 个集合的邮件仍保留，头部总量可超过 1,000；这些记录不再参与本轮 flags 刷新。
7. 邮件批次、flags、删除与既有游标推进事务核对账号当前 `mailboxSourceId`、文件夹归属与 UIDVALIDITY，任一不匹配就拒绝写入迟到结果。文件夹计数只核对来源与归属，代际初始化事务负责建立或切换 UIDVALIDITY。每目录提交后发布数据版本，整轮全部成功才更新账号成功时间；部分失败保留目录失败信息。worker generation 和账号 revision 在阻塞任务实际取得存储锁后再次校验，已取消任务不能靠排队中的写操作恢复旧结果。

UID 只在文件夹及其 `UIDVALIDITY` 世代内有效，不能拿序号或邮件头 `Message-ID` 当唯一远端主键。[RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html)。MailX 使用 `(accountId, mailboxSourceId, folderId, uidValidity, uid)` 表达远端位置，本地 `emailId` 是独立 UUID；更换接收来源后建立新来源，即使远端使用相同文件夹名和 UID，也不复用旧映射。

服务端 UID 不连续是正常情况；搜索得到明确的 UID 集合后再抓取，不用 `UIDNEXT - 1000` 推算数量，也不将 UIDNEXT 当作本地已提交进度。CONDSTORE / QRESYNC 和保持连接的 IDLE 可在后续优化每轮完整搜索、flags 获取与重新登录成本。

## 4. 本地变更与恢复（写操作为后续设计）

v0.1 只支持已读和星标写回。`pending_mutations` 保存包含来源世代的目标远端身份、期望 flags、客户端操作 ID 和状态。离线修改显示“待同步”，服务端确认 flags 与本地意图分开存储。

- 同一邮件的同类待写操作可合并，按账号串行应用；成功后重新读取服务端状态。
- 使用支持的条件写能力检测冲突；不支持时应用用户最后一次明确操作并重新读取，不宣称具备跨设备强一致性。
- 远端已删除或 UID 世代变化时失败并提示，不按主题或 `Message-ID` 猜测重放。
- SQLite 写入失败不推进同步游标；磁盘满时停止新增缓存、保留草稿并报告可恢复错误。
- 进程重启恢复未完成的只读同步；发送与写操作按各自状态处理，不把所有任务一律重跑。
- 配置变化后，读取批次与游标仅向匹配来源世代提交；OAuth 刷新按 grant/凭证版本接管，SMTP 结果始终关联原发送尝试。删除准入规则应阻止旧任务复活账号。

## 5. 本地草稿与可靠发送（后续）

v0.1 草稿只存本地，含 `accountId`、正文、收件人、附件引用和单调递增 `revision`。回复 / 全部回复依据原邮件 Reply-To、From 和收件人集合构建，排除当前身份，界面始终展示完整 To / Cc / Bcc。构造邮件时拒绝地址和主题中的头部注入。

发送前 UI 展示所用账号、全部收件人、正文与附件。核心验证当前 revision、账号能力和交互主体授权，固化 MIME 快照与附件摘要，再以 `clientMutationId` 创建唯一队列项。草稿排队后不可原地修改；编辑应先取消队列或另建草稿。

```text
draft → queued → sending → accepted
          │         ├── failed（明确失败）
          │         └── unknown（可能已被服务器接受）
          └── canceled
```

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| queued | 用户已确认，等待网络或队列 | 可取消；网络恢复后按该快照发送 |
| sending | 已进入一次 SMTP 尝试 | 禁止并发重复提交；中途取消不保证撤回 |
| accepted | 收到 SMTP 提交成功响应 | 显示“服务器已接受”，不等同收件人已收到 |
| failed | 明确未被接受 / 明确拒绝 | 标记错误；用户处理后创建新的发送尝试 |
| unknown | DATA 提交后断线，或重启时无法证明是否已接受 | 不自动重发；引导检查已发送后再确认 |
| canceled | 在提交前取消 | 永不发送该队列项 |

应用幂等只能防止自身重复入队，无法使 SMTP 具备跨网络故障的 exactly-once 保证。SMTP 规范对最终响应和超时重试有明确语义，因此本设计保守保留 `unknown`。[RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html)。

同一 `clientMutationId` 和相同快照返回同一队列结果；键复用但内容不同报 `IDEMPOTENCY_CONFLICT`。新一次人工确认重试使用新键，历史结果不可覆盖。重启后遗留 `sending` 按 `unknown` 处理，除非持久化阶段能证明尚未提交消息内容。

任一收件人在 RCPT 阶段被拒绝时，v0.1 在 DATA 前中止整次发送并报告拒绝名单，不静默只发给部分人。发送后 Sent 归档独立记录 `pending / archived / unknown / failed`：服务商自动归档时对账；需要 IMAP APPEND 时单独执行。归档失败或不确定不能触发再次 SMTP 发送。

## 6. 邮件聚合与线程

统一收件箱是各账号 INBOX 已缓存邮件的查询视图，按 `(receivedAt, emailId)` 降序游标分页。v0.1 不做跨文件夹去重；Gmail 标签映射成多个文件夹时，同一内容可能有多个位置，UI 应保留账号和文件夹来源。

线程聚合尚未实现。后续按账号内 `References` / `In-Reply-To` 尝试关联，缺失或有歧义时保持独立。不能仅凭同主题合并，也不跨账号合并正文供 AI 使用。线程摘要始终标明实际纳入的邮件集合。

## 7. 完成证据
