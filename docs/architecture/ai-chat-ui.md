# AI 交互界面

状态：**Proposed** · 2026-11-14，2026-11-15 按修订后的权限更新操作结果与确认卡。「此刻」对话已实现（`frontend/src/features/ai/` 共用构件与 `features/now/now-chat.tsx`；自动测试与浏览器预览，未在桌面实机与真实服务商上验证）：输入框、对话视图、回复的 Markdown（`marked` 词法分析＋自有渲染，见 4.2）、工具行、操作结果与撤销、草稿卡片、邮件引用、确认卡、贴底滚动与视图切换。回复的悬停操作（复制、重新生成）、“继续生成”、建议按钮与打开卡片尚未实现；阅读区与写信窗口入口仍为 Proposed。**全局胶囊与 AI 对话岛已实现**（2026-11-19，`features/ai/assistant-island.tsx` 与主窗口工作台接入；自动测试与浏览器预览，未在桌面实机验证）：胶囊、对话岛（可拖宽、窄窗口为浮层）、上下文标签与“不带上这项”、`Cmd/Ctrl+J`、“问 AI”命令，以及与「此刻」共用同一个对话；对话上下文由 core 按 id 读取（`core/src/assistant/view.rs`，见 5.1）。**阅读区的邮件摘要已实现**（2026-11-19，`features/mail/summary/`，见 5.2；自动测试与浏览器预览，未在桌面实机与真实服务商上验证）；写信窗口的原地功能仍为 Proposed。本文定义内置 AI 在前端的共用构件、各入口的形态、视觉与动效规则和性能要求，适用于[「此刻」页面](now-page.md)的对话，以及以后阅读区、写信窗口和命令面板中的 AI 入口。界面整体规则仍以[界面设计语言](ui-design.md)为准；权限与确认见[内置 AI 工具权限](ai-permissions.md)，运行生命周期与数据披露见 [AI Runtime](../ai-runtime/README.md)。

## 1. 原则

- **与整体风格一致**：现代、简约、克制。AI 的文字、间距和图标与邮件阅读、写信保持同一套语言。
- **AI 有自己的视觉标识，但点到为止**：霓虹渐变与发光边框是 AI 能力的识别符号，可以使用，但只用在“AI 在这里 / AI 正在工作”的少数位置，不铺满界面，不影响整体的平衡与可读性，规则见 4.6。
- **过渡优雅自然**：每个状态变化都有衔接，不跳变；动效短、轻、有方向感，只用于说明“什么出现了、去了哪里”，不为装饰而动。
- **体验优先**：随时可停止、可返回、可撤销；不打断用户手头的工作；AI 不可用或失败时界面安静地退回，不制造焦虑。
- **性能是约束而非优化项**：流式输出、长对话和后台常驻都不能让界面掉帧或持续占用 CPU。

## 2. 选型：自建构件，不引入现成聊天组件库

AI Elements、assistant-ui 等现成组件库不直接引入，作为交互参考：

1. 模型调用在 Rust core，前端经 Tauri 事件接收带序号的流式片段，掉线后按 Run 快照恢复；数据的权威在 core，套用组件库自带的状态模型需要额外的转换层。
2. 前端的 shadcn 使用 Base UI 底层（`base-mira` 风格），这类库多基于 Radix，混用会带来两套弹层与焦点管理。
3. 它们默认的气泡、卡片与边框需要大幅改造，才符合“岛内不加卡片边框和分割线”的约定。
4. MailX 的关键构件（邮件引用、确认卡、建议按钮、带 revision 的草稿修改建议）这些库都没有。

可以引入解决单一通用问题、体积小、无样式的依赖（例如“贴底滚动”），引入前评估体积、维护状态与许可证。现成库的组件代码不复制进仓库。

## 3. 分层

代码放在 `frontend/src/features/ai/`：

| 层 | 职责 |
| --- | --- |
| 数据层 | `useAiConversation(context)` 等 hook：发起与取消 Run、合并流式片段、按快照恢复、外发同意、确认请求与结果。只经 `MailxClient` 访问 core，不直接请求模型。无界面。 |
| 构件 | 消息与片段渲染、输入框、确认卡、引用、建议、AI 标记、状态行。只依赖数据层的类型，不关心所在入口。 |
| 入口 | 各处按场景组合构件并提供上下文（「此刻」、阅读区、写信窗口、命令面板）。 |

共用的是“AI 交互构件”，聊天只是其中一种组合；写信窗口以修改建议为主，不强行套用聊天形态（见第 5 节）。

## 4. 构件

### 4.1 消息

- **用户消息**：靠右，淡底色（`bg-muted` 一档），圆角与列表选中态一致，无边框；最大宽度约内容列的 80%。
- **AI 回复**：不加气泡，直接作为正文排版，字号、行高与阅读区一致，左对齐占满内容列。回复开头不放头像；第一段前有一个小的星芒标记，表示由 AI 生成。
- 消息之间用留白区分，同一角色的连续消息间距较小，换角色时间距较大；不加分割线和时间戳行，时间在悬停时以 Tooltip 显示。
- 每条 AI 回复底部在悬停或聚焦时淡入一行小操作：复制、重新生成；不常显。

### 4.2 回复中的片段

一条 AI 回复由有序片段组成，按到达顺序展示：

| 片段 | 呈现 |
| --- | --- |
| 文字 | 安全渲染的 Markdown（GFM，覆盖范围见下）；不渲染 HTML，不加载图片，链接点击后交给系统浏览器，悬停显示完整地址 |
| 思考 | 模型的每一段思考一行弱化小字，与工具行同一样式：进行中为“思考中 · 12 秒”（“思考中”带 AI 光泽，秒数每秒更新），默认不显示思考原文；结束后原位交叉淡入为“思考了 12 秒”（不足 1 秒为“思考了片刻”），整行是展开按钮，展开后在下方以更小的弱化字号显示原文（保留换行，左侧一道细竖线，与引用同样式，不加卡片或边框）。默认收起，读回的对话也收起；只有脱敏 / 空思考时只显示时长，没有展开按钮。工具调用前后的思考各占一行 |
| 工具进行中 | 一行弱化小字与小图标，如“正在搜索邮件…”，完成后折叠为“搜索了 12 封邮件”，可展开查看调用了什么（不显示原始参数 JSON） |
| 操作结果 | 直接执行的整理操作完成后一行结果，如“归档了 3 封 · 撤销”；撤销过期后按钮消失。AI 新建或修改的草稿显示为草稿卡片：主题、收件人与“打开草稿” |
| 打开卡片 | 模型想让用户查看某封邮件或草稿时，显示为可点的小卡片，不自动切换视图、不抢焦点 |
| 邮件引用 | 行内小标签：发件人头像（或账号色点）＋主题截断，悬停显示发件人、时间和主题全文，点击打开该邮件。独占一行时为卡片（与「此刻」列表同样的行内容：头像、发件人、主题、时间），静止时带淡底色（`bg-muted/50`）以便看出是一个整体，悬停加深、按下轻微缩小，不加边框；加载中的占位与卡片同高同底色，载入后不跳动。文件夹引用卡片同样处理；「此刻」概览里的列表行仍只在悬停时显示底色 |
| 建议 | 回复末尾一组文字按钮（如“归档这 3 封”），点击等同于把这句话作为新消息发给助手 |
| 确认卡 | 见 4.4 |
| 未完成 | 被取消或中断的回复末尾一行弱化小字“已停止”，可“继续生成” |
| 失败 | 一行平实的原因与“重试”，不用红色大块提示 |

**渲染器**（`frontend/src/features/ai/markdown.ts`、`markdown-view.tsx`）：只用 `marked` 的词法分析器（`Lexer`，`gfm: true`、`breaks: true`，单个换行仍是换行）把文字切成 token，再由自己的代码转成纯数据（`MarkdownBlock` / `Inline`），最后画成 React 元素。不使用 marked 的 HTML 渲染器，也不用 `dangerouslySetInnerHTML`。曾评估的 Tiptap 只读渲染、react-markdown / remark、streamdown 均未采用：前者为编辑器设计、流式时整篇重建，后两者体积更大且仍需另做安全约束。

覆盖范围：段落与换行；标题（h1–h6 映射为两三档接近正文的字号，h1、h2 上方略多留白）；紧凑与松散列表（有序列表保留起始序号，可嵌套，列表项可含多段与代码块）；任务清单（静态的勾选 / 空框图标，不可点击）；引用；带语言标注的围栏代码块；GFM 表格（含列对齐）；删除线；水平线；行内代码；粗体、斜体；链接、尖括号自动链接与裸地址；HTML 实体解码（`&amp;` → `&`）；反斜杠转义；引用式链接（`[文字][id]`）。

安全规则：

- 原始 HTML（块级与行内）按原样显示为文字；图片从不加载，只保留替代文字。
- 链接只经 `safeHref` 放行 http、https、mailto，其余只显示链接文字；尖括号自动链接不安全时显示原文。裸地址在中文标点（`。，、；：！？）】」』` 等）处结束，结尾的英文标点与不成对的右括号不算地址。
- `mailx://email/<id>`、`mailx://folder/<id>` 经 `parseRef` 校验后成为行内引用小标签；段落中独占一行的引用成为卡片（见“邮件引用”）。格式不对的 `mailx:` 地址只显示文字。
- 表格单元格与其他正文走同一套行内处理与过滤。

视觉：表格按内容宽度显示，放在可横向滚动、圆角的容器里，最宽不超过正文列；表头淡底色、中等字重，行与行之间用很淡的隔行底色区分，不画网格线和边框；`text-sm`、等宽数字，遵循列对齐。代码块保持 `bg-muted/60` 圆角块，有语言时顶部一行弱化小字标注语言；右上角的复制按钮在悬停或键盘聚焦时出现，复制后图标交叉淡入为对勾约 1.5 秒；不做语法高亮。水平线不画通栏分割线（岛内规则），而是居中一段约 3rem 宽、1px 高、半透明的 AI 渐变短条。删除线为 `line-through` 加弱化前景色。

### 4.3 输入框

- 单行胶囊形，聚焦后按内容增高，最多约 6 行后内部滚动；高度变化平滑（见第 6 节）。聚焦时描边变为 AI 渐变，生成中描边流动并带淡柔光（见 4.6）。
- 右侧只有一个主按钮：有内容时为“发送”，生成中变为“停止”，两者原位交叉淡入，不改变按钮尺寸。
- `Enter` 发送，`Shift+Enter` 换行；输入法组字时 `Enter` 不发送（沿用快捷键守卫的判断）。`Esc`：生成中先停止，再按返回上一级。
- 占位文字随入口变化（如“问问你的邮件”“问问这封邮件”）。
- 以后可支持用 `@` 引用邮件或联系人，以小标签插入；首期不做。

### 4.4 确认卡

- 代表一个独立对象，是“岛内不加边框”的允许例外：细轮廓（`ring-1 ring-foreground/10`），圆角，内边距与附件元素同级，不加阴影。
- 用于需要确认的操作：发信、取消发送、修改或删除用户自己的草稿，以及在设置中改为“每次询问”的类别（见[内置 AI 工具权限](ai-permissions.md#3-确认怎么实现)）。内容由 core 根据当前数据生成：标题写明动作（“发送这封邮件？”），下方是要素清单（发信为发件账号、收件人、主题、正文开头和附件）；风险信号用琥珀色小字逐条列出，不用整卡变色。运行在等待确认期间暂停，确认卡是继续它的唯一途径。
- 按钮：右侧主按钮为动作本身（“发送”），左侧为“取消”；默认焦点在“取消”。处理后卡片原位收起为一行结果（发信为“已排队发送 · 撤销”，在撤销发送等待期内可用；拒绝为“已取消”），不留下大块历史卡片。
- 确认卡出现时，如用户不在可见位置，输入框上方淡入一个小提示“有一项操作等待你确认”，点击滚动到卡片。

### 4.5 状态与空态

- 生成开始到首个片段之间显示一行“正在思考…”，文字上有一道缓慢流过的 AI 渐变光泽；什么都还没收到（没有思考、文字或工具行）超过约 10 秒时追加“仍在等待模型响应”，不显示假的进度条。思考片段一出现，这一行就让位给思考行，两者不同时出现；思考进行中不显示“仍在等待”。
- 对话为空时不放示例问题列表；「此刻」页面以问候和统计作为背景，阅读区和写信窗口直接显示输入框。

### 4.6 AI 视觉标识：霓虹渐变与发光

**AI 渐变**是一组固定的冷暖霓虹色（暂定青蓝 → 蓝紫 → 品红），定义为共用 CSS 变量（如 `--ai-gradient` 与各色标），浅色、深色各有一套：浅色主题降低饱和与亮度，避免发灰发脏；深色主题可更亮，但限制光晕的透明度。它不跟随强调色：AI 标识需要在任何外观下都能被认出，同时也避免与用户选的强调色混在一起分不清。

用在哪里：

| 位置 | 静止时 | AI 工作时 |
| --- | --- | --- |
| 星芒标记（AI 生成内容、入口图标） | 渐变填充的小图标 | 不变 |
| AI 输入框 | 普通输入框外观；聚焦时描边变为 1px 渐变 | 渐变描边缓慢流动，外侧有很淡的柔光（模糊半径小、透明度低） |
| “正在思考” / “思考中” | — | 文字上流过一道渐变光泽 |
| 「此刻」的 AI 概述句 | 星芒标记 | 生成期间概述句下方一道细的渐变光带，完成后淡出 |
| 阅读区 / 写信窗口的 AI 入口按钮 | 渐变星芒图标，按钮本身照常 | 图标缓慢流光 |
| 写信窗口的修改建议 | 建议文字左侧一道细渐变竖条 | — |
| AI 回复正文 | 水平线显示为居中的半透明渐变短条 | 正在写的文字末尾一个小星芒（流式光标），透明度缓慢呼吸，结束后淡出 |

不用在哪里：

- **正文文字**：AI 回复的正文、邮件内容、统计数字不用渐变色和发光，保证可读。
- **确认卡与风险提示**：确认卡保持中性的细轮廓，让“要不要执行”这个判断不被装饰干扰；风险信号仍用琥珀色。
- **大面积背景**：不把整块面板、整个岛或对话区铺成渐变；「此刻」页面的时段氛围背景走自己的规则（跟随强调色），不与 AI 渐变叠加。
- **错误与失败**：不发光，安静退回。

平衡规则：

- 同一视图里同时“发光”的元素最多一个（通常是正在工作的那一个）；其他 AI 元素只保留静态的渐变图标或描边。
- 发光只表示状态：AI 工作时出现，结束后约 300ms 内淡出，不常亮。
- 渐变描边最粗 1.5px，柔光不越出元素约 8px；不使用多层阴影堆叠的强光效。
- 对比度：渐变只用于装饰与图标，文字颜色仍取前景色 token。

## 5. 各入口

| 入口 | 形态 | 上下文 |
| --- | --- | --- |
| 「此刻」 | 内容列内的完整对话；发出第一句后概览收成顶部一行摘要，`Esc` 或“返回”回到概览 | 全部可用账号 |
| 全局胶囊 / AI 对话岛 | 邮件页面右下角的胶囊；点开后在邮件岛右侧出现 AI 自己的岛（见 5.1） | 当前邮件、选中的邮件或当前草稿 |
| 阅读区的邮件摘要 | 工具栏的摘要按钮与正文上方的摘要卡（见 5.2） | 当前这一封邮件 |
| 写信窗口的原地功能 | 尚未实现（工具性能力，单独设计） | — |
| 命令面板 | “问 AI”打开最合适的入口并带上当前上下文：只看「此刻」时有对话就回到它，否则打开对话岛 | 当前视图 |

### 5.1 全局胶囊与 AI 对话岛

胶囊和对话岛只出现在邮件页面（收件箱、文件夹、搜索、草稿、发件箱），与分屏还是单栏无关；布局只改变它带上的上下文。「此刻」页、设置、启动页不显示胶囊。

**胶囊**：岛内右下角，高约 36px、宽 240px 的胶囊形按钮——星芒标记加一句随上下文变化的占位（“问问你的邮件” / “问问这封邮件” / “问问选中的邮件” / “问问这份草稿”）。静止时是普通表面，悬停加深阴影与文字颜色。主窗口内写信区打开时上移到底栏之上，不挡“发送”。助手关闭或没有可用模型时整个不显示。

**上下文**按优先级取一项，界面不发送任何正文：

| 当前状态 | 上下文 | 标签 |
| --- | --- | --- |
| 内嵌写信区打开 | `draft` | 草稿主题（空为“（无主题）”） |
| 列表多选 | `emails`（最多 20 封） | “已选 N 封邮件” |
| 草稿视图选中一份 | `draft` | 草稿主题 |
| 阅读区打开一封邮件 | `email` | 邮件主题 |

core 收到 id 后自己经工具层读取：仍受助手设置的账号范围约束，范围外或不存在的 id 当作没有上下文；正文未缓存的邮件只给头部（`bodyCached: false`），模型可用工具再取。结果是整轮运行系统提示末尾的一段 `<tool_result name="current_view" trust="untrusted">`，只对这一次消息有效，不进对话历史——下一句话说的是屏幕上当下有的东西。这段内容涉及的账号照常记入对话，移除账号时随之删除。

**对话岛**：

- 邮件岛右侧的第二个岛，同一画布、间隔 8px，表面与主岛相同。左边缘可拖动或按方向键改宽（320–560px，默认 380px），双击恢复默认；宽度存 `layout.assistantWidth`，与列表宽度一样防抖写入。
- 打开后邮件岛改为一次只显示一栏：分屏视图切换到单栏（阅读区优先），本身就是单栏时收窄即可。这只影响显示，不写入 `layout.readingMode`；关闭后回到原来的布局与折叠状态。
- 窗口放不下“侧栏（或图标栏） + 邮件岛最小宽度 + 对话岛”时，对话岛改为浮在邮件岛右侧上的浮层，不再压窄邮件岛。
- 岛内自上而下：标题“AI 助手”与三个按钮（新对话、历史对话、关闭）、对话列表、上下文标签与输入框。没有消息时显示一行星芒与一句说明。确认卡待答而卡不在可见范围时，输入框上方淡入“有一项操作等待你确认”；向上翻看时出现“回到底部”。确认卡、工具行、思考行、草稿卡片、邮件引用和撤销与「此刻」完全相同。
- 上下文标签在输入框上方一行：小图标、名称与“不带上这项”。移除后本次消息不带上下文，直到屏幕上的内容变了才重新出现（同一封邮件不会反复弹出）。
- 与「此刻」共用同一个对话：切到「此刻」时对话岛关闭，`Chat` 状态原样交给页面，页面直接显示对话而不是概览；从「此刻」回到邮件页面时胶囊恢复，再打开对话岛仍是同一段对话。新对话、历史对话、删除与清除在两边相同。
- `Esc`：焦点在对话岛内时先停止正在进行的回复；不关闭岛、不关闭旁边的邮件。单键快捷键（`j` / `e` / `#` 等）在岛内一律不触发，与内嵌写信区相同。
- `Cmd/Ctrl+J` 与命令面板的“问 AI”：

| 当前 | 行为 |
| --- | --- |
| 邮件页面，对话岛关闭 | 打开并聚焦输入框 |
| 邮件页面，对话岛打开 | 关闭 |
| 「此刻」 | 打开时聚焦页面输入框；关闭时回到对话岛；没有对话时打开对话岛（切到收件箱） |
| 设置、启动页 | 命令面板的“问 AI”在有对话时打开对话岛，否则打开「此刻」 |

- 对话岛开着时切换邮箱、搜索、打开别的邮件都保持打开：上下文标签随之更新。

### 5.2 阅读区的邮件摘要

固定任务（见 [AI Runtime](../ai-runtime/README.md#2-两类运行)），代码在 `frontend/src/features/mail/summary/`（面板、摘要卡与 `useEmailSummary`）与 core 的 `core/src/assistant/email_summary.rs`。只总结当前打开的这一封邮件，不总结整个会话。

**入口。** 阅读区工具栏的 ✦“AI 摘要”按钮，与翻译按钮各自独立，打开一个小面板：

- 篇幅：简短（1–2 句）/ 详细（一小段）/ 要点（列表；有待办时末尾加一行加粗的“待办”）。
- 语言：跟随界面 / 邮件原语言 / 指定一种语言（取自翻译的目标语言）。
- 复选框“总是总结来自 X 的邮件”：把发件地址（小写）加入 `assistant.summary.senders`。
- “生成摘要”按钮默认获得焦点，`Enter` 即生成。面板里的选择同时存为“上次使用”（`assistant.summary.style` / `language`），以后自动生成沿用。

**摘要卡。** 在邮件头之下、正文之上，表面与翻译提示条相同（弱化底色，不加边框）：标题“✦ 摘要 · 篇幅”，右侧操作为复制、重新生成（`fresh`，跳过缓存）、继续问（打开对话岛并带上这封邮件作为上下文，见 5.1）、收起 / 展开、关闭。收起时只显示一行，并全局记住（`assistant.summary.collapsed`）；关闭只对这一封邮件生效。生成中流式显示并带“停止”；失败时在卡内显示原因与“重试”（需要设置时为“打开 AI 设置”）；尚未同意时卡内询问，选“允许”后进入同意对话框，同意后重新开始。流式光标与渐变光泽沿用 4.6 的规则，同一视图只有一处发光。

**何时出现与自动生成。** 打开邮件时：

- 已有保存的摘要（该邮件、正文未变，任一篇幅与语言中最新的一条）：立即显示，不请求模型，也不需要同意。
- 没有：只有开启了“自动总结打开的邮件”（默认关）且正文文字不少于 200 字符，或发件人在“总是总结的发件人”里（不限长度）时才自动生成；否则只有用户点按钮才生成。
- 切换邮件时取消正在进行的摘要。
- 助手关闭或没有可用模型、邮件所属账号被排除在助手范围外、正文尚未下载时不提供摘要入口。

**数据。** 摘要由 core 按邮件 id 经工具层读取邮件（上限 24,000 字符），所以界面不发送正文，助手的账号范围照常生效；内容作为不可信的 `<email>` 数据放入提示词，不带工具。结果按（邮件、篇幅、语言）缓存在本机（`message_summaries`，见[数据库迁移](database-migrations.md)），只在正文与提示词版本都未变时有效；因输出上限被截断的摘要显示但不保存。接口见[应用服务 API](../contracts/app-api.md#ai-助手主窗口)。

**本轮不做**：回复建议、写信窗口里的 AI 工具、整个会话的总结、单键快捷键。

## 6. 动效

### 6.1 时长与缓动

沿用现有界面的节奏（现有组件多为 100 / 150 / 200ms，配 `ease-out`），AI 界面不另起一套：

| 用途 | 时长 | 缓动 |
| --- | --- | --- |
| 悬停、按钮状态、小操作淡入淡出 | 100–150ms | `ease-out` |
| 片段出现、确认卡收起、输入框增高 | 200ms | 减速曲线（如 `cubic-bezier(0.2, 0, 0, 1)`） |
| 视图切换（概览 ↔ 对话、面板展开收起） | 250–300ms | 同上；离开用更短的时长（约为进入的 2/3） |

实现时把这几档缓动和时长定义为 `index.css` 中的共用 CSS 变量，AI 构件与以后的界面共用，不在组件里写死数值。

### 6.2 具体衔接

- **新消息**：用户消息自底部上移约 4px 并淡入；AI 回复的新片段只淡入，不位移，避免流式时文字抖动。
- **流式文字**：按到达的片段整段追加，不做逐字打字机效果。回复已显示后，流式过程中新出现的顶层块（段落、列表、表格等）在 `--motion-medium` 内从 0.4 透明度淡入到 1，不位移；正在增长的最后一块不重复播放，首次显示时已有的块（历史对话、已完成的回复）不播放。
- **流式光标**：正在写的文字末尾显示一个约 0.75em 的 `AiMark` 星芒，与文字同行；最后一块是代码块、表格、水平线或引用卡片时另起一行放在其后。它的透明度在 0.35 与 1 之间以约 1.2s 缓慢往复，窗口隐藏时暂停；该段文字结束（回复完成，或被工具行、确认卡接续）时在约 200ms 内淡出后移除。只改变透明度，不用发光或模糊。
- **工具行**：进行中 → 完成时，文字原位交叉淡入，高度不变。
- **思考行**：“思考中”→“思考了”同样原位交叉淡入；展开 / 收起原文为一次性的透明度过渡加高度过渡（约 200ms）。
- **概览 ↔ 对话**：问候与统计向上收拢并淡出，收成顶部摘要行；对话列表自下淡入。返回时反向。优先使用 View Transitions API（目标平台的 WebView 不支持时退回为简单的交叉淡入）。
- **对话岛**：自右侧淡入并轻微左移（`--motion-view`），邮件岛同时收窄；从分屏切到单栏用交叉淡入，不跳变。关闭反向、约为进入时长的 2/3。
- **确认卡收起**：高度过渡到结果行，内容交叉淡入。
- **贴底滚动**：用户在底部时新内容到达自动跟随，平滑滚动；用户向上翻看时不跟随，并在输入框上方淡入“回到底部”按钮。

### 6.3 减少动态效果

遵循系统“减少动态效果”（项目已有 `use-reduced-motion`）：取消位移、高度过渡和平滑滚动，只保留不超过 100ms 的透明度变化或直接切换；渐变与发光保留为静态（不流动、不脉动），“正在思考”的光泽改为静态渐变文字；流式光标不呼吸、以固定透明度显示，淡出缩短为 100ms；新块不做淡入；思考原文的展开收起直接切换。

## 7. 性能

- **流式合并**：流式片段先进入缓冲，每帧（`requestAnimationFrame`）最多提交一次到 React 状态。
- **增量词法分析**：文字只是变长时，保留上一次的顶层 token，只从“仍可能改变的尾部”开始重新分析：最后一个非空白 token，连同与它之间没有空行的前一个 token，以及它前面隔着空行的列表（其后的段落可能变成下一项）。尾部出现引用式链接定义、或文字不是在原有基础上变长时，整篇重新分析；结果与整篇分析一致（有单元测试逐个前缀比对）。流式时尾部先补全未闭合的 `**`、`*`、`_`、`~~`、行内代码，半截的 `[文字](地址` 只显示文字，表头已到时提前补上分隔行，避免文字在标记与格式之间闪动；未闭合的代码围栏本身就按代码显示。每个顶层块是按序号作 key、按源文与是否在写比较的 memo 组件，已完成的块不再解析也不再渲染；单条消息的流式更新不触发其他消息重渲染。
- **只动画合成属性**：位移与淡入只用 `transform` 与 `opacity`；高度过渡只用于少数一次性的展开收起，流式增长不做高度动画。
- **长对话**：已离开视口的消息使用 `content-visibility: auto` 并配合预估高度；超过一定条数（暂定 200）再考虑虚拟列表，与邮件列表共用 `@tanstack/react-virtual`。
- **渐变与发光**：流动效果通过移动一个预先绘制好的渐变层（`transform` 或 `background-position`）实现，柔光用固定的模糊层并只改变其透明度；不逐帧改变 `box-shadow`、`filter: blur()` 半径或用 `@property` 逐帧重算锥形渐变角度。只在 AI 工作期间运行，结束即停。
- **后台**：窗口隐藏或页面不可见时暂停所有动画、渐变流动与发光；流式数据照常接收，回到前台时一次性呈现，不补播动画。
- **隔离重渲染**：输入框的输入不触发消息列表重渲染；单条消息的流式更新（文字与思考原文同样按帧合并）不触发其他消息重渲染；思考行的秒数只重渲染该行。
- **依赖体积**：新依赖需说明体积与用途。`marked` 约 12 KB（gzip，实测 v17.0.6 压缩包 12.4 KB），与写信窗口 Tiptap Markdown 扩展共用同一份（`bun.lock` 中只有一个版本），引入后从写信编辑器的懒加载块移入主包。代码高亮、公式、图表等重型渲染首期不支持，回复中的代码块按等宽文本显示，只加语言标注与复制按钮。

## 8. 无障碍与国际化

- 对话列表为 `role="log"`；AI 回复生成完成后以礼貌级 `aria-live` 播报一次，生成中不逐字播报，停止或失败时播报状态。
- 确认卡出现时把焦点移到卡片标题（若用户正在输入，则只播报不抢焦点）；处理后焦点回到输入框。
- 邮件引用标签、工具行的展开按钮都有完整的无障碍名称。
- 所有文案中英文同时提供；AI 回复的语言跟随用户提问，界面文字跟随界面语言。

## 9. 待定问题

- 写信窗口的原地 AI 功能（工具性能力），单独设计；阅读区只做了邮件摘要，回复建议、待办提取与整个会话的总结尚未做。
- 对话跨入口延续与持久化已定：全局对话岛与「此刻」共用同一段对话，按“保存对话记录”设置保存在本机。
- 目标平台 WebView 对 View Transitions API 的支持情况，需三平台实测。
- AI 渐变的具体色标，以及在浅色、深色和各强调色下的观感，需出样稿比较后确定。
- 对话岛与更新提示、toast 在右下角可能重叠，需实机检查位置。
