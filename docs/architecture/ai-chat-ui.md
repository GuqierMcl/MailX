# AI 交互界面

状态：**Proposed** · 2026-11-14。尚无实现。本文定义内置 AI 在前端的共用构件、各入口的形态、视觉与动效规则和性能要求，适用于[「此刻」页面](now-page.md)的对话，以及以后阅读区、写信窗口和命令面板中的 AI 入口。界面整体规则仍以[界面设计语言](ui-design.md)为准；权限与确认见[内置 AI 工具权限](ai-permissions.md)，运行生命周期与数据披露见 [AI Runtime](../ai-runtime/README.md)。

## 1. 原则

- **与整体风格一致**：现代、简约、克制。AI 的文字、间距和图标与邮件阅读、写信保持同一套语言。
- **AI 有自己的视觉标识，但点到为止**：霓虹渐变与发光边框是 AI 能力的识别符号，可以使用，但只用在“AI 在这里 / AI 正在工作”的少数位置，不铺满界面，不影响整体的平衡与可读性，规则见 4.6。
- **过渡优雅自然**：每个状态变化都有衔接，不跳变；动效短、轻、有方向感，只用于说明“什么出现了、去了哪里”，不为装饰而动。
- **体验优先**：随时可停止、可返回、可撤销；不打断用户手头的工作；AI 不可用或失败时界面安静地退回，不制造焦虑。
- **性能是约束而非优化项**：流式输出、长对话和后台常驻都不能让界面掉帧或持续占用 CPU。

## 2. 选型：自建构件，不引入现成聊天组件库

AI Elements、assistant-ui 等现成组件库不直接引入，作为交互参考：

1. 模型调用在 Rust core，前端经 Tauri 事件接收带序号的流式片段，掉线后按 Run 快照恢复；数据的权威在 core，套用组件库自带的状态模型需要额外的转换层。
2. 前端的 shadcn 使用 Base UI 底层（`base-mira` 风格），这类库多基于 Radix，混用会带来两套弹层与焦点管理。
3. 它们默认的气泡、卡片与边框需要大幅改造，才符合“岛内不加卡片边框和分割线”的约定。
4. MailX 的关键构件（邮件引用、确认卡、建议按钮、带 revision 的草稿修改建议）这些库都没有。

可以引入解决单一通用问题、体积小、无样式的依赖（例如“贴底滚动”），引入前评估体积、维护状态与许可证。现成库的组件代码不复制进仓库。

## 3. 分层

代码放在 `frontend/src/features/ai/`：

| 层 | 职责 |
| --- | --- |
| 数据层 | `useAiConversation(context)` 等 hook：发起与取消 Run、合并流式片段、按快照恢复、外发同意、确认请求与结果。只经 `MailxClient` 访问 core，不直接请求模型。无界面。 |
| 构件 | 消息与片段渲染、输入框、确认卡、引用、建议、AI 标记、状态行。只依赖数据层的类型，不关心所在入口。 |
| 入口 | 各处按场景组合构件并提供上下文（「此刻」、阅读区、写信窗口、命令面板）。 |

共用的是“AI 交互构件”，聊天只是其中一种组合；写信窗口以修改建议为主，不强行套用聊天形态（见第 5 节）。

## 4. 构件

### 4.1 消息

- **用户消息**：靠右，淡底色（`bg-muted` 一档），圆角与列表选中态一致，无边框；最大宽度约内容列的 80%。
- **AI 回复**：不加气泡，直接作为正文排版，字号、行高与阅读区一致，左对齐占满内容列。回复开头不放头像；第一段前有一个小的星芒标记，表示由 AI 生成。
- 消息之间用留白区分，同一角色的连续消息间距较小，换角色时间距较大；不加分割线和时间戳行，时间在悬停时以 Tooltip 显示。
- 每条 AI 回复底部在悬停或聚焦时淡入一行小操作：复制、重新生成；不常显。

### 4.2 回复中的片段

一条 AI 回复由有序片段组成，按到达顺序展示：

| 片段 | 呈现 |
| --- | --- |
| 文字 | 安全渲染的受限 Markdown：段落、列表、粗斜体、行内代码、引用；不渲染 HTML，不自动加载链接与图片，链接点击后交给系统浏览器，显示完整地址 |
| 工具进行中 | 一行弱化小字与小图标，如“正在搜索邮件…”，完成后折叠为“搜索了 12 封邮件”，可展开查看调用了什么（不显示原始参数 JSON） |
| 邮件引用 | 行内小标签：发件人头像（或账号色点）＋主题截断，悬停显示发件人、时间和主题全文，点击打开该邮件 |
| 建议 | 回复末尾一组文字按钮（如“归档这 3 封”），点击后按权限规则执行或进入确认 |
| 确认卡 | 见 4.4 |
| 未完成 | 被取消或中断的回复末尾一行弱化小字“已停止”，可“继续生成” |
| 失败 | 一行平实的原因与“重试”，不用红色大块提示 |

渲染器在实现时评估：优先考虑复用仓库已有的 Tiptap 及其 Markdown 扩展以只读方式渲染，避免新增依赖；若流式场景下反复解析的开销不可接受，再选用轻量的流式 Markdown 渲染方案。无论哪种，都禁止原始 HTML。

### 4.3 输入框

- 单行胶囊形，聚焦后按内容增高，最多约 6 行后内部滚动；高度变化平滑（见第 6 节）。聚焦时描边变为 AI 渐变，生成中描边流动并带淡柔光（见 4.6）。
- 右侧只有一个主按钮：有内容时为“发送”，生成中变为“停止”，两者原位交叉淡入，不改变按钮尺寸。
- `Enter` 发送，`Shift+Enter` 换行；输入法组字时 `Enter` 不发送（沿用快捷键守卫的判断）。`Esc`：生成中先停止，再按返回上一级。
- 占位文字随入口变化（如“问问你的邮件”“问问这封邮件”）。
- 以后可支持用 `@` 引用邮件或联系人，以小标签插入；首期不做。

### 4.4 确认卡

- 代表一个独立对象，是“岛内不加边框”的允许例外：细轮廓（`ring-1 ring-foreground/10`），圆角，内边距与附件元素同级，不加阴影。
- 内容由宿主根据当前数据生成（见[内置 AI 工具权限](ai-permissions.md#3-确认机制)）：标题写明动作（“发送这封邮件？”），下方是要素清单；风险信号用琥珀色小字逐条列出，不用整卡变色。
- 按钮：右侧主按钮为动作本身（“发送”），左侧为“取消”；默认焦点在“取消”。处理后卡片原位收起为一行结果（“已发送 · 撤销”或“已取消”），不留下大块历史卡片。
- 确认卡出现时，如用户不在可见位置，输入框上方淡入一个小提示“有一项操作等待你确认”，点击滚动到卡片。

### 4.5 状态与空态

- 生成开始到首个片段之间显示一行“正在思考…”，文字上有一道缓慢流过的 AI 渐变光泽；超过约 10 秒追加“仍在等待模型响应”，不显示假的进度条。
- 对话为空时不放示例问题列表；「此刻」页面以问候和统计作为背景，阅读区和写信窗口直接显示输入框。

### 4.6 AI 视觉标识：霓虹渐变与发光

**AI 渐变**是一组固定的冷暖霓虹色（暂定青蓝 → 蓝紫 → 品红），定义为共用 CSS 变量（如 `--ai-gradient` 与各色标），浅色、深色各有一套：浅色主题降低饱和与亮度，避免发灰发脏；深色主题可更亮，但限制光晕的透明度。它不跟随强调色：AI 标识需要在任何外观下都能被认出，同时也避免与用户选的强调色混在一起分不清。

用在哪里：

| 位置 | 静止时 | AI 工作时 |
| --- | --- | --- |
| 星芒标记（AI 生成内容、入口图标） | 渐变填充的小图标 | 不变 |
| AI 输入框 | 普通输入框外观；聚焦时描边变为 1px 渐变 | 渐变描边缓慢流动，外侧有很淡的柔光（模糊半径小、透明度低） |
| “正在思考” | — | 文字上流过一道渐变光泽 |
| 「此刻」的 AI 概述句 | 星芒标记 | 生成期间概述句下方一道细的渐变光带，完成后淡出 |
| 阅读区 / 写信窗口的 AI 入口按钮 | 渐变星芒图标，按钮本身照常 | 图标缓慢流光 |
| 写信窗口的修改建议 | 建议文字左侧一道细渐变竖条 | — |

不用在哪里：

- **正文文字**：AI 回复的正文、邮件内容、统计数字不用渐变色和发光，保证可读。
- **确认卡与风险提示**：确认卡保持中性的细轮廓，让“要不要执行”这个判断不被装饰干扰；风险信号仍用琥珀色。
- **大面积背景**：不把整块面板、整个岛或对话区铺成渐变；「此刻」页面的时段氛围背景走自己的规则（跟随强调色），不与 AI 渐变叠加。
- **错误与失败**：不发光，安静退回。

平衡规则：

- 同一视图里同时“发光”的元素最多一个（通常是正在工作的那一个）；其他 AI 元素只保留静态的渐变图标或描边。
- 发光只表示状态：AI 工作时出现，结束后约 300ms 内淡出，不常亮。
- 渐变描边最粗 1.5px，柔光不越出元素约 8px；不使用多层阴影堆叠的强光效。
- 对比度：渐变只用于装饰与图标，文字颜色仍取前景色 token。

## 5. 各入口

| 入口 | 形态 | 上下文 |
| --- | --- | --- |
| 「此刻」 | 内容列内的完整对话；发出第一句后概览收成顶部一行摘要，`Esc` 或“返回”回到概览 | 全部可用账号 |
| 阅读区 | 阅读区内可收起的 AI 面板，问“这封邮件 / 这个往来”；位置（右侧还是底部）待定 | 当前邮件与所在往来 |
| 写信窗口 | 以修改建议为主：选中文字或整篇后选择“改写 / 更正式 / 更简短”等，或输入要求；结果以差异形式内联展示，“接受 / 放弃”，接受时校验草稿 revision | 当前草稿 |
| 命令面板 | “问 AI”命令，打开最合适的入口并带上当前上下文 | 当前视图 |

- 对话按入口分开，只在本次运行内保留；是否跨入口延续（如“在「此刻」中继续”）与是否持久化待定。
- 写信窗口是独立系统窗口，构件同样可用；修改建议不会自动写入草稿。

## 6. 动效

### 6.1 时长与缓动

沿用现有界面的节奏（现有组件多为 100 / 150 / 200ms，配 `ease-out`），AI 界面不另起一套：

| 用途 | 时长 | 缓动 |
| --- | --- | --- |
| 悬停、按钮状态、小操作淡入淡出 | 100–150ms | `ease-out` |
| 片段出现、确认卡收起、输入框增高 | 200ms | 减速曲线（如 `cubic-bezier(0.2, 0, 0, 1)`） |
| 视图切换（概览 ↔ 对话、面板展开收起） | 250–300ms | 同上；离开用更短的时长（约为进入的 2/3） |

实现时把这几档缓动和时长定义为 `index.css` 中的共用 CSS 变量，AI 构件与以后的界面共用，不在组件里写死数值。

### 6.2 具体衔接

- **新消息**：用户消息自底部上移约 4px 并淡入；AI 回复的新片段只淡入，不位移，避免流式时文字抖动。
- **流式文字**：按到达的片段整段追加，不做逐字打字机效果；新增的文字可在约 150ms 内从较淡过渡到正常颜色，让出现过程柔和而不拖慢阅读。
- **工具行**：进行中 → 完成时，文字原位交叉淡入，高度不变。
- **概览 ↔ 对话**：问候与统计向上收拢并淡出，收成顶部摘要行；对话列表自下淡入。返回时反向。优先使用 View Transitions API（目标平台的 WebView 不支持时退回为简单的交叉淡入）。
- **阅读区 AI 面板**：沿用阅读区折叠的方式展开，内容在宽度到位后再淡入，避免挤压时文字重排的闪动。
- **确认卡收起**：高度过渡到结果行，内容交叉淡入。
- **贴底滚动**：用户在底部时新内容到达自动跟随，平滑滚动；用户向上翻看时不跟随，并在输入框上方淡入“回到底部”按钮。

### 6.3 减少动态效果

遵循系统“减少动态效果”（项目已有 `use-reduced-motion`）：取消位移、高度过渡和平滑滚动，只保留不超过 100ms 的透明度变化或直接切换；渐变与发光保留为静态（不流动、不脉动），“正在思考”的光泽改为静态渐变文字。

## 7. 性能

- **流式合并**：流式片段先进入缓冲，每帧（`requestAnimationFrame`）最多提交一次到 React 状态；Markdown 只重新解析最后一个未完成的块，已完成的块缓存结果不再渲染。
- **只动画合成属性**：位移与淡入只用 `transform` 与 `opacity`；高度过渡只用于少数一次性的展开收起，流式增长不做高度动画。
- **长对话**：已离开视口的消息使用 `content-visibility: auto` 并配合预估高度；超过一定条数（暂定 200）再考虑虚拟列表，与邮件列表共用 `@tanstack/react-virtual`。
- **渐变与发光**：流动效果通过移动一个预先绘制好的渐变层（`transform` 或 `background-position`）实现，柔光用固定的模糊层并只改变其透明度；不逐帧改变 `box-shadow`、`filter: blur()` 半径或用 `@property` 逐帧重算锥形渐变角度。只在 AI 工作期间运行，结束即停。
- **后台**：窗口隐藏或页面不可见时暂停所有动画、渐变流动与发光；流式数据照常接收，回到前台时一次性呈现，不补播动画。
- **隔离重渲染**：输入框的输入不触发消息列表重渲染；单条消息的流式更新不触发其他消息重渲染。
- **依赖体积**：新依赖需说明体积与用途；代码高亮、公式、图表等重型渲染首期不支持，回复中的代码块按等宽文本显示。

## 8. 无障碍与国际化

- 对话列表为 `role="log"`；AI 回复生成完成后以礼貌级 `aria-live` 播报一次，生成中不逐字播报，停止或失败时播报状态。
- 确认卡出现时把焦点移到卡片标题（若用户正在输入，则只播报不抢焦点）；处理后焦点回到输入框。
- 邮件引用标签、工具行的展开按钮都有完整的无障碍名称。
- 所有文案中英文同时提供；AI 回复的语言跟随用户提问，界面文字跟随界面语言。

## 9. 待定问题

- 阅读区 AI 面板放在右侧还是底部。
- 对话是否跨入口延续、是否持久化。
- 回复渲染器选用 Tiptap 只读还是轻量流式 Markdown 方案。
- 目标平台 WebView 对 View Transitions API 的支持情况，需三平台实测。
- AI 渐变的具体色标，以及在浅色、深色和各强调色下的观感，需出样稿比较后确定。
