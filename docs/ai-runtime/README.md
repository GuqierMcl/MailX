# AI Runtime

状态：**Proposed** · 2026-11-15 修订。服务商与模型配置、非流式 `complete` 调用和以模型为来源的翻译已有实现；流式客户端、`core/src/assistant/` 中的运行管理与智能体循环（含同意、上限、取消、「此刻」概述缓存）和 `assistant` 设置已在 core 实现；暂停等待确认、撤销整理所需的数据与桌面 IPC（主窗口命令与事件，见[应用服务 API](../contracts/app-api.md#ai-助手主窗口)）已实现，仅有自动测试；界面已有“设置 → 集成 → AI → 助手”与「此刻」AI 概述句（自动测试与浏览器预览，未在桌面实机或真实服务商上验证）；「此刻」对话（含确认卡、撤销、不支持工具调用的模型只回答问题）已实现，阅读区的邮件摘要（第 2 节）与写信窗口的 AI 写作（第 2 节）也已实现，同样未在桌面实机与真实服务商上验证。实现选型见 [ADR 0005](../adr/0005-builtin-agent-loop.md)，权限见[内置 AI 工具权限](../architecture/ai-permissions.md)，界面见 [AI 交互界面](../architecture/ai-chat-ui.md)。

## 1. 定位

内置 AI 是邮箱里的助手：能做本地 MCP 能做的事，设置项完整，但机制比 Claude Code、OpenCode 这类编程智能体简单得多。

**能力与 MCP 对齐。** [工具层](../architecture/agent-tools.md)中现有的读取、整理、草稿、附件、发信与发件箱工具全部对内置 AI 开放；与 MCP 一样不提供删除邮件。MCP 专属的“在应用里打开邮件 / 草稿”在内置 AI 中改为对话里可点的卡片，不抢焦点。

**省掉的机制。**

| 编程智能体常见 | MailX 内置 AI |
| --- | --- |
| 多种权限模式、按工具与参数的允许 / 拒绝规则、hooks、沙箱 | 设置里按操作类别各一个选项，见[权限](../architecture/ai-permissions.md) |
| 子代理、计划模式、待办列表、斜杠命令、技能 | 不做；只有一个对话循环和几个固定任务 |
| 上下文压缩、长会话管理 | 不做压缩；单次对话有轮数与长度上限，接近上限时提示新开对话 |
| 项目说明文件、长期记忆 | 设置里一段“自定义指令” |
| 第三方 MCP、文件系统、命令执行、联网搜索 | 不做；工具只有邮件相关的这些 |
| 独立的授权凭据系统 | 不需要：循环在 core 内，需要确认时运行暂停，由主窗口回应后继续 |

AI 关闭、离线或失败时，收发、搜索与其他功能照常可用。

## 2. 两类运行

- **固定任务**：由界面发起、提示词预设，例如「此刻」概述句、总结当前邮件或往来、改写选中文字、起草回复、待办建议。内容由应用选定，最多允许少量只读工具；不依赖模型支持工具调用，本地小模型也能用。
- **对话**：用户在「此刻」（以后还有阅读区、写信窗口）与助手对话，可使用全部工具。

待办建议只是界面里的建议列表，不自动创建外部任务；邮件中的日期可能不完整，输出依据和不确定性，不擅自补一个确定的截止日。

**邮件摘要**（`RunKind::EmailSummary`，实现见 `core/src/assistant/email_summary.rs`）是两个邮件固定任务之一：对当前打开的一封邮件调用一次模型，不带工具，输出上限 8192 个 token（模型的输出上限更小时取其值，思考也计在内），流式输出与其他运行相同，`toolsAvailable` 为 `false`。邮件由 core 按 id 经工具层的 `mail_read` 读取（正文最多 24,000 字符），助手设置的账号范围照常生效：范围外或不存在按 `notFound`，正文未下载按 `bodyNotCached`。邮件内容作为不可信的 `<email>` 数据放进提示词。篇幅为简短、详细、要点三种，语言可跟随界面、用邮件原语言或指定一种；省略时取设置中保存的值。同意规则与其他运行相同（`awaitingConsent`）。结果的缓存见第 4 节。

**写信的 AI 写作**（`RunKind::ComposeAssist`，实现见 `core/src/assistant/compose.rs`）是另一个邮件固定任务：针对一份草稿调用一次模型，不带工具，输出上限 8192 个 token，流式输出与其他运行相同，`toolsAvailable` 为 `false`。任务为 `ComposeTask` 的三种之一：按说明起草（`draft`，可指定语言）、按风格改写（`rewrite`，风格为润色、更正式、更友好、更简洁、展开、翻译成某语言或自定义说明）、校对（`proofread`）。core 按草稿 id 读取草稿，助手设置的账号范围照常生效，范围外或不存在按 `notFound`；草稿信头总是带上，起草时另经工具层 `mail_read` 读取草稿回复 / 转发的原邮件（正文最多 8,000 字符）。界面发来的是用户自己的文字（选中的内容或自己写的正文，Markdown）；core 把草稿、原邮件、说明与文字分别包成不可信的 `<draft>` / `<original_email>` / `<instruction>` / `<text>` 区段。**运行只读草稿：答案只是供编辑器预览和插入的 Markdown，从不写入草稿**；因输出上限结束（`length`）时卡片提示被截断。单次最多 20,000 字符文字、2,000 字符说明；同一窗口发起新任务会先取消上一个。同意规则与其他运行相同（`awaitingConsent`）。回复建议、待办建议与整个会话的总结尚未实现。

对话可以带上用户正在看的内容（当前邮件、选中的邮件或当前草稿，`ChatContext`）。界面只发 id；core 在第一轮模型请求前用工具层按助手设置读取它（`core/src/assistant/view.rs`），账号范围之外或不存在的 id 当作没有上下文。读取结果作为一轮运行系统提示末尾的 `<tool_result name="current_view">` 交给模型，只对这条消息有效、不进对话历史，涉及的账号照常记入对话。打开邮件时正文取前 4,000 字符（不支持工具调用的模型 8,000），选中的每封 400 字符，正文不在本机的只给头部。

## 3. 结构

```text
界面（主窗口）  ──IPC 命令 / 事件──▶  运行管理（core）
                                        │
                                        ├─ 智能体循环：消息 → 流式请求 → 工具 → 结果 → …
                                        │        │                 │
                                        │   流式客户端          工具层（与 MCP 共用）
                                        │   （AI 专用路由）      RequestContext：BuiltinAgent
                                        └─ 同意、确认、取消、上限
```

1. **流式客户端**（`core/src/ai/client`）：OpenAI 兼容（Chat Completions）与 Anthropic Messages 两种协议的流式请求与工具调用。复用 `net::http` 的路由连接（代理失败不回退直连），响应体按块读取、解析 SSE，统一为内部事件：文字片段、思考片段、工具调用（参数增量拼接完成后才交出）、要回传的思考数据、结束原因、用量。服务商原文不出模块，错误映射为已有的固定错误码。
2. **运行管理**：运行只保存在内存里，按 `runId` 管理；状态、累积输出和每个流式片段的单调序号随事件推给主窗口，前端重连后可按快照恢复。应用重启不恢复运行，也不自动重新请求。对话记录（见第 4 节）单独保存在本机数据库，与运行无关。
3. **智能体循环**：组装系统提示（固定规则 + 自定义指令 + 当前上下文说明）、历史消息与工具定义，发起流式请求；回复中有工具调用就逐个执行，结果作为不可信材料写回，再次请求，直到模型给出最终回答或达到上限。需要确认的工具让运行进入等待确认，见第 6 节。
4. **思考的捕获与回传**：见下文。
5. **工具**：直接调用现有工具层（`Tools::call`），主体为 `Principal::BuiltinAgent { run_id }`，授权由宿主按助手设置生成。工具定义来自 `Tools::list(Audience::BuiltinAgent)`，不另写一套。

### 思考的捕获与回传

会思考的模型在回答前先输出推理。核心只按两种协议处理，不区分服务商（实现见 `core/src/ai/reasoning.rs` 与两个协议解码器）：

- **捕获**：OpenAI 兼容协议读 `delta.reasoning_content`，以及值为字符串的 `delta.reasoning`（OpenRouter、vLLM 等的写法），并记住服务器用的是哪个字段名；其他形状（如结构化的 reasoning 对象）不读。Anthropic 协议读 `thinking` 块（`thinking_delta` 文字与 `signature_delta` 签名）和 `redacted_thinking` 块（不透明的 `data`），并记下它们与 `text`、`tool_use` 块的先后。
- **保存**：思考随这一轮的助手消息保存（`AssistantReasoning`）：要回传的原样数据（OpenAI 兼容是“字段名 + 文字”，Anthropic 是按原顺序排列的思考块，签名与 `data` 不改动），产生它的来源（协议、连接 id、服务地址、模型），以及每一段思考的时长与位置（只供界面重现）。它进入内存中的对话，也按“保存对话记录”与其他内容一起写入本机记录（行内容是 JSON，新增字段可省略，旧记录照常读取，不需要迁移）。
- **回传规则：服务器发来什么就原样发回什么，别的不加。** OpenAI 兼容：之后的请求里，这条助手消息带上同名字段与原文；服务器从没发过思考的，请求里就没有这个字段，所以 OpenAI 本身与严格校验字段的服务器看不到未知字段。部分服务器要求带工具的对话必须回传思考，否则拒绝下一次请求。Anthropic：思考块按原位置放回助手消息的内容里，签名与 `data` 不变（扩展思考配合工具调用时协议要求如此）。
- **只回传给同一来源**：请求发往的协议、连接、地址与模型和保存时完全一致才回传；中途换了模型或连接，旧思考不再发送（签名与加密数据绑定原模型，别处用不了）。已知限制：换模型后继续同一对话，新模型看不到之前的思考；要求回传的服务器在换回原模型前也只能看到没有思考的历史。
- **上下文估算**：会被回传的思考计入第 8 节的对话预算，不会回传的不计。
- **界面**：思考按段经 `reasoning` / `reasoningEnd` 事件实时推给主窗口（一段从第一个思考片段开始，到随后的文字、工具调用或本轮结束为止），快照与保存的对话都带各段的文字、时长与位置；签名等回传数据不出核心。
- 没有任何服务商专属的思考开关：请求里不加 `thinking`、`reasoning_effort` 之类的参数，模型按自己的默认方式思考。

## 4. 运行生命周期

```text
awaitingConsent → running ⇄ awaitingConfirmation
                     │
                     ├── completed
                     ├── failed
                     └── canceled
```

- 已有有效同意时直接进入 `running`。
- 取消会断开 HTTP 流并停止循环；已产生的服务商计费无法撤回。被取消或中断的回复保留已输出部分并标为“未完成”，不会被写成完整草稿。
- 重做一条回复（`regenerate`）或编辑一条用户消息（`edit`）在开始前就把要替换的部分从内存里移走，并记下当时的对话与保存进度；运行没能开始时按记录原样放回。运行开始后，新的内容像普通的一轮一样保存，从被移走的第一行写起，覆盖存储里的旧行（每条用户消息的存储行号随对话记在内存里，读入已保存的对话时一并算出；找不到行号时这段对话不再保存，而不是存错）。要移走的部分里有任何改信、写草稿或发信的调用时不重做也不编辑（`conflict`），已发生的变动不能撤回。继续生成（`continuation`）只在最后一条是助手回复时开始，历史照旧，模型接着写。
- 修改草稿的工具沿用草稿版本号（`expectedRevision`），用户在此期间改过草稿时调用失败，模型收到冲突结果。
- 写信的 AI 写作只读草稿：取消、失败或中断时，已输出的部分只留在卡片里，不会写入草稿。
- 固定任务的结果可以缓存，键包括所选内容摘要、模型、提示词版本和语言；内容或选择变化后失效，不同账号范围不复用。「此刻」概述句的输入还有 core 算出的“值得一提的事”、用户本地的时段与星期、今天的节日或节气，并把最近几句概述附给模型以免重复；最近几句不进缓存键（见[「此刻」页面 5.1](../architecture/now-page.md#51-概述句)）。

邮件摘要缓存在本机数据库（`message_summaries`，迁移 `0035`，实现见 `core/src/storage/summaries.rs`），主键为（邮件、篇幅、语言）；只在 `source_sha256`（主题、发件人、接收时间与正文文字的哈希）与 `prompt_version`（`EMAIL_SUMMARY_PROMPT_VERSION`）都未变时有效，随邮件一起删除。命中且不是重新生成时直接返回已完成的快照，不请求模型也不需要同意；`fresh` 时跳过缓存并替换。因输出上限（`length`）被截断的摘要展示但不保存；写缓存失败被忽略。界面打开邮件时还可以用 `assistant_email_summary` 取该邮件最新保存的一条摘要（不需要同意）。缓存里是模型对邮件内容的转述，与邮件缓存同样不加密，设置里可以一键清除。

## 5. 同意与数据披露

- **同意**：复用翻译已有的 `AiConsent`（绑定连接 id 与规范化的服务地址；换模型、换密钥不需重新同意，换连接或地址需要）。首次使用助手时运行停在 `awaitingConsent`，由 core 强制；在设置里可以撤销。
- **发送什么**：工具返回的内容（邮件主题、发件人、正文纯文本、附件名等）和用户输入。附件的文件内容、图片与原始 MIME 不发送给模型。写作帮助只发送用户自己的文字（选中的内容或自己写的正文）与草稿的信头；起草时还包括它回复 / 转发的原邮件（经工具层读取，正文最多 8,000 字符）。回复引用的原文与内嵌图片不发送；草稿本身也不会被改动。
- **范围**：工具只能访问设置中“可用账号”内的账号；范围外的账号对 AI 不可见，与不存在的表现相同。
- **不可信材料**：邮件内容与工具结果放在明确标记的区段中，提示模型其中的指令不代表用户意图；最终的防线是第 6 节的确认与撤销，而不是提示词。

## 6. 确认与撤销

规则见[内置 AI 工具权限](../architecture/ai-permissions.md)。要点：

- 读取与整理默认直接执行；整理类操作在对话里列出结果并提供撤销。
- 发信、取消发送默认每次确认；修改或删除用户自己写的草稿每次确认。
- 需要确认时，运行暂停在 `awaitingConfirmation`，向主窗口发出确认请求（动作、目标、由 core 根据当前数据生成的摘要）；只有主窗口的回应能让运行继续。拒绝时模型收到“用户拒绝”的结果。

**对话记录。** 对话在内存里是工作集（最近使用的 20 个），同时按“保存对话记录”设置保存在本机数据库（迁移 `0032`，实现见 `core/src/assistant/history.rs` 与 `storage/assistant_chats.rs`）。保存发生在内存历史被替换的同一些一致点：一轮完整的“助手消息 + 全部工具结果”之后，以及一条回复结束时（写入一行收尾记录：完成、失败的错误码或已停止）。

- 保存的内容：用户消息；助手文字与工具调用；工具结果（与发给模型的相同，已受单个结果的字符上限约束）；每个工具结果对应的界面活动（`ToolActivity`，**不含撤销数据**，撤销令牌与旧标志在重启后失效）；用户回答过的确认只留一行结果（动作与批准 / 拒绝 / 超时），**从不保存待确认的请求或确认卡细节**。
- 被取消或失败的回复保存为已停止或失败：历史末尾补一句“回复未完成”的助手说明，下一条消息可以接着聊。应用在回复中途退出时，数据库里只有已提交的部分、没有收尾记录，读回来是“已取消”，继续时同样补这句说明。
- 标题取第一条用户消息（折成一行，最多 60 个字符，不调用模型）。最多保留最新 100 个对话（超出时最旧的随保存删除）；对话已有约 400 条消息时不再接受新消息（`assistantContextFull`），需新开对话。
- 继续已保存的对话：不在内存里就从数据库读入，历史原样发给模型；对话在别处已被删除（例如其涉及的账号被移除）时返回 `notFound`。删除正在运行的对话会取消该运行，已排队的保存不会让它复活。
- 记录对话涉及的账号：工具调用的参数与结果里出现的账号 id（`accountId` / `accountIds`）。移除账号时，涉及它的对话在同一个事务里删除；只列出账号（`accounts_list`）不算涉及。
- “保存对话记录”关闭后，新的轮次不再保存，已保存的保持原样直到用户删除或“清除全部”；关闭期间进行过的对话之后即使重新打开开关也不会补存。

## 7. 设置

在“设置 → 集成 → AI”增加“助手”一组，保存在核心 `settings.json`：

| 设置 | 说明 |
| --- | --- |
| 启用助手 | 关闭时不显示任何对话入口，固定任务也不运行 |
| 对话模型 | 默认跟随默认模型；可单独选择 |
| 内容发送同意 | 显示已同意的连接，可撤销 |
| 可用账号 | 默认全部，可排除个别账号 |
| AI 可以做什么 | 整理邮件、AI 自己的草稿：直接执行（默认）/ 每次询问；发信：每次确认（默认）/ 直接发送 |
| 自定义指令 | 一段文字，附加到系统提示，例如称呼、语气、签名习惯 |
| 保存对话记录 | 默认开；保存在本机，可逐个删除或“清除全部”。关闭只停止保存新的轮次，已有记录保留（`assistant.saveHistory`，旧文件按开启读取） |
| 自动总结打开的邮件 | 默认关。开启后，打开正文不少于 200 字符的邮件时自动生成摘要，会把邮件发给模型（`assistant.summary.auto`） |
| 总是总结的发件人 | 小写地址列表，最多 500 个；来自他们的邮件打开时自动总结，不限长度（`assistant.summary.senders`） |
| 摘要的篇幅与语言 | 最近一次在面板里的选择：`brief`（默认）/ `detailed` / `points`；语言为跟随界面（默认）/ 邮件原语言 / 指定语言（`assistant.summary.style`、`assistant.summary.language`） |
| 摘要卡收起 | 全局记住摘要卡是否收起（`assistant.summary.collapsed`，默认 `false`） |
| 清除摘要 | 设置页的按钮，删除全部已保存的摘要，并显示清除的条数（`assistant_clear_email_summaries`） |
| 读取邮件的 HTML 结构 | 默认关。开启后 `mail_read` 额外返回净化后的 `html`（标题、列表、表格、链接），发给模型的内容明显增多，且含他人写的标记（`assistant.readHtml`，布尔，缺省 `false`）；只影响内置助手，MCP 不返回 `html` |

“AI 可以做什么”与“自定义指令”只影响对话，在对话界面上线前设置页不显示这几行（`AssistantGroup` 的 `chat` 开关）；它们已保存在设置中，默认值即上表所列。邮件摘要与写信的 AI 写作相关的几行不受这个开关影响，始终显示；写作帮助使用“启用助手”“对话模型”和“内容发送同意”，没有单独的设置。`assistant.summary` 手写损坏时逐项修复，不影响其他设置。

## 8. 上限与预算（初始值，实测后调整）

- 同时最多 2 个运行中的任务；写信窗口同一草稿只允许一个改写任务。
- 每条用户消息最多 20 轮工具调用；单轮最多执行 8 个工具调用。超过时停止并说明，用户可以继续。
- 单个工具结果沿用工具层的输出上限（正文默认 8,000、最多 32,000 字符）。
- 整个对话的输入估算接近模型上下文长度（取模型目录的 `context_length`，未知时按 32,000 token 估算）的八成时，不再追加，提示新开对话。
- 每次模型请求（对话的每一轮与「此刻」概述）：首个片段 30 秒、相邻片段间隔 60 秒（收到任何字节都重新计时，思考片段也算）、单次请求总时长 10 分钟，让一边思考一边持续输出的模型不被总时长截断（`CHAT_STREAM_LIMITS`，`core/src/ai/client/stream.rs`）。翻译等非流式调用的时限不变。超时保留已有输出并提示重试，不自动重试。
- 「此刻」概述句的输出上限为 4096 token（与模型目录的输出长度取较小者）：思考 token 也计入上限，太小会让先思考的模型一个字都写不出来。不发送任何服务商专属的“关闭思考”参数（见第 3 节的思考捕获与回传）；概述里的思考不显示，也不进缓存。因输出上限而被截断的概述句按失败处理，不展示也不缓存。
- 记录服务商返回的用量（如有），不把估算费用当账单。

## 9. 模型能力

- 模型目录标明不支持工具调用（`tool_call: false`）时，只提供固定任务和不带工具的对话（只回答当前上下文中的内容）。
- 能力未知时按支持处理；服务商因工具参数拒绝请求时，提示换用支持工具调用的模型。
- 不使用 JSON 模式或结构化输出参数；需要结构化结果的固定任务（如待办建议）用工具调用或宽松解析，解析失败就当普通文字显示。

## 10. 输出与安全

- AI 输出按纯文本或受限 Markdown 显示：不渲染 HTML，不自动加载链接或图片，链接点击后交给系统浏览器并显示完整地址。
- 工具调用与结果在对话里以简洁的行显示（“搜索了 12 封邮件”“归档了 3 封”），可展开查看，不显示原始 JSON。
- 完整提示词与对话内容不写日志；工具调用照常进入工具层审计（只有工具名、资源 id 与结果码）。
- 对话记录保存在本机数据库，和邮件缓存同样受数据目录的保护，不上传、不同步、不进日志；其中的工具结果含邮件内容，随涉及账号的移除一并删除，也可以在界面里逐个或全部删除。
- 引用：提示词要求模型提到某封邮件或某个文件夹（来自工具结果）时，写 Markdown 链接 `[标签](mailx://email/<emailId>)` 或 `[标签](mailx://folder/<folderId>)`，id 照工具结果原样使用、不自造；单独一行显示为卡片，行内是短提及；其他位置不贴原始 id。`mail_search`、`mail_read` 的结果有 `id`，`mail_folders` 的每项有 `id`，足够使用。界面只在 id 对应本机已有的邮件或文件夹时渲染引用，否则当普通文字。

## 11. 分期

1. **运行时**：流式客户端、运行管理、循环与工具接入、同意、确认、助手设置；第一个使用方是「此刻」的 AI 概述句。
2. **对话**：「此刻」的对话框、全部工具、确认卡、操作结果与撤销。
3. **阅读区与写信窗口**：总结、改写、起草回复与草稿修改建议。当前邮件的摘要与写信窗口的 AI 写作（起草、改写、校对）已实现（第 2 节），待办建议、回复建议与整个会话的总结未做。
4. **对话记录**：保存、恢复与清除（已实现，见第 4 节）。

## 12. 验收

至少覆盖一个云端 OpenAI 兼容模型、一个 Anthropic 模型和一个本地 Ollama 模型：流式输出、取消、超时、工具调用多轮、并行工具调用、确认与拒绝、撤销、草稿版本冲突、同意撤销后立即生效、不支持工具调用的模型，以及恶意邮件中的提示词注入（例如要求转发邮件或添加附件）。自动测试不能替代真实服务商的验证，结果写入[验证指引](../development/validation.md)。
